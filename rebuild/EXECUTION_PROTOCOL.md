# 조사·집필·검토·웹 제작 실행 절차

버전 2.0 · 2026-11-18. 이 절차는 GPT-6.2.sol / high reasoning으로 다음 명령 한 번에서 이어갈 수 있게 작성했다. 모델 성능에 대한 보증이나 설정 자동 변경 문서가 아니다. 계획을 잘게 나누고, 필요한 근거와 판단을 파일로 남겨 작업의 일관성을 유지한다.

## 1. 범위와 실행 원칙

- 목표는 자립형 교재와 학습 웹의 전면 개편이다. 기존 문장을 길게 바꾸거나 C 단원에 몇 문단 덧붙이는 작업으로 축소하지 않는다.
- 주 작성자가 설명 흐름·문체·용어·사례를 책임진다. 여러 에이전트의 답변을 그대로 이어 붙이지 않는다.
- 한 번의 조사·집필 묶음은 **하나의 독립적인 학습 질문을 충분히 설명하는 수업 또는 긴 수업의 자연스러운 절**이다. 초안은 보통 3천~7천 자 정도에서 검토하기 편하도록 나누되 길이 제한으로 자르지 않는다. 단원 하나를 단일 짧은 응답으로 완성하려 하지 않는다.
- 조사·본문·예제 검토를 가까이 붙인다. 모든 출처를 먼저 수집하고 나중에 기억으로 교재를 쓰지 않는다.
- 한 묶음 완료 후 다음 묶음으로 계속 진행한다. 토큰을 소진하기 직전에 나머지 단원을 요약본으로 만들어 ‘전체 완료’ 처리하지 않는다.
- 실제 호출 한도·사용자 중단·필수 선택 대기로 더 진행할 수 없으면 상태를 남긴다. 진행하지 못한 것을 진행했다고 말하거나 무한 자동 재개를 약속하지 않는다.

## 3. 단일 수업을 만드는 순서

### 3.1 수업 계약과 근거

1. BLUEPRINT의 해당 단원과 선행 개념을 읽고 ‘수업 뒤 무엇을 설명할 수 있어야 하는가’를 구체화한다.
2. 필수 설명 목록을 5~10개 정도의 실질적인 항목으로 쓴다. 목록 개수를 채우기 위한 작은 항목 분할은 피한다.
3. 공식 규격·논문·제품 문서의 **실제 필요한 본문 절**을 읽는다. 검색 요약과 abstract만으로 세부 동작을 기술하지 않는다.
4. 주장별 근거를 source ledger에 남긴다. 확인하지 못한 것은 pending으로 표시하고 본문에서 확정하지 않는다.
5. 예제의 데이터·질문·예상 결과를 먼저 고정한다. 필요한 새 용어와 기호를 목록화하고 처음 설명할 위치를 정한다.

### 3.2 본문 집필

도입은 독자가 알아볼 수 있는 문제나 장면으로 시작한다. 곧바로 다수의 정의와 경고를 나열하지 않는다. 개념을 소개한 뒤 실제 예에서 요소를 짚고, 과정과 결과를 해설한다. 조건이 바뀌면 무엇이 달라지는지도 보여준다.

본문은 자연스러운 한국어 존댓말을 기본으로 한다. 독자에게 지시만 하는 ‘구분한다/주의한다/사용한다’의 연속을 피한다. 지나친 친근체, 과장된 감탄, ‘핵심은’, ‘쉽게 말해’의 반복도 피한다. 기술 용어를 쉬운 말로 풀되 정확한 용어를 함께 익히게 한다.

**예시 — 기존의 부족한 문장**

> 같은 그래프를 Turtle, RDF/XML, JSON-LD로 기록할 수 있다. 추상 데이터 모델과 구문을 구분한다.

**수정 시 필요한 설명 요소**

‘민수는 사람이다’라는 한 사실이 주어/술어/목적어에 어떻게 대응하는지 먼저 설명한다. Turtle에서 `ex:Minsu`, `rdf:type`, `ex:Person`이 뜻하는 것을 풀고, prefix를 긴 IRI로 바꿔 보인다. 이어 같은 사실을 RDF/XML로 적은 짧은 코드와 각 핵심 표기의 역할을 보여준다. 표기 방법이 달라도 파싱 결과의 세 요소가 같다는 것을 표나 작은 그림으로 확인한다. 그 후에 ‘구문과 모델이 다르다’는 문장이 의미를 갖게 된다. 이 설명을 새 본문에서 실제로 완성해야 한다.

이 예시는 문체와 설명 순서의 지침이며 모든 수업의 템플릿은 아니다.

### 3.3 독립 검토와 수정

작성자의 의도를 추정하지 말고 실제 본문만 검토한다. 기술적 검토와 설명 검토를 분리한다. 작성자가 테스트를 모두 통과했다는 말로 설명 검토를 대체하지 못한다.

- 기술 검토: 핵심 주장·버전·근거가 맞는가? 예제에 숨은 가정이 있는가? 계산·파싱·질의 결과가 맞는가? 비교 대상의 조건이 동등한가?
- 설명 검토: 첫 등장한 용어·기호를 이해할 수 있는가? 왜 필요한지와 실제 작동을 연결했는가? 예제에서 본문에 없는 지식을 요구하는가? ‘설명할 수 있다’는 목표의 답을 본문에서 찾을 수 있는가?
- 수정 후 재검토: 지적한 위치가 실제로 고쳐졌는지 확인한다. 검토자의 총평만 저장하지 않는다.

각 단원의 `review.md`에는 차단 문제·수정 위치·남은 제한·근거를 기록한다. AI가 이해한 것처럼 응답했다고 실제 학습자의 이해가 입증된 것은 아니다. 사용자의 이후 피드백은 여전히 중요한 검증이다.

## 4. 출처와 연구 기록의 규칙

기술적인 설명은 1차 자료를 우선한다. 사용자가 준 블로그는 설명 방식과 궁금한 지점의 참고 자료로 읽고, 기술적 핵심은 규격·논문·공식 문서에서 대조한다. 공식 제품 블로그도 공급사 관점이며 독립적 성능 근거는 아니다.

`learning-v2/research/sources.json`의 권장 필드:

```json
{
  "source_id": "SRC-RDF11-CONCEPTS",
  "title": "RDF 1.1 Concepts and Abstract Syntax",
  "url": "https://www.w3.org/TR/rdf11-concepts/",
  "kind": "standard",
  "version_or_date": "2014 Recommendation",
  "accessed_on": "실제 확인 날짜",
  "sections_read": ["실제 읽은 절만"],
  "supports": [{"claim_id": "U04-C01", "section": "근거 절", "paraphrase": "해당 근거의 요지"}],
  "status": "pending_or_checked",
  "limitations": "근거가 보장하지 않는 것"
}
```

자료를 등록한 것과 해당 주장을 확인한 것은 별개다. `checked`는 문서 전체 정독을 의미하지 않는다. 연구 논문 수치에는 표·데이터·모델·평가 조건을 기록하고, 논문 결과·설계 제안·toy 예제·자체 실험을 구분한다. 교재에는 주장을 뒷받침하는 위치 가까이에 링크를 붙인다. 제작용 claim ID를 본문에 과도하게 노출하지 않는다.

현재 RDF 1.2 등 후속 규격의 지위는 집필 시 재확인한다. 이전 SOURCES의 문서 성격 표기도 그대로 신뢰하지 않는다. 특히 RDF 1.1 Primer는 Recommendation이 아닌 Working Group Note다. 공식 규격의 ‘This version/Latest published version’과 날짜를 기록한다.

원문을 길게 복제하지 않고 이해한 내용을 새로 설명한다. 그림은 직접 그리며 데이터·아이디어의 근거를 인용한다. 원본 그림을 쓸 때는 라이선스와 허용 범위를 확인한다. 검색 도구의 인용·요약 제한을 따른다.

연구 시작점은 기존 SOURCES.md와 learning/concepts/RESEARCH.md이며, 신규 출처 목록을 늘리는 것이 조사 완료가 아니다. S01 survey는 해당 절과 기법을 실제 읽고 U09~U12/U17에 연결한다. 모든 참고 논문 정독을 요구하지 않되 교재에서 설명하는 방법은 근거를 확인한다.

## 5. 예제·도해·인터랙션

### 공통 사례 운영

원천 자료와 예제 데이터는 하나의 기준 파일에서 관리한다. 본문 숫자·쿼리 결과·그림에 각각 수작업 복제하여 어긋나게 하지 않는다. 복잡한 실시간 연동이 필요 없으면 기준 fixture에서 정적 결과와 그림 데이터를 생성한다.

교육용 출력은 세 종류로 표시한다.

1. **실제 실행:** 엔진/라이브러리·버전·입력·명령·출력 기록이 있다.
2. **예상 결과:** 공식 의미에 따라 손으로 도출했으며 해당 엔진을 실행하지 않았다.
3. **교육용 모의 예:** 알고리즘 원리를 보여주는 합성 값이다. 실제 검색·LLM의 품질 결과가 아니다.

외부 유료 API나 대규모 인프라는 자립형 교재의 필수 조건이 아니다. 로컬에서 가능한 파싱·SHACL·작은 질의·계산을 확인한다. Neo4j를 실행하지 않았다면 Cypher를 실행 검증했다고 말하지 않는다. 이미 확인한 동일 예제를 이유 없이 반복 실행하지 않는다.

### 시각화 우선순위

| 우선 | 시각화 | 이해를 도울 변화 |
|---|---|---|
| 1 | RDF 사건 노드와 Property Graph 병렬 관계 | 같은 사건을 선택해 코드·속성·트리플 대응 확인 |
| 1 | Ontology 개념/개체/공리와 개정 | 잘못된 is-a를 바꾸면 어떤 해석이 달라지는지 확인 |
| 1 | RAG의 chunk·후보·context 추적 | 선택된 근거와 빠진 근거를 한 질문에서 확인 |
| 2 | 추론 vs SHACL | 공리/누락/타입을 바꾸고 서로 다른 결과 읽기 |
| 2 | Entity resolution | 후보·증거·병합/보류와 후속 영향 확인 |
| 2 | GraphRAG local/global | 선택 경로·원문·community report를 구분 |
| 2 | RAPTOR 계층/검색 | 요약 수준·두 탐색 경로와 최종 context 비교 |
| 3 | 지식 수명주기 | 정정·권한 변경 시 영향 산출물 추적 |

위 그림을 모두 애니메이션으로 만들 필요는 없다. 정적 비교 그림이 충분하면 그것을 쓴다. 시각적 요소는 항상 ‘이것으로 무엇을 더 쉽게 이해하는가’를 설명할 수 있어야 한다. 수식·코드·이름을 해설 없이 노드 안에 밀어 넣지 않는다. 범례·대체 설명·모바일 대안을 제공한다.

## 6. 디자인 프로토타입과 본 웹

### 세 안의 차이

- **A · 긴 글 중심 교재:** 넉넉한 본문 폭과 단원 내 목차, 본문 옆 짧은 보충 해설, 흐름 중간의 큰 비교 도해. 장시간 읽기와 개념의 연결에 초점을 둔다.
- **B · 설명과 예제의 병렬 화면:** 본문 옆에 예제/그래프를 유지하며 현재 설명과 대응 부분을 강조한다. 모바일에서는 설명→해당 예제로 자연스럽게 이어진다. 상시 분할로 본문 폭이 지나치게 좁아지지 않아야 한다.
- **C · 문제에서 완성 예제로 발전하는 화면:** 실제 문제→데이터→표현→비교→확인의 흐름을 제공하되 한 단계마다 설명을 충분히 읽을 수 있게 한다. 클릭해야만 본문을 볼 수 있는 슬라이드형 페이지로 축약하지 않는다.

같은 U04 수업 본문과 그림을 세 안에 넣어 내용 차이가 디자인 선호를 왜곡하지 않게 한다. 각 안에 U05 또는 U13의 긴 설명 일부도 넣어 비교 그림 하나에만 최적화되지 않았는지 확인한다. 실제 제목·코드·표·출처·긴 문장을 사용하며 placeholder와 장식용 대시보드 수치로 채우지 않는다.

데스크톱과 모바일에서 스크린샷을 확인하고, 읽기 폭·행간·한글 줄바꿈·코드 가로 넘침·표·색 대비·접기·목차·키보드 조작을 검토한다. 디자인 설명보다 실제 화면을 우선 제시한다. 사용자의 선택/수정 의견을 받은 뒤 전체 웹으로 확장한다. 답변 대기 중 교재 작업을 계속하며 무응답을 승인으로 간주하지 않는다.

### 웹 정보 구조

첫 화면은 공부를 시작하거나 이어갈 수 있게 한다. 전체 개념 지도를 거대한 장식 그래프로 만들지 않는다. 기본 경로·기초 복습/진단·추가 KG/자동화/RAG 경로를 찾을 수 있게 한다.

읽기 화면은 단원 맥락, 현재 수업의 질문, 본문, 코드/도해/표, 설명 연습, 출처, 다음 수업을 연결한다. 용어를 클릭하면 간단한 정의와 본 설명 위치를 찾을 수 있다. 전문 용어 팝업으로 본문 설명의 누락을 가리지 않는다.

검색·책갈피·메모·이어 읽기는 학습을 돕는 기능이다. 새 단원 ID 때문에 기존 localStorage 데이터를 지우거나 이전 완료 기록을 새 단원 완료로 자동 오인하지 않는다. 마이그레이션과 내보내기를 제공한다.

## 7. 스킬과 에이전트 활용

### 스킬 선택

| 도구/스킬 | 사용할 일 | 적용 경계 |
|---|---|---|
| frontend-design | 실제 읽기 화면 3안과 선택된 디자인 | 미학 지침이 본문을 짧게 만들거나 핵심 설명을 숨기게 해서는 안 됨 |
| webapp-testing | Playwright 기능·회귀·스크린샷 확인 | 테스트 통과를 교육 품질 통과로 보고하지 않음 |
| diagram-design | 필요한 개별 도해의 레이아웃 검토 | 매번 대규모 스타일 절차를 도입하지 않으며 적용 전 SKILL.md 요구 확인 |
| visual-explainer | 작은 비교·흐름 설명이 적합한 경우에만 | 전체 교재를 figure-first 요약 페이지로 바꾸는 기본 틀로 사용하지 않음 |
| skill-creator | 실제 제작 후 반복 검토 절차를 재사용할 가치가 생기면 | 현재는 프로젝트 문서로 충분함. 스킬 제작이 교재 제작보다 앞서지 않음 |
| skill-installer | 정말 부족한 능력을 발견했을 때만 | 이미 조사한 목록에 교재의 깊이를 대신 해결하는 스킬은 확인되지 않았음. 설치 자체를 성과로 삼지 않음 |
| Sites | 기존 비공개 사이트 업데이트 시 | 배포 때 해당 SKILL.md를 읽고 같은 Site ID·공개 범위 유지 |

스킬 파일 위치는 현재 호스트 catalog에서 확인한다. 전역 스킬은 삭제하지 않는다. 기존 스타일 지침이 학습 목적과 충돌하면 해당 작업에 적용하지 않고 이유를 기록한다. 새 플러그인·유료 도구는 현재 작업의 필수 전제가 아니다.

기술만으로 집필 문제를 해결할 수 없다. worked example 뒤 일부 도움을 줄인 문제, 설명과 도해의 대응, 구체 사례→추상 개념→다른 사례, 회상·자기 설명을 사용한다. 이 교육 방법의 참고는 [IES practice guide](https://ies.ed.gov/ncee/wwc/PracticeGuide/1), [CMU learning principles](https://www.cmu.edu/teaching/principles/index.html)이다. 이들 근거가 우리 교재의 실제 효과를 검증한 것은 아니다.

### 제한된 에이전트 분담

사용자는 GPT-6.2.sol high로 진행할 예정이다. 주 모델은 사용자가 선택하며 파일에서 바꾸지 않는다. 도구가 지원하면 보조 에이전트도 `model: gpt-6.2-sol`, `reasoning_effort: high`, `fork_turns: none`으로 요청한다. 같은 모델에서 역할·입력·판정 기준을 명확히 분리한다. 도구가 지원하지 않으면 주 작성자가 순차 검토한다.

동시 작업은 최대 가용 슬롯 이내에서, 보통 주 작성자 + 필요한 검토자 1~2명으로 제한한다. 각 에이전트에게 현재 수업, 관련 blueprint 절, 근거, 정확한 산출물 경로만 전달한다. 전 대화·전 교재를 무조건 복제하지 않는다. 같은 파일을 동시에 수정하지 않는다.

**기술 검토자 작업문**

> 대상: {수업 파일}, 기준: {BLUEPRINT 해당 절}, 예제: {fixture}, 출처: {ledger 항목}. 핵심 사실·표준 지위·제품/일반 모델 혼동·예제 결과·빠진 가정을 확인하라. 수정할 본문을 직접 덮어쓰지 말고 {reviews/ID-technical.md}에 위치, 문제, 근거 URL/절, 수정 방향, 차단 여부를 남겨라. 출처를 실제 확인하지 못한 주장은 pending으로 적어라. 문장이 매끄럽다는 이유로 통과시키지 마라.

**설명 검토자 작업문**

> 대상: {수업 파일}, 학습자: 프로그래밍 숙련, 해당 개념 입문, 선행 단원 {목록}. 본문에 제공되지 않은 지식을 추정하지 말라. 첫 등장 용어/기호, 단계 생략, 예제 해석, 목적과 원리 연결, 가까운 개념 비교를 점검하라. 독자가 해야 할 설명 과제 {목록}의 답이 본문 어디에서 제공되는지 표시하라. 못 찾으면 {reviews/ID-learning.md}에 구체적인 공백과 필요한 설명을 적어라. 실제 사람의 이해를 측정했다고 표현하지 마라.

**시각·웹 검토자 작업문**

> 대상: {로컬 URL/프로토타입}, 학습 질문: {질문}. 실제 화면을 데스크톱/모바일에서 확인하라. 도해와 본문·예제의 대응, 읽기 폭, 숨겨진 핵심 설명, 범례, 조작의 의미, 키보드·overflow·장시간 읽기 문제를 {reviews/ID-visual.md}에 스크린샷과 위치로 남겨라. 취향만으로 전체 재설계하지 말라. 기능 검사와 학습상 문제를 구분하라.

조사 에이전트가 필요하면 한 주제의 자료/절·판본·주장 근거만 맡긴다. 근거 수집 결과를 주 작성자가 읽고 통합한다. 에이전트가 쓴 교재를 검토 없이 merge하지 않는다. 사소한 문단마다 새 에이전트를 만들지 않고, 공통 피드백이 나오면 집필 규칙을 한 번 수정해 다음 묶음에 적용한다.

## 8. 완료 판단표

| 단계 | 통과에 필요한 증거 | 통과가 아닌 것 |
|---|---|---|
| 연구 | 핵심 주장별 실제 근거 절·버전·확인일 | 링크 목록, abstract만 읽기 |
| 본문 | BLUEPRINT의 필수 내용을 실제 설명, 예제·해설·전이 과제 | 용어 등장, 일정 글자 수 |
| 기술 | 중요한 오류 수정, 실행/예상/모의 구분, 버전·조건 정합 | 문법 검사만 통과 |
| 설명 | 용어·기호 공백 해소, 과제 답의 근거 위치, 개념에 맞는 전개 | ‘친절해 보인다’는 총평 |
| 도해 | 코드/데이터와 일치, 학습 목적·범례·대체 설명 | 장식적인 노드 수·애니메이션 |
| 웹 | 원문 핵심 내용·예제·출처 보존, 실제 화면·기능 검토 | 모든 파일이 build에 포함됨 |
| 통합 | 단원 간 중복/모순/누락 해결, 사례 데이터 일치, 요청 범위 추적 | 단원 개수 충족 |
| 배포 | 기존 비공개 범위 확인, 실제 페이지 확인, 원격 commit 확인 | 로컬 빌드 성공 |

차단 기준은 사실 오류, 미해설 핵심 기호, 설명 과제 답의 부재, 핵심 본문 누락, 비교 조건 왜곡, 핵심 UI 읽기/조작 실패다. 취향 차이와 선택 심화는 개선 목록으로 구분한다. 불필요한 반복 검토로 완료를 지연하지 않는다.

## 9. 상태 기록·컴팩션·커밋

`STATE.json`은 다음 실행이 먼저 읽는 작은 상태 파일이다. current_batch, active_unit, next_actions, open_decisions, unit별 status/artifacts/review_evidence/blockers를 유지한다. 자세한 조사·검토 내용은 별도 파일로 두고 상태 파일에 경로만 연결한다.

수업 작업을 마칠 때 `rebuild/WORKLOG.md`에 바뀐 파일, 실제 검증, 남은 문제, 다음 한두 작업을 기록한다. 테스트 수가 아니라 무엇을 확인했는지 쓴다. compaction 전에 아직 쓰지 않은 판단과 임시 실행 결과를 저장한다. 다음 실행은 상태와 현재 파일을 대조하고 이어간다.

commit 전 `git diff --check`, 변경 범위 확인, 해당 묶음에 필요한 검증을 한다. 내용 검토가 끝난 자연스러운 단위로 commit/push한다. 웹 중첩 저장소는 TECHNICAL_HANDOFF의 절차를 따른다. 사용자 변경을 되돌리지 않고 토큰·비밀정보·임시 배포 자격증명을 commit하지 않는다.

계획 범위 변경은 `rebuild/DECISIONS.md`에 이유·영향·대체 위치를 짧게 기록한다. 파일 이름·숫자만 바뀌어도 필요한 manifest·링크·상태를 함께 갱신한다. 모든 단원에 ready 근거가 있고, 웹 대응·디자인 선택·배포가 끝나야 전체 완료다.
