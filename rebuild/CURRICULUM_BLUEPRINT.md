# 새 교재의 범위와 단원별 집필 명세

버전 2.0 · 2026-11-18. 실행 진입점은 [START_HERE](START_HERE.md), 제작·검수 방법은 [EXECUTION_PROTOCOL](EXECUTION_PROTOCOL.md)이다. 이 문서는 최종 교재가 아니라, 다음 작성자가 내용과 깊이를 임의로 줄이지 않도록 하는 제작 계약이다. 조사 결과 더 좋은 설명 순서는 변경할 수 있지만, 요구 내용을 빼려면 이유와 대체 위치를 기록한다.

## 1. ‘안다’의 기준

독자가 어떤 용어를 보았다는 것으로 끝내지 않는다. 각 핵심 개념을 배운 뒤 다음 행동이 가능해야 한다.

1. 자기 말로 뜻을 설명하고, 해결하려는 문제와 등장 배경을 연결한다. 역사적 연도·기원을 억지로 붙이지 않는다.
2. 구성 요소가 어떻게 작동하는지 예제의 입력→중간 상태→출력으로 따라간다.
3. 코드·표·그림의 주요 기호와 요소가 무엇을 뜻하는지 설명한다.
4. 가장 가까운 다른 개념과 공통점·차이를 구분한다.
5. 새로운 사례에 적용하거나, 쓰지 않는 편이 나은 조건을 설명한다.
6. 실패·한계의 이유를 설명하고, 더 깊은 원문을 읽을 때 무엇을 찾을지 안다.

이 여섯 가지를 매 절의 동일한 소제목으로 복제하지 않는다. 설명 구성은 개념에 맞춰 선택한다. 문법은 줄별 해설, 알고리즘은 중간 결과, 모델링은 대안 비교, 운영은 사건·변경의 시간 흐름이 효과적이다.

### 깊이를 만드는 구체적인 방식

- 정의 뒤에 정의를 더 붙이는 것은 심화가 아니다. RDF에서는 집합 의미와 사건 식별이 질의 결과를 어떻게 바꾸는지, ontology에서는 모델링 선택과 공리가 어떤 추론을 만드는지 보여준다.
- Auto ontology에서는 도구 목록을 늘리는 대신 후보 생성·정렬·검토·모델 변경의 산출물을 실제로 보여준다. RAG에서는 추상적인 상자 네 개를 넘어, 어떤 근거가 생성기에 전달되거나 사라지는지 보여준다.
- ‘주의한다’, ‘구분한다’, ‘고려해야 한다’만 적힌 문장을 발견하면 **무엇을, 왜, 어떻게, 예를 들면**이 앞뒤에 설명돼 있는지 확인한다.
- 정의→작은 완성 예제→조건 변경/반례→도메인 전이의 흐름을 활용하되, 모든 단원을 동일한 이야기로 끼워 맞추지 않는다.
- 외부 링크를 열어야 핵심 예제의 기호·전제가 이해되는 부분은 집필 누락이다. 선행 단원의 정확한 위치로 이동해 복습할 수는 있지만, 현재 절에 필요한 전제는 짧게 다시 연결한다.
- 학습 문제에는 해설·판단 근거·흔한 오답의 이유가 있다. ‘생각해 보자’만 남기지 않는다.

### 분량과 구성

기존 M/C/D 본문 약 111,077자, C 개념 교재 약 51,001자에서 새 본편과 논문 해설 합계 **약 30만~45만 자**를 예상한다. 아래 단원별 초안 예산의 합은 30.6만~43만 자다. UTF-8 바이트나 페이지 수가 아닌 Unicode 문자 기준 참고치다. 코드·반복 표로 분량을 부풀리지 않는다. 설명에 더 필요하면 늘린다. 적게 썼다면 충족 여부를 다시 검토하며, 분량 달성만으로 합격시키지 않는다.

각 단원은 자연스러운 학습 덩어리의 여러 Markdown 파일로 나눈다. 한 화면에 2만 자를 밀어 넣거나, 기존처럼 짧은 카드로 산산이 분리하지 않는다. 아래 ‘수업 전개’ 항목은 분량에 따라 여러 수업으로 나눌 수 있으며 고정된 수업 개수는 아니다.

## 3. 단원별 명세

### U01. 기업이 기억하고 설명하려면 무엇이 필요한가

**설명할 수 있어야 하는 것:** Enterprise Brain을 특정 DB나 챗봇과 동일시하지 않고, 기업 지식의 수집·의미·접근·활용·갱신을 묶는 관점으로 설명한다. Second Brain과 조직 시스템의 차이도 설명한다.

**수업 전개**

- ‘장비 A의 최근 정비 이후 문제가 반복됐는가?’라는 질문에 문서 검색만으로 답하기 어려운 이유를, 흩어진 문서·정형 기록·담당자 경험으로 보여준다. 도입부터 미해설 용어로 구성도를 채우지 않는다.
- Second Brain의 개인 지식 관리 맥락과 CODE 등 원저자 방법론의 의미를 설명하고, 이를 기업 공유·권한·동일성·책임·수명주기로 확대할 때 생기는 차이를 살핀다.
- Enterprise Brain이라는 표현의 일반적 비유와 개별 제품 사용례를 구분한다. 업계 전체가 합의한 단일 표준 아키텍처처럼 정의하지 않는다.
- 문서 저장소, 검색, KG, ontology, Graph DB, RAG, agent의 역할과 조합을 한 질문의 흐름에 배치한다. 구성도를 설명한 후에야 전체 지도로 제시한다.
- 문서 검색만으로 충분한 경우, 정형 조회가 나은 경우, KG가 유용한 경우를 비교한다. ‘모든 기업은 그래프가 필요하다’를 결론으로 고정하지 않는다.

**필수 산출물:** 개인 메모 사례와 기업 정비 사례 두 개, 용어 역할 지도, 과도한 통합 시스템을 만들지 않는 대안 설명. **검토 질문:** ‘Enterprise Brain=Knowledge Graph인가?’에 조건을 붙여 답할 수 있는가?

**조사:** Second Brain 원저자, 실제 Enterprise Brain 공급사 사용례, Hogan et al. KG survey. 제품 홍보를 독립 효과 근거로 사용하지 않는다. 제품 설치·agent 프레임워크 구현은 제외 가능.

### U02. 관계형 DB가 있는데 왜 그래프를 사용하는가

**수업 전개**

- 데이터 모델, 저장 엔진, 질의 언어, 색인의 층위를 구분한다. 그래프 그림과 Graph DB는 같은 말이 아니다.
- 사람·차·운행 또는 직원·팀·문서를 테이블과 그래프로 각각 표현한다. 기본키·외래키·관계 테이블이 무엇을 보존하는지 연결한다.
- 한 단계 조회, 여러 단계 경로, 집계 질문을 같은 데이터에서 따라간다. 조인 수가 많다는 사실만으로 성능 결론을 내리지 않는다.
- 그래프 순회, 시작점 선택, 선택도·차수·경로 폭발·색인의 역할을 작은 탐색 예로 보여준다. ‘관계를 따라가면 항상 O(1)’ 같은 설명을 배제한다.
- 논리 모델의 RDF/Property Graph, 실행·저장 선택, 트랜잭션·제약·규모 고려를 나눠 설명한다. RDB로도 그래프성 데이터를 다룰 수 있고 그래프 DB도 인덱스·계획·메모리 영향을 받는다.

**필수 산출물:** 동일 데이터의 관계형/그래프 도식, 동일 질문의 결과 일치, 질문 유형별 선택표, 범위 확장 시 탐색량이 늘어나는 예. **검토:** ‘RDB는 관계를 표현 못한다’와 ‘그래프는 무조건 빠르다’를 왜 틀렸는지 설명하는가?

**조사:** Neo4j 공식 개념·실행 계획·인덱스 문서, 선택 RDB의 공식 재귀 질의 문서. 저장 엔진의 내부 페이지 구조와 대규모 성능 튜닝은 선택 심화.

### U03. 속성 그래프와 Neo4j를 구체적으로 이해하기

**수업 전개**

- 노드·관계·라벨·관계 타입·속성·식별자를 처음부터 구분한다. 사람 이름은 식별자 자체가 아니며 라벨·타입·속성이 모두 같은 분류 수단은 아니다.
- Neo4j에서 방향·관계 타입·여러 라벨·병렬 관계·속성 값이 어떻게 표현되는지 읽는다. 특정 제품 규칙을 모든 속성 그래프의 보편 규칙으로 확장하지 않는다.
- 반복 운행 3건을 관계 3개로 표현한 모델과 운행을 사건 노드로 둔 모델을 비교한다. 운행에 승인자·정비 기록·근거를 연결하면 어떤 모델이 설명하기 쉬운지 살핀다.
- 간단한 생성·조회·수정과 제약·인덱스를 보여준다. MERGE를 실세계 동일성 판정이나 아무 조건 없는 중복 방지로 설명하지 않는다.
- Neo4j의 DBMS 역할, Cypher, 드라이버, Browser 등 이용 경로, 트랜잭션, 실행 계획의 의미를 필요한 수준에서 연결한다. 사용 중인 버전·에디션 조건을 확인한다.

**필수 산출물:** 작은 완성 그래프, 속성/노드 선택의 두 대안, 조회 전후 결과, Neo4j와 일반 모델의 경계 표시. **검토:** ‘속성 그래프에는 ontology가 없다’가 왜 과도한 주장인지 설명하는가?

**조사:** Neo4j Getting Started·Cypher·constraints/indexes 공식 문서, GraphFrames 공식 property graph 문서는 제품 차이를 비교하는 보조 근거. 클러스터 운영·플러그인 전체 학습은 제외 가능.

### U04. Semantic Web에서 RDF가 맡는 일과 실제 표현

**수업 전개**

- 웹 문서를 사람이 읽는 것과 데이터를 시스템 간에 식별·연결하는 문제의 차이에서 Semantic Web을 소개한다. Semantic HTML·SEO와 혼동하지 않는다. W3C의 역할과 Recommendation/Note/초안의 차이를 설명한다.
- 주어·술어·목적어를 문장과 연결한 후 IRI·literal·blank node를 설명한다. IRI가 식별한다는 것과 해당 URL이 문서를 반환한다는 것을 분리한다.
- `@prefix`, `ex:`, `rdf:`, `rdfs:`, `xsd:`, `a`, `rdf:type`, `;`, `,`, `.`, `^^`, `@ko`를 **실제 등장하기 전에** 또는 같은 자리에서 풀어준다. prefix는 줄임표이고 이름의 공간을 지정한다는 점을 구체적인 확장 결과로 보여준다.
- 같은 그래프의 Turtle·RDF/XML·JSON-LD 최소 예를 비교한다. 먼저 추상 그래프를 이해시킨 뒤 구문을 바꾼다. 각각의 주요 구문 역할을 읽을 만큼 설명하고 파서로 같은 그래프인지 확인한다.
- RDF 그래프의 집합 성질과 같은 트리플의 반복, 관계 발생의 식별, 사건 노드 모델링을 다룬다. 사용자 운행 예에서 3사건×6트리플=18은 **선택한 필드·모델에 따른 값**이며 모든 RDF 표현의 절대 비용이 아니다.
- RDF의 술어 IRI에 설명을 붙이는 것과 특정 사건/주장에 속성을 붙이는 것은 다르다. ‘RDF 술어에는 아무 속성도 못 붙인다’로 단순화하지 않는다. n-ary relation, reification, named graph의 목적·차이를 작은 예로 분리한다.
- RDF dataset, default/named graph, 문맥·출처 연결의 가능성과 한계를 설명한다. named graph 자체가 출처의 의미·진실성을 자동 부여하지 않는다.
- RDF 1.1을 기초 기준으로 삼되 RDF 1.2와 triple term 관련 최신 지위를 다시 확인한다. 버전별 표현을 섞지 않고 심화에서 연결한다.

**필수 산출물:** 줄별 해설된 1트리플→복수 트리플→사건 그래프, 같은 세 사건의 RDF/속성 그래프 나란한 그림, 선택 강조 시 대응 코드·필드 표시, 세 직렬화의 동등성 확인, 식별자/표기/데이터 모델 차이 문제.

**검토:** `rdf:type`을 모르던 독자가 예제를 읽고 직접 문장으로 바꿀 수 있는가? 사건·주장·술어를 혼동하지 않는가? RDF가 시간·출처를 표현할 수 없다는 잘못된 결론을 남기지 않는가?

**조사:** W3C RDF Concepts, RDF Primer, Turtle, RDF/XML, JSON-LD, n-ary relations Note, dataset 관련 정의. 본문을 규격 전체 문법 목록으로 채우지 않는다.

### U05. Ontology는 어떤 도메인 이해를 합의하는가

**수업 전개**

- 같은 ‘장비’, ‘고장’, ‘정비’를 부서마다 다르게 사용하는 상황에서 시작한다. 도메인의 개념·관계·가정·공유된 의미를 명시하는 일이 데이터 컬럼 이름을 정하는 일과 어떻게 연결되고 달라지는지 설명한다.
- taxonomy·통제 어휘·SKOS·개념 모델·ontology·DB schema를 목적과 표현력 기준으로 비교한다. schema도 의미를 담을 수 있으므로 ‘schema=형식만, ontology=의미만’으로 이분화하지 않는다.
- 범위·이용자·역량 질문을 정하고, 기존 모델 재사용 여부, 용어 수집, 클래스/인스턴스·속성·관계·제약/공리 선택으로 발전시킨다. 모델링 절차가 항상 직선형인 것처럼 쓰지 않는다.
- 장비 모델과 실제 장비, 부품 종류와 특정 부품, 정비 작업 유형과 실제 수행 사건을 구분한다. is-a와 part-of를 혼동했을 때 질문 답변이 어떻게 잘못되는지 보여준다.
- 사건·역할·시간·단위·상태를 어디에 둘지 대안을 비교한다. ‘온톨로지가 이미 정해졌으니 모든 데이터는 그대로 맞추면 된다’가 아닌 변경·합의 과정을 보여준다.
- 개념적 설계와 OWL 표현, 속성 그래프 스키마/애플리케이션 구현의 관계를 설명한다. OWL을 사용하지 않아도 의미 합의가 필요하지만 동일한 추론 기능이 자동 생기지는 않는다.
- 실제 소규모 도메인 모델을 초안→문제 발견→개정으로 발전시킨다. 어떤 역량 질문이 가능해졌고 어떤 것은 여전히 답할 수 없는지 확인한다.

**필수 산출물:** 역량 질문 6~10개, 용어의 모호성 사례, 클래스/관계 정의 표와 긍정·부정 예, 버전 1/2 비교, 모델→표/그래프 매핑. **검토:** ‘도메인의 규약’이라는 표현을 암기하는 것을 넘어 어떤 합의를 문서화하는지 예로 설명하는가?

**조사:** Stanford Ontology Development 101, W3C SKOS·OWL Primer, KG survey. 전문 철학사·전체 기술 논리 증명은 선택 심화.

### U06. RDFS·OWL의 추론과 SHACL의 검증

**수업 전개**

- class·instance·property를 앞 단원 예로 되짚고 RDFS의 subclass/subproperty/domain/range를 한 규칙씩 추가한다. 입력 트리플과 따라 나오는 트리플을 구분한다.
- domain/range를 입력 양식의 허용 목록처럼 사용하면 생기는 오해를 반례로 해소한다. OWL의 동치·서로소·역관계·일부/전부·cardinality 제한을 필요한 예와 함께 설명한다.
- 열린 세계 가정, 이름이 다르다고 별개로 자동 간주하지 않는 점, ‘없음’과 ‘모름’을 실제 질의·추론 사례로 풀어준다. existential 제한이 반드시 명명된 새 개체를 DB에 삽입한다는 뜻이 아님을 설명한다.
- entailment·일관성·물질화/질의 시 추론을 구분한다. OWL 프로파일은 표현력·계산 특성의 목적을 이해할 수준에서 다루고 공리 전체 문법을 암기시키지 않는다.
- SHACL의 target·shape·property path·datatype·min/maxCount 등을 하나의 데이터 오류에서 전개한다. 검사 보고서를 읽고, 통과가 사실성 보장이 아닌 이유를 같은 예로 보여준다.
- ‘추론 결과와 검증 결과가 다르다’를 넘어서 어느 데이터와 어떤 entailment 설정에서 실행했는지 표시한다. 두 도구가 서로를 대체하지 않는 이유를 설명한다.

**필수 산출물:** 데이터/공리/추론/검사보고서 네 층, 누락·충돌·동일성 반례, 실제 실행 가능한 작은 fixture. **검토:** 자료를 찾지 않고 domain과 minCount의 역할 차이를 예로 설명하는가?

**조사:** W3C RDFS·OWL2 Primer/semantics/profiles·SHACL, 사용하는 reasoner/validator 공식 문서. 실행 엔진이 지원하지 않는 OWL 전체 의미를 테스트했다고 주장하지 않는다.

### U07. Cypher와 SPARQL을 읽고 결과를 예상하기

**수업 전개:** 같은 질문과 동등한 사건 데이터로 MATCH/WHERE/RETURN, RDF triple pattern/SELECT/WHERE, 변수와 조건, OPTIONAL, 집계·정렬·LIMIT를 해석한다. 그래프 패턴이 매칭되어 결과 행이 생기는 과정을 보여준다. 경로·DISTINCT·누락값이 결과를 바꾸는 작은 예를 추가한다. SPARQL의 해법 매핑과 중복 결과, Cypher의 관계 패턴을 섣불리 일대일 치환하지 않는다.

**필수 산출물:** 질문→패턴 표시→코드→중간 매칭→최종 행을 가진 짝 예제 3~4개. **검토:** 3회 운행의 횟수/거리 질의를 설명하고 중복 집계 원인을 찾는가?

**조사:** SPARQL1.1 Query, Neo4j Cypher 공식 문서. 실행 결과와 손으로 도출한 예상 결과를 명시한다. 모든 쿼리 문법·관리 명령·고급 튜닝은 생략 가능하지만 예제 안의 문법은 빠짐없이 설명한다.

### U08. Knowledge Graph는 무엇을 지식으로 연결하는가

**수업 전개**

- KG의 다양한 정의를 소개하되 공통 축인 개체·관계·의미·맥락을 실제 예로 설명한다. Graph DB·ontology·단순 링크망과 역할을 구분한다.
- schema/TBox와 instance/ABox의 쓰임을 소개하고, 모든 KG가 같은 형식의 ontology를 강제하는 것은 아님을 설명한다. 논리 용어는 쓰는 만큼 풀어준다.
- 사람·장비·문서·사건·주장·관측·권고를 구분한다. ‘문서가 그렇게 말한다’와 ‘검증된 실제 사실이다’를 어떻게 분리할지 비교한다.
- 식별자, 동의어, 타입, 관계 정의, 시간, 출처, 단위가 빠지면 생기는 오류를 그래프의 성장 과정에서 보여준다. 그래프가 연결돼 있다는 사실만으로 신뢰·추론·인과가 생기지 않는다.
- top-down/bottom-up/hybrid 구축, materialized graph와 가상/연합 접근, 목적에 맞춘 최소 모델을 비교한다. link prediction·추론·정보 추출은 서로 다른 생성 근거를 가진다.

**필수 산출물:** 작은 연결망→사용 가능한 KG로 발전하는 3단계, 사실/관측/가설 구분 사례, 고객지원·반도체 두 적용, 역량 질문으로 확인한 가능/불가 답변.

**조사:** Hogan et al. Knowledge Graphs와 자동 구축 survey. ‘KG란 RDF만’ 또는 ‘어떤 그래프든 KG’라는 극단을 피한다. 대규모 graph ML 알고리즘 구현은 제외 가능.

### U09. 정형·비정형 원천에서 지식 후보가 만들어지는 과정

**수업 전개**

- 수집 대상·권한·문서 버전·원문 위치·파싱 결과를 왜 먼저 확보하는지 보여준다. 표·PDF·본문·OCR 등에서 손실되는 문맥이 추출에 미치는 영향을 설명한다.
- 정형 데이터는 키·코드·단위·시간·업무 의미를 매핑한다. R2RML의 역할과 직접 ETL/가상 접근 대안을 설명한다. 컬럼명만 보고 의미가 완성된 것으로 간주하지 않는다.
- 비정형 데이터의 NER, entity typing, entity linking, coreference, relation/event extraction을 같은 문단에서 각각 다른 산출물로 보여준다. 문장 내/문서 간 관계, 조건·부정·추측·시점 처리를 포함한다.
- 규칙·전통 모델·LLM·결합 접근이 어떤 반복 작업을 맡는지, 구조화 출력과 프롬프트가 보장하는 범위를 설명한다. JSON 형식 준수는 내용 정확도와 다르다.
- 원문→span→후보 entity/relation/event→타입 매핑→근거 연결→후속 검토까지 하나의 기록을 끝까지 따라간다. 오류가 어느 단계에서 들어왔는지 역추적한다.

**필수 산출물:** 정형 표·정비 기록·매뉴얼/표 혼합 문서의 3경로, 부정/가설을 포함한 추출 예, 원문 위치가 있는 후보 주장, precision/recall의 의미 연결. **검토:** entity linking과 coreference, extraction과 검증의 차이를 예로 설명하는가?

**조사:** 자동 KG 구축 survey의 acquisition, R2RML, 실제 선택한 parser/추출 도구 공식 문서, 기법이 필요한 경우 해당 원논문. 유료 LLM 대량 호출·모든 모델 벤치마크는 요구하지 않는다.

### U10. 같은 대상을 찾고 충돌하는 기록을 통합하기

**수업 전개:** 이름 정규화와 실세계 동일성의 차이→후보 생성/blocking→특징과 증거→매칭 판단→클러스터/통합→충돌 보존·수정으로 진행한다. 장비 별칭·시리얼·부서 코드·부품 교체 전후를 사용한다. pairwise match의 전이로 생기는 과도한 병합, false merge/false split의 영향, 단위·시간·출처에 따른 값 충돌을 설명한다. ontology/schema alignment와 entity resolution을 구분한다. `owl:sameAs` 같은 강한 동일성 선언은 별칭 관계와 다르다.

**필수 산출물:** 입력 레코드 8~12개의 후보/탈락/보류/통합 결과, 잘못 합친 사례와 되돌림, canonical record와 원천 주장 보존의 대안. **검토:** 유사도 점수를 사실 확률처럼 해석하지 않고 검토 조건을 설명하는가?

**조사:** Entity Resolution survey·자동 KG 구축 survey의 fusion, OWL 동일성 의미. 알고리즘 수식의 전면 유도보다 후보 폭 축소와 오판 파급을 깊게 다룬다.

### U11. 검증·사람 검토·암묵지의 실질적인 설계

**수업 전개**

- 형식/구조, 의미 일관성, 원문 충실성, 실제 사실, 업무 적합성, 최신성의 검사를 구분하고 각각 통과해도 남는 오류를 보여준다.
- 모든 건 사람 검토, 규칙 우선, 위험별 분기, 표본 감사, active learning 등 대안을 비교한다. 근거 없는 ‘LLM confidence 0.9 이상 자동 승인’을 쓰지 않는다. 위험·손실·검토 용량·측정 데이터가 필요하다.
- 검토 큐의 도착량·처리량·표본 추출을 작은 수치 예로 설명한다. 제안 정책의 임계값과 효과는 합성 설계 예이며 실증값이 아니다. 평균 처리량만으로 불확실한 대기시간을 단정하지 않는다.
- 검토자가 볼 원문 span·변경 전후·판단 이유·불일치·재검토를 구성한다. 사람도 일관된 정답을 항상 제공하지 못하므로 기준과 이견 처리 과정이 필요하다.
- 암묵지의 성격을 설명하고 인터뷰·critical incident·작업 관찰·회고·사례 검토를 비교한다. 조건·판단 근거·예외·불확실성을 기록하며 모든 숙련을 문서로 완전히 바꿀 수 있다고 하지 않는다.

**필수 산출물:** 오류 5종의 검증 결과, 검토 화면의 정보 명세, 두 검토 정책의 용량/위험 비교, 인터뷰→검토된 조건부 지식 예. **검토:** 검증 통과와 진실을 구분하면서도 실제 운영 결정을 내릴 수 있는가?

**조사:** SHACL·DQV·관련 품질 연구, NASA knowledge capture/lessons learned, 사용하는 human review 기법의 원자료. 반도체 작업 안전 절차를 임의로 규정하지 않는다.

### U12. Auto ontology와 자동 지식 구축이 실제로 자동화하는 것

**수업 전개**

- ontology learning, ontology population, KG construction, schema induction, mapping/alignment를 구분한다. 새 개념을 만드는 일과 기존 개념의 인스턴스를 넣는 일을 혼동하지 않는다.
- 문서 용어 수집→개념 후보→동의어/유형→분류 체계→비계층 관계→제약/공리 후보→평가·전문가 수정의 산출물을 한 묶음 문서에서 보여준다.
- bottom-up·top-down·반복적 결합의 장단점과 실패 사례를 다룬다. 도메인 범위·역량 질문·재사용 모델·근거·버전을 어떻게 제공하는지 설명한다.
- LLM 기반 방식은 prompt/출력 예와 오류를 보여주고, taxonomy cycle·클래스/인스턴스 혼동·의미 중복·과도한 일반화·근거 없는 관계를 검토한다. 자동 평가와 전문가 판단의 역할을 나눈다.
- 특정 `NVIDIA/auto-ontology` 프로젝트는 당시 공식 README·코드·출력·커밋을 확인해 별도 사례로 설명한다. 제품의 ontology라는 이름을 OWL ontology와 자동 동일시하지 않는다. 현재 접근 가능성과 실제 기능을 재확인한다.
- 모델 변경 제안→diff→역량 질문 회귀 확인→승인/기각→버전 적용으로 연결한다. ‘사람이 마지막에 확인’ 한 줄로 책임 구조를 대신하지 않는다.

**필수 산출물:** 후보 개념 목록과 정제 후 모델, 기각된 후보의 이유, 기존 인스턴스에 대한 영향, 자동화 수준별 책임표. **검토:** 자동으로 ‘그래프를 만들었다’는 결과에서 무엇이 아직 검증되지 않았는지 설명하는가?

**조사:** LLMs4OL·ontology learning 관련 원논문, 자동 KG 구축 survey, 공식 auto-ontology 코드. 실측하지 않은 품질·시간 절감은 주장하지 않는다. 새로운 제품 조사가 필요하면 ledger에 추가한다.

### U13. Vector RAG의 내부에서 무엇이 일어나는가

**수업 전개**

- 원래 RAG 논문과 현재 일반적인 검색 후 프롬프트 구성 파이프라인을 구분한다. 파라미터 지식과 외부 근거, 인덱싱과 질의 시점의 역할을 설명한다.
- parsing/chunking/metadata→embedding→index→query→retrieval→filter/hybrid→rerank→context assembly→generation/citation을 실제 입력·출력으로 전개한다.
- embedding의 의미와 유사도, 정규화, cosine/dot product를 작은 수치 예로 읽는다. 2차원 교육용 벡터가 실제 임베딩 결과가 아님을 표시한다. ANN/HNSW 그래프는 업무 의미 관계 KG와 다르다.
- chunk 경계·overlap·표/제목·질문 재작성·lexical 검색·hybrid·reranking이 어떤 문제를 해결하고 어떤 오류를 남기는지 문서 6~10개에서 비교한다. 조정 항목을 나열만 하지 않는다.
- top-k가 정답/근거 수와 같지 않은 이유, context budget과 중복, citation의 원문 정합, 답변 거부·불충분 근거의 처리를 설명한다.
- 단일 사실·다중 근거·최신 버전·전체 경향 질문에서 다른 실패를 보여준다. retrieval 실패와 generation 실패를 분리한다.

**필수 산출물:** 같은 질문의 chunk/후보순위/rerank/context/답변 전체 추적, 유사도 손계산, 경계 변경 전후, 근거 누락의 결과. **검토:** ‘벡터가 비슷하면 맞는 답’이 아닌 이유를 단계별로 설명하는가?

**조사:** Lewis et al., IR 교과서, HNSW 원논문, 선택 임베딩·검색기 공식 문서. 모델 학습 손실 전체 유도·상용 서비스별 구축법은 제외 가능.

### U14. Graph RAG는 어떤 그래프를 어떻게 검색하는가

**수업 전개**

- 일반적인 그래프 활용 RAG, graph traversal/text-to-Cypher/SPARQL·vector+graph 혼합, Microsoft GraphRAG를 구분한다. 하나의 고정 알고리즘 이름처럼 취급하지 않는다.
- 질문의 entity linking→시작점→관계/경로 확장→필터/순위→원문 근거 회수→컨텍스트를 작은 KG에서 따라간다. 잘못 연결한 entity와 과도한 이웃 확장이 결과에 미치는 영향을 보여준다.
- Microsoft 방식의 entity/relation 추출·community·report 생성과 local/global 검색을 각 중간 산출물로 설명한다. 왜 community report가 전역 질문에 쓰이는지, 요약에서 손실·오류가 어떻게 전파되는지 연결한다.
- 같은 질문을 vector·graph 경로에서 비교하되, 문서 내용·모델·예산이 다른 데서 생긴 차이를 구조의 우월성으로 단정하지 않는다. 구조화가 도움이 안 되는 질문과 원문이 여전히 필요한 이유를 포함한다.
- 구축 비용, 증분 갱신, 출처 추적, 권한, 추출 품질, text-to-query의 실행 안전·스키마 제약을 설명한다. 구현별 DRIFT/basic 등은 기본 원리 후 선택 심화로 둔다.

**필수 산출물:** 관계 경로와 선택된 근거를 함께 보는 예, Microsoft local/global 입력 비교, 잘못된 관계 한 개의 파급, 그래프 없어도 충분한 반례. **검토:** GraphRAG·KG·Graph DB가 각각 맡는 역할과 조합을 설명하는가?

**조사:** Edge et al. 논문 본문, Microsoft GraphRAG 공식 docs/현재 구현, Neo4j GraphRAG retriever 공식 문서. 버전마다 달라지는 기본값을 고정 사실로 쓰지 않는다.

### U15. Tree RAG와 RAPTOR의 계층적 검색

**수업 전개:** 문서 목차 트리·parent-child retrieval·재귀 요약 트리가 어떻게 다른지 먼저 구분한다. RAPTOR의 chunk→embedding→clustering→summary→재귀 계층을 실제 작은 문서 묶음으로 전개한다. 논문이 사용하는 군집/차원 축소/soft membership의 역할을 설명하되 세부 수식 전체 증명은 생략한다. tree traversal과 collapsed-tree retrieval을 동일 질문에서 비교한다. 요약이 추상화 수준을 바꾸는 이점과 세부 수치·조건·출처 손실을 보여준다. tree도 graph의 한 구조라는 수학적 관계와 여기서의 검색 설계 차이를 구분한다.

**필수 산출물:** 원문 조각과 각 수준 요약을 모두 읽을 수 있는 계층, 두 탐색 전략의 선택 노드·context, 하위 근거로 내려가야 하는 질문. **검토:** ‘Tree RAG=RAPTOR’ 또는 ‘요약을 단계적으로 만들면 항상 향상’으로 설명하지 않는가?

**조사:** RAPTOR ICLR 출판본 방법·실험·ablation·저자 구현, parent-child 검색을 다룬 공식 구현 자료. 임의 toy tree를 논문 알고리즘 실행 결과라고 부르지 않는다.

### U16. 어떤 RAG가 좋은지 판단할 수 있는가

**수업 전개:** 질문 유형·gold evidence·답변 가능 여부→고정 조건/변인→retrieval 평가→generation 평가→비용·지연·갱신·사람 판단으로 진행한다. precision/recall/ranking 지표와 answer correctness/faithfulness/citation을 구분하고 작은 표를 손으로 계산한다. 누수·비교 예산·LLM judge의 한계·ablation·반복 실험의 의미를 설명한다. end-to-end 성능 차이를 단계별 오류로 분해한다.

**필수 산출물:** 세 방법의 장단점이 드러나는 질문 세트와 근거, 동일 조건 비교 설계, 합성 수치와 실측을 구분한 계산 예. **검토:** ‘GraphRAG가 n% 좋다’는 주장에 필요한 조건을 질문할 수 있는가?

**조사:** IR 평가 교과서·RAG/GraphRAG/RAPTOR 원논문의 평가 절, 추가 지표는 원논문 확인. 실제 팀 발표자의 전면 벤치마크 실험을 대신하는 범위로 확대하지 않는다.

### U17. 지식이 바뀌거나 철회되면 무엇을 바꿔야 하는가

**수업 전개:** provenance·문서 version·발생/유효/등록 시점→정정·충돌·철회→파생 관계/요약/임베딩/캐시 영향→증분 재처리→접근 권한과 감사로 전개한다. PROV-O의 Entity/Activity/Agent를 실제 파생 관계와 연결한다. 원문 승인·후보 주장·운영 그래프의 상태 모델은 여러 대안을 비교한다. 가상 조회와 복제의 최신성/비용 차이, source ACL과 파생 데이터의 접근, 변경 이력과 rollback을 설명한다.

**필수 산출물:** 매뉴얼 개정과 정비 기록 정정 두 타임라인, 영향 노드/산출물 목록, ‘현재’와 ‘당시’ 질문의 답 차이, 권한 변경 후 확인 항목. **검토:** 원문 삭제만으로 파생 지식이 자동 철회된다고 생각하지 않는가?

**조사:** PROV-O·Data on the Web Best Practices·자동 KG 구축 survey evolution·선택 저장소 공식 버전/권한 문서. toy ACL 예를 운영 보안 구현으로 제시하지 않는다.

### U18. 반도체 사례로 연결하고 다른 사람에게 설명하기

**사례 묶음 A — 장비·정비·이상 관측:** 장비 대장, 정비 작업, 매뉴얼, 알람/검사 관측, 엔지니어 메모. 동일성·사건·관측/원인 가설·출처·시간을 다룬다.

**사례 묶음 B — 공정 문서·검사·변경 이력:** 제품/lot/wafer/공정 단계의 기본 개념을 먼저 설명하고 절차 개정·검사 항목·용어/단위 차이를 연결한다. 실제 공정 recipe나 수율 인과를 꾸며내지 않는다.

**사례 묶음 C — 부품·공급사·사내 경험:** 부품 규격, 대체품 검토, 공급사 문서, 내부 조건부 권고. 제품 모델/개별 부품, 동일성과 대체 가능성, 암묵지의 조건을 다룬다.

하나의 거대한 그래프에 모두 넣지 않는다. 여러 지식 유형과 질문이 실제로 다른 설계 선택을 요구하게 한다. 기존 합성 corpus를 검토해 재사용하되 서술·수치·식별자를 새 단원과 일치시킨다. 예상 규모는 원천 기록 25~40개, 정형 표 5~8종, 후보 주장 80~150개이며 교육 질문을 만들기 위한 설계 참고치다. 줄 수 채우기가 목적이 아니다.

**수업 전개:** 각 묶음의 업무와 용어→답해야 하는 질문→대안 모델→수집·추출·연결·검증→운영 변경→RAG 근거→설계 선택을 설명한다. 모든 기록을 본문에서 나열하지 않고 대표 기록을 깊게 해석하며 나머지는 탐색 가능한 자료로 제공한다.

**필수 산출물:** 한 지식의 원천에서 답변까지 추적, 두 대안 아키텍처의 선택 근거, 90초/3분/10분 설명 연습과 해설·점검 기준, 예상 청중 질문과 근거. 특정 대본·슬라이드 확정은 후속 요청까지 보류한다.

**조사:** ASML 등 제조 기본 교육 자료와 분야별 공식 기초 자료, 앞 단원의 검증된 원리. 모든 합성 회사·사건·정량값을 명시한다.

### S01. A Comprehensive Survey on Automatic Knowledge Graph Construction 읽기

논문을 요약 목록으로 바꾸지 않는다. 먼저 논문이 분류하는 구축 문제를 보여주고, 앞 단원의 사례를 논문 용어에 대응시킨다.

- 논문 판본·범위·출판 시점과 이후 기술 변화의 경계를 확인한다. 공개본과 ACM 출판본의 목차·내용 차이가 있으면 기록한다.
- background와 semi-structured preprocessing을 선행 개념과 연결한다.
- acquisition의 entity discovery/typing/linking, coreference, relation extraction 분류를 각각 작은 입력/출력과 연결한다. 서로 다른 supervision·문장/문서 범위가 어떤 문제를 풀려는지 설명한다.
- refinement의 completion/fusion, evolution의 조건·시간·동적 변화, storage의 역할을 U10·U17과 연결한다. completion을 사실 검증의 대체재로 설명하지 않는다.
- 연구 과제별 대표 접근의 아이디어·입력·출력·평가·실패를 선별해서 읽는다. 모든 인용 논문을 나열하거나 2023 survey가 최신 LLM 시스템까지 설명한다고 주장하지 않는다.
- ‘우리 사례의 어느 부분을 자동화하는가, 아직 누가 무엇을 판단해야 하는가’로 돌아와 읽기를 마친다.

**필수 산출물:** 실제 본문 절/그림과 교재 단원 대응표, 기법 비교 3~5개, 읽기 전/중/후 질문과 해설, 논문 주장과 교재 응용의 구분. 출처는 [공개본](https://arxiv.org/abs/2302.05019), [공개 HTML](https://arxiv.org/html/2302.05019v1), [ACM 출판본](https://doi.org/10.1145/3618295). 다음 작성자가 실제 사용할 절을 다시 읽고 근거를 남긴다.

## 5. 본문과 웹이 함께 충족할 조건

본문은 Markdown만 읽어도 핵심 내용과 예제 결과가 이해되어야 한다. 웹은 순서·레이아웃·그림·상호작용을 바꿀 수 있지만 핵심 설명을 요약 카드로 대체하지 않는다. 그래프나 검색 인터랙션을 실행하지 않아도 정적 그림·표와 해설로 동일한 학습이 가능해야 한다.

각 수업은 검색 가능한 제목, 필요한 선행 개념, 충분한 본문, 실제 예제, 가까운 출처, 다음 연결을 갖는다. 펼침 영역은 정답·부가 심화에 사용하고 핵심 해설을 숨기는 용도로 쓰지 않는다. 전체 과정의 완료 조건은 [EXECUTION_PROTOCOL](EXECUTION_PROTOCOL.md)의 교육·사실·웹 검토를 모두 적용한다.
