# 전면 개편 실행 진입점

버전: 2.0 · 2026-11-18 · 다음 실행의 요청 모델: **GPT-6.2.sol / high reasoning**

사용자는 다음 메시지에서 모델을 직접 바꾸고 **“전면 개편 진행해”**라고만 지시할 예정이다. 이 문서와 상태 파일을 읽고 실제 조사·집필·웹 제작을 시작한다. 계획을 다시 설명하거나 착수 허가를 다시 묻는 것으로 턴을 끝내지 않는다.

## 1. 지시의 우선순위와 현재 상태

최신 사용자 요구 → 프로젝트 AGENTS.md → 이 문서 → CURRICULUM_BLUEPRINT.md / EXECUTION_PROTOCOL.md → 이전 REBUILD_PLAN.md 순서로 해석한다. 시스템·개발자 지시는 항상 우선한다. 이전 계획은 실패 분석과 참고자료이며, 최신 명세와 충돌하는 ‘운전 사례 하나 승인 전 전부 보류’·분량·순서는 최신 명세로 대체한다.

- 기존 학습 사이트와 M/C/D 교재는 사용자가 품질을 거부했다. 부분 덧붙이기로 해결하지 않는다.
- 기존 구간·제목·본문·화면을 새 제작의 틀로 삼지 않는다.
- 아직 새 본편도 새 HTML 디자인 3안도 작성하지 않았다.
- DRIVING_LESSON_SAMPLE.md는 설명 방법의 한 표본이다. 전체 교재 구조·정답·최소 충족 기준이 아니다.
- 모델은 사용자가 UI에서 선택한다. 이 파일이 주 모델 설정을 자동 변경한다고 주장하지 않는다.
- 보조 에이전트를 사용하는 경우 사용자 지정과 같은 모델·reasoning을 따른다. 실제 호출에서 지원되는 이름은 도구 목록을 확인한다. 현재 제공된 별칭은 gpt-6.2-sol, reasoning_effort high다.
- 전역 스킬·설정 변경은 이미 실행한 일이 아니다.

## 2. 반드시 보존할 사용자 의도

독자는 프로그래밍 숙련자이고 RAG를 접해 봤다. 초기에는 Enterprise Brain이 처음이었으며, 지금은 직접 Graph DB·RDF·ontology·Neo4j·Cypher 기초를 공부했다. 이 사실을 이유로 독립 교재의 기초 설명을 생략하지 않는다. 복습을 빨리 통과할 수 있는 경로를 제공한다.

목표는 모든 핵심 개념의 뜻·배경·구성·특징·작동 원리·다른 개념과의 관계·쓰임·한계를 이해하고 **새 예를 들어 다른 사람에게 설명할 수 있는 것**이다. 외부 원문은 더 깊이 읽는 선택이어야 한다. 핵심을 이해하려면 원문으로 나가야 하는 자료는 미완성이다.

사용자가 든 RDF/운전 예는 부분 예시다. 모든 개념을 운전이나 하나의 파이프라인에 억지로 맞추지 않는다. 생소한 기호를 설명하지 않은 코드, 정의·주의사항만 나열한 요약, 깊이를 보여주지 않는 ‘심화’ 제목을 반복하지 않는다.

분량은 기존보다 몇 배 커지는 것을 전제로 잡는다. 새 본편+survey 해설 계획량은 30만~45만 Unicode 문자 규모다. 이는 분량 상한이나 자동 합격 기준이 아니다. 충분한 설명을 위해 늘릴 수 있고, 표·코드 복제·상투적 경고로 수를 채우면 불합격이다. 현재 M/C/D 총량 111,077자, C 개념 교재 51,001자는 파일 기준 참고치다.

4~5일·16시간 제한은 폐기됐다. 발표 자료 제작은 나중이다. 반도체 기본 수준의 여러 사례를 사용하되 현실의 공정 사실과 합성 자료를 구분한다. 발표의 세부 아키텍처를 미리 정답으로 고정하지 않는다.

## 3. 시작할 때 읽을 파일

첫 실행에서는 다음을 순서대로 읽는다. 이후에는 변경된 상태와 현재 묶음만 읽는다.

1. 이 START_HERE.md.
2. STATE.json의 current_batch·next_actions·open_decisions·units.
3. CURRICULUM_BLUEPRINT.md의 공통 기준과 현재 제작할 단원 명세.
4. EXECUTION_PROTOCOL.md의 단계·검수·에이전트·커밋 절차.
5. TECHNICAL_HANDOFF.md의 저장소·빌드·배포 주의점.
6. 처음 한 번은 ../REBUILD_PLAN.md의 실패 분석. 상세 운전 표본은 해당 비교 수업을 만들 때만 읽는다.

모든 과거 파일·원문·도구 출력을 한꺼번에 읽지 않는다. 필요한 절을 읽고 근거 위치와 판단 결과를 파일에 남긴다.

## 4. 다음 실행의 정확한 첫 작업

B00 실행 준비부터 시작한다.

- git status로 사용자 변경을 확인하고 계획 파일을 보존한다.
- STATE.json의 상태와 실제 산출물을 대조한다. 파일이 있다고 검수 완료로 간주하지 않는다.
- 새 원문 폴더 learning-v2/와 새 사례·단원 manifest를 만든다. 기존 production build 입력은 아직 바꾸지 않는다.
- BLUEPRINT의 U04 RDF/표현, U05 ontology, U13 RAG에서 각기 다른 설명 방식의 표본 수업을 고른다.
- 표본마다 학습 질문→필요한 선행 개념→본문 상세안→예제 데이터→실제 근거 절을 준비한다. 계획만 반복하지 말고 첫 표본 본문까지 작성한다.
- 처음 작성할 주제의 사실·구문을 확인하고, 설명 공백 검토를 받거나 독립 재검토한다.
- 상태와 작업 기록에 완료한 것·다음 구체 행동을 남기고, 검증된 묶음을 commit/push한다.
- 남은 작업을 계속한다. 한 묶음 커밋을 전체 완료나 자동 중단 이유로 삼지 않는다.

## 5. 디자인 확인과 자율 진행의 관계

같은 실제 수업 내용을 담은 HTML 3안을 제작해 사용자가 선택할 구체물을 제공한다. 서체·색만 바꾼 3안은 불충분하다. 비교형 수업과 긴 해설 읽기 모두를 검토할 수 있게 한다.

디자인 선택 요청은 프로토타입이 완성된 뒤 한 번만 구체적으로 한다. 사용자의 답변을 기다리는 동안 독립적인 조사·본문·예제·검토는 계속한다. 경과 시간이나 무응답을 승인으로 간주하지 않는다. 디자인이 미정이면 그 선택에 종속되는 전면 UI 확정·운영 교체만 보류한다.

이 디자인 확인은 사용자가 앞서 요구한 절차다. 모든 문단·단원·커밋마다 승인받는 절차가 아니다. 다음 실행을 시작하기 위한 추가 프롬프트도 필요 없다.

## 6. 지속 실행과 종료

- 컴팩션·턴 재개 시 STATE.json부터 읽는다. 현재 묶음의 출력과 git 이력을 확인하고 다음 작업을 이어간다.
- 실제 한도·중단으로 멈춰야 한다면 미완료 내용을 짧게 축약해 완성 처리하지 않는다. next_actions를 명령 수준으로 남긴다.
- 상태는 not_started → researching → drafting → reviewing → ready → integrated로 진행한다.
- ready는 기술 검토·설명 검토·필수 산출물 증거가 있어야 한다. integrated는 웹에서 본문·예제·도해가 보존되어야 한다.
- 전체 완료는 모든 단원·survey·시각화·웹 통합·출처 검토·배포·git push가 끝난 때다. 파일 수·글자 수·테스트 개수는 보조 정보다.
- 새 설명의 실제 이해 효과를 AI 평가나 기능 검사만으로 입증했다고 말하지 않는다.

## 7. 실행 권한 범위

사용자는 전면 개편의 조사·Markdown·웹 제작과 묶음별 commit/push를 이미 요청했다. 해당 작업은 재허가 없이 진행한다. 사이트의 기존 비공개 범위를 유지한다. 관련 없는 파일·전역 스킬을 삭제하지 않는다.

에이전트 활용은 EXECUTION_PROTOCOL의 검토·분담 계획에 따라 제한적으로 수행한다. 에이전트를 쓰기 어려우면 같은 검토 계약을 순차 실행한다. 특정 스킬·에이전트가 없다는 이유로 전체 작업을 멈추지 않는다.
