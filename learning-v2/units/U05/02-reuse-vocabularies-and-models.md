# 이름과 의미를 재사용할 때 일치하는 범위를 정하기

구매팀의 부품 검색에는 ‘진공 펌프’, 정비팀의 작업 화면에는 ‘진공계 펌프’라는 항목이 있습니다. 엔지니어가 두 이름을 왔다 갔다 검색해야 하는 문제라면 두 어휘를 연결해 해결할 수 있습니다. 그러나 정비 수행을 조회하는 화면이 구매 카탈로그의 제품 사양까지 정비 대상으로 세면, 이름이 연결됐다고 해서 데이터의 뜻을 맞춘 것은 아닙니다. 이 수업에서는 어떤 결과를 만들려는지 먼저 정한 뒤, 같은 업체 안에서 이미 관리하는 코드와 공개 어휘를 어디까지 재사용할지 결정합니다.

## 분류 메뉴의 개념, 실물의 유형, 입력 필드

앞 수업에서는 공정 장비의 하위 클래스에 식각 장비를 둡니다. 클래스는 공통 정의에 속하는 대상의 집합으로 이해할 수 있습니다. A-07은 그 집합의 한 구성원입니다. 다른 화면에서는 관리자가 기술 문서에 ‘식각 장비’라는 주제 분류를 붙입니다. 식각 장비 매뉴얼에서 그 항목을 찾아 들어가고, 상위 주제인 ‘공정 장비’를 탐색할 수 있습니다. 이때 분류하는 대상은 매뉴얼입니다. 매뉴얼이 식각 기능을 수행하는 실물이 될 필요는 없습니다.

**통제 어휘**에서는 사람이 양식에 입력할 표준 라벨과 코드를 관리합니다. 동일한 뜻으로 쓸 이름을 하나 정하고, ‘식각기’처럼 검색에 도움이 되는 대체 이름을 둘 수 있습니다. 여기에 좁은 항목을 넓은 항목 밑에 놓는 **분류 체계(taxonomy)**를 더하면 탐색 경로가 생깁니다. **SKOS**는 이런 용어목록, 분류 체계, 시소러스를 공유하고 연결할 수 있는 RDF 모델입니다. 시소러스는 대표·대체 용어와 상하·연관 관계를 운영하는 어휘입니다. 이 접근은 어디에서 어떤 이름을 쓸지 명시하는 데 적합합니다. [W3C SKOS Reference §1, §3.5.1, §5](https://www.w3.org/TR/2009/REC-skos-reference-20090818/#concepts)

**개념 모델**은 업무에 존재하는 대상과 관계를 설계자가 합의할 때 사용합니다. ‘담당자가 지시를 등록한다’와 ‘실제 작업을 수행한다’를 두 상자에 나누는 그림에서 업무 규칙이 드러납니다. **도메인 온톨로지**는 함께 쓸 개념과 관계, 정의에서 따르는 결론을 공유하는 데 초점을 둡니다. 예를 들어 A-07 자체를 공정 장비 조회에 포함해야 한다면 “식각 장비에 속하는 모든 것은 공정 장비에 속한다”라는 의미가 필요합니다. **데이터베이스 스키마**에서도 장비 행을 식별하는 키와 모델 참조, 허용할 코드와 상태 전이를 관리해 업무 의미를 표현할 수 있습니다. 다만 공정 장비 조회의 범위를 SQL 뷰로 구현할지, 애플리케이션에서 트리 계층을 따라갈지, OWL 공리를 선언해 추론할지는 별도로 정합니다. [Stanford Ontology Development 101 §1, §3](https://protege.stanford.edu/publications/ontology_development/ontology101.pdf#page=4), [OWL 2 Primer §3–4](https://www.w3.org/TR/2012/REC-owl2-primer-20121211/#Modeling_Knowledge:_Basic_Notions)

| 다음 기능이 요구하는 것 | 선택할 표현 | 확인 가능한 예 |
| --- | --- | --- |
| ‘식각기’로 검색해도 관련 문서를 찾기 | 통제 어휘의 대표·대체 이름 | ‘식각 장비’ 주제로 분류한 문서가 나타납니다. |
| ‘공정 장비’에서 더 구체적인 주제로 들어가기 | SKOS의 상하 관계를 사용하는 분류 | ‘식각 장비’가 탐색 메뉴의 하위 항목에 나타납니다. |
| 모든 공정 장비 실물의 집합을 조회하기 | 클래스 포함을 정의한 온톨로지와 해당 추론 또는 질의 규칙 | 식각 장비 개체 A-07·A-08이 포함됩니다. |
| 실제 사용 중인 모델 코드를 장비 등록 때 확인하기 | 자산 모델의 참조 관계와 DB의 외래 키 | 등록된 모델의 ID를 참조합니다. |

## 두 종류의 ‘식각 장비’를 식별자로 구별합니다

다음 Turtle에서는 하나의 주제 개념과 하나의 업무 클래스를 각각 선언합니다. `@prefix`는 짧게 쓸 앞부분을 정합니다. `voc:`는 문서 주제의 주소, 이름 앞에 단독으로 쓰인 `:`는 자산 업무 모델의 주소입니다. `a`는 `rdf:type`의 약어로, 주어가 어떤 클래스에 속함을 나타냅니다. 세미콜론 다음에는 방금 쓴 주어를 이어 쓰고, 마침표가 그 주어에 대한 트리플 묶음을 끝냅니다. 큰따옴표는 문자열, `@ko`는 한국어 라벨이라는 표시입니다.

```turtle
@prefix : <https://example.org/maintenance/> .
@prefix voc: <https://example.org/topics/> .
@prefix skos: <http://www.w3.org/2004/02/skos/core#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

voc:Etch a skos:Concept ;
    skos:prefLabel "식각 장비"@ko ;
    skos:altLabel "식각기"@ko ;
    skos:broader voc:ProcessEquipment .
voc:ProcessEquipment a skos:Concept .

:EtchEquipment a owl:Class ;
    rdfs:subClassOf :ProcessEquipment .
:ProcessEquipment a owl:Class .
:A07 a :EtchEquipment .
```

`voc:Etch`에는 이름이 있고 주제 메뉴의 위 항목을 가리킵니다. `skos:broader`의 방향은 더 좁은 개념에서 더 넓은 개념으로 향합니다. `:EtchEquipment`에는 장비 실물이 속하고, `rdfs:subClassOf`가 있으면 그 실물이 상위 클래스에도 속합니다. 검색 창에 같은 이름을 표시해도 이 두 주소가 가리키는 대상을 다르게 관리합니다. 예를 들어 기술 매뉴얼 U-44에 주제 `voc:Etch`를 달아도 그것만으로 U-44를 `:EtchEquipment`의 개체로 분류할 근거는 생기지 않습니다. SKOS 규격도 개념 탐색을 위한 관계와 클래스 포함을 이용하는 모델의 역할을 따로 설명합니다. [SKOS Reference §3.5.1, §8.6.6](https://www.w3.org/TR/2009/REC-skos-reference-20090818/#semantic-relations)

## 코드 두 개를 대응시키려면 어느 차이를 남겨야 할까요

아래 구매·작업 코드는 비교를 위해 만든 합성 어휘입니다. 두 팀의 담당자가 원천 코드북의 정의, 정상 예, 경계 예를 읽은 후 비교합니다. 같은 라벨이라도 입력이나 집계에서 허용하는 범위가 다를 수 있습니다.

| 원천의 정의와 예 | 목적 모델에서 찾을 후보 | 판정과 결과 |
| --- | --- | --- |
| 부품 카탈로그의 VPU는 진공 펌프 제품군입니다. 창고에 있는 재고도 포함합니다. | 정비 분류의 ‘진공계 부품’은 펌프와 호스도 포함합니다. | VPU 쪽이 좁습니다. 주제 검색에는 넓은 쪽을 가리키는 `skos:broadMatch`를 검토합니다. 진공계 부품 전부를 펌프로 매핑하면 호스가 잘못 포함됩니다. |
| 두 팀의 검색 어휘에서 '식각 장비'는 같은 주제 범위와 경계 예를 갖습니다. | 양쪽의 식각 장비 주제 | 여러 검색 기능에서 서로 대신 쓸 수 있다는 근거가 충분하면 `skos:exactMatch`를 쓸 수 있습니다. 실물과 제품 사양을 합치는 근거에는 사용하지 않습니다. |
| 전산실의 REPAIR는 부품을 분리해 복원하는 작업과 교체 작업을 포괄합니다. | 정비의 REPLACEMENT는 제거·설치의 역할을 모두 요구합니다. | 넓은 REPAIR를 읽고 교체를 확정하지 않습니다. 작업에서 두 역할이 보고됐는지 확인하거나 상위 정비 수행 분류로만 매핑합니다. |
| 운영 대장의 ALARM은 장치가 낸 신호의 기록입니다. | 품질 대장의 DEFECT는 검토자가 확인한 결함입니다. | 별도 개념을 유지합니다. 개별 확인 기록이 실제로 참조한 경보만 근거 관계로 연결합니다. |

`skos:closeMatch`는 어떤 정보 검색 기능에서는 서로 대신 쓸 정도로 유사함을, `skos:exactMatch`는 넓은 범위의 그런 기능에서 호환된다는 높은 확신을 표현합니다. `exactMatch`는 연쇄에서 전이합니다. A와 B, B와 C가 정확 대응하면 A와 C도 연결될 수 있으므로, 팀 하나가 자기 범위에서만 비슷하다고 확인했다면 뒤의 연결까지 검토합니다. `owl:equivalentClass`는 두 클래스에 속할 수 있는 대상의 집합이 같다는 선언이고, `owl:sameAs`는 두 이름이 같은 개체를 가리킨다는 더 다른 주장입니다. 주제 리소스 간 검색 대응만 있을 때는 업무 실물이나 클래스 전체를 그 방식으로 합칠 근거가 충분하지 않습니다. [SKOS Reference §10.1, §10.3, §10.6.3, §10.6.8](https://www.w3.org/TR/2009/REC-skos-reference-20090818/#mapping)

## 공개 모델은 정의가 맞는 조각부터 가져옵니다

출처 이력을 다른 시스템과 같이 제공하려고 W3C의 **PROV-O**를 검토해 봅니다. PROV-O에서 `prov:Entity`는 어떤 특성을 가진 물리적·디지털·개념적 대상이 될 수 있고, `prov:Activity`는 시간에 걸쳐 일어나는 활동입니다. 문서 RPT-02 개정 1의 생성을 추적한다면 문서 파일을 Entity, 작성 활동 REG-02를 Activity로 두고 문서에서 작성 활동을 향해 `prov:wasGeneratedBy`로 연결할 수 있습니다. 이 사례에서 근거 작성 활동(REG-02)과 실제 교체(E-02)는 각각의 시간이 있고, 기록은 교체를 기술합니다. 문서가 했다고 적은 행위와 문서를 만든 행위가 구별됩니다. [W3C PROV-O Recommendation §3.1](https://www.w3.org/TR/2013/REC-prov-o-20130430/#starting-point-terms)

`prov:wasGeneratedBy` 하나로 ‘보고서는 E-02에 관한 것이다’까지 표현하려고 하면, 그래프를 읽는 사람은 실제 교체가 그 문서를 생성했다고 해석할 수 있습니다. 작성 등록 이벤트가 별도로 있다면 팀에서 정의한 ‘정비 수행을 기술함’ 관계를 문서에서 E-02로 추가합니다. 이때 PROV의 공통 표현은 문서 생성의 출처를 주고, 도메인 관계는 문서가 설명한 대상을 알려줍니다. 공개 모델에 해당 관계가 있다고 바로 가져오기보다, 정의·방향·값 범위·추론 결과가 해당 업무 질문에 맞는지 작은 데이터를 두고 확인합니다.

가져올 범위도 결정합니다. 협력 시스템도 PROV를 읽을 수 있고 공통 파일 생성 관계가 필요하다면 같은 IRI를 쓰는 데 이점이 있습니다. 배포가 요구하는 추론이 공리 전체를 가져오는 데 의존한다면 버전과 가져온 공리·의존 파일을 따로 기록합니다. 업무 화면에서 보고서와 교체 사건의 연결만 제공한다면 필요한 관계 몇 개를 살펴 재사용하고, 도메인 특유의 관계는 자체 이름으로 관리할 수 있습니다. 명세에 있는 어휘를 사용한다는 선언만으로 엔진이 다른 문서를 다운로드하고 해석하는 것은 처리기의 의존성 설정에 달려 있습니다. [OWL 2 Structural Specification §3.4](https://www.w3.org/TR/2012/REC-owl2-syntax-20121211/#Imports), [Noy·McGuinness §3 Step 2](https://protege.stanford.edu/publications/ontology_development/ontology101.pdf#page=5)

## 설명 연습

**1.** 도서관의 검색 주제 ‘고서’와 소장 관리의 ‘고서 실물’이 있습니다. 고서 보존 안내서도 검색에서 나와야 하고, 온습도 기록 대상은 실제 고서만이어야 한다면 각각 무엇을 모델링하겠습니까?

주제에는 대표 라벨과 상하 관계를 두고 보존 안내서에 주제 ID를 붙입니다. 온습도 관리에서는 소장본을 특정할 ID와 고서 실물 클래스의 정의를 사용합니다. 같은 말을 쓰더라도 안내서에 달린 주제 ID 때문에 안내서 자체가 고서 실물로 분류되지는 않습니다. 보존 담당자가 소장본을 분류하는 근거를 별도로 정의해야 합니다.

**2.** 화재 점검의 ‘출입 확인서’와 시스템의 ‘출입 승인’을 이름이 비슷하다는 이유로 동치 클래스라 부를 수 있을까요?

확인서는 문서이고 승인이 시간에 걸쳐 일어나는 판단이라면 서로의 개체 범위가 다릅니다. 어느 문서가 어느 승인 활동에서 발급됐는지를 관계로 표현하고, 검색에서 같은 주제로 찾는 편의는 별도 어휘에서 다룹니다. 이름의 의미를 다시 보면 ‘정비 수행’과 ‘완료 확인서’를 다른 대상으로 구분한 이유도 설명할 수 있습니다.
