# 문서 전체의 변화를 묻는다면 무엇을 검색하나요?

구매 책임자가 정비·공급·반품 기록을 함께 올리고 “이 자료에서 분기 동안 일하는 방식이 어떻게 바뀌었나요?”라고 물었습니다. ‘김하늘’처럼 어떤 개체를 바로 잡을 수 있는 단서가 없고, ‘일하는 방식’은 어느 문서 제목에도 없습니다. 한 사람의 승인 이력을 따라가는 경로와 다른 검토가 필요합니다. 공급 변경, 현장 점검, 반품 기록이라는 여러 묶음을 읽고 각 묶음의 변화에서 전체 주제를 구성해야 합니다.

**Microsoft GraphRAG**는 원문에서 개체와 관계를 추출하고, 그 관계망을 여러 **커뮤니티**로 묶어 자료를 검색하는 구체적인 도구·방법입니다. 이때 커뮤니티란 관계가 밀집한 개체들의 그룹입니다. 비슷한 주제 이름을 붙여 직접 분류한 폴더보다, 자료에서 어떤 개체들이 서로 연결되는지가 그룹 형성에 관여합니다. 사람·부품·절차·사건이 한 묶음에 들어갈 수 있습니다. 앞 수업처럼 이미 구축된 업무 KG에 정확한 경로를 질의하는 방식도 넓은 의미의 그래프 활용 RAG에 속합니다. 여기서는 Microsoft 논문의 그래프 구성과 전체 질문 처리, 공식 문서의 개체 중심 Local Search를 각각 따라갑니다. [Edge et al., arXiv v2, §3.1](https://arxiv.org/html/2404.16130#S3.SS1), [Microsoft GraphRAG, Query Overview](https://microsoft.github.io/graphrag/query/overview/)

> **교육용 모의 예.** 다음 개체 추출, 커뮤니티, 보고서, 검색 입력, 중요도와 답변은 이 장의 기록을 사람이 엮은 것입니다. 모델이나 Leiden 실행 결과가 아닙니다. 앞 수업의 G01~G11에 이 수업의 G12~G18을 더한 자료를 사용합니다.

## 먼저 읽는 자료를 작게 나눕니다

아래 추가 기록은 한 자료 묶음 안에서도 관심사가 다름을 보여 줍니다. 한 청크를 읽고 다른 청크가 무엇을 뜻하는지 모르더라도, 개체 관계를 모으면 서로 참조할 수 있습니다.

| 원문 조각 | 원본 위치 | 원문에 해당하는 내용 |
| --- | --- | --- |
| G12 | 점검 지침 v2, p.2 §3 | PX-47 점검표에 ‘모드 확인’ 항목을 추가했다. |
| G13 | 운영 회의록 04호, p.1 항목 2 | W-207 이후 PX-47 점검표에 재시험 시각을 남기기로 했다. |
| G14 | 반품 지침 v2, p.4 항목 8 | RH-12 반품은 송장 원본 번호를 의무 기록한다. |
| G15 | 배송 회의록 04호, p.2 항목 5 | RH-12 송장을 사진으로만 남기던 방식을 중단하고 반품 기록에 송장 번호를 구조화한다. |
| G16 | 부품변경 회의록 04호, p.1 항목 3 | CR-119부터 변경 승인자는 승인 대장에 담당 역할과 이름을 함께 남긴다. |

| G18 | 운영 회의록 05호, p.2 항목 5 | PX-47 점검표의 모드와 재시험 시각은 정비 일지의 같은 작업 번호로 연결한다. |

Microsoft GraphRAG 문서에서 **TextUnit**은 그래프 구축 또는 검색에 쓰는 원문 조각입니다. 예에서는 G01~G18을 각각 한 TextUnit으로 간주합니다. TextUnit은 어떤 문서에서 왔는지 추적할 수 있습니다. 문서 원본과 조각의 연결이 없으면 추출 결과가 이상할 때 어떤 페이지를 고쳐야 하는지 알기 어렵습니다. 청크에 작업 번호는 들어가고 교체 부품 번호가 옆 청크에만 남으면, 추출기가 관계 양끝을 함께 읽지 못할 수 있습니다. 반대로 서로 다른 공급 변경 행이 한 청크에 들어가면 승인자 이름을 잘못된 변경 건에 붙일 여지가 생깁니다. [Microsoft GraphRAG, Indexing Dataflow, Phases 1–2](https://microsoft.github.io/graphrag/index/default_dataflow/#phase-1-compose-textunits)

## TextUnit에서 개체 설명과 관계 설명을 쌓습니다

예를 들어 G01을 읽은 추출기가 “W-207은 3월 20일 PX-47의 정비 작업”, “VL-042는 현장에서 교체된 밸브”라는 개체 설명을 만들 수 있습니다. 관계 후보는 “W-207에서 VL-042를 교체했다”입니다. G02를 읽으면 VL-042에 “릴리프 밸브, 별칭 현장 밸브”라는 설명이 추가됩니다. G03은 VL-042, CR-119, 한빛정밀과 그 사이 연결을, G04는 CR-119와 김하늘의 최종 승인 연결을 제공합니다.

| 추출 대상 | 어디에서 나왔나요? | 통합 후 읽을 정보 |
| --- | --- | --- |
| VL-042 이름과 설명 | G01, G02, G03, G05 | W-207에서 교체한 릴리프 밸브이며 두 공급 변경 이력에 등장합니다. |
| CR-119 이름과 설명 | G03, G04, G16 | 공급사 변경 사건이며 지정 공급사, 최종 승인자, 기록 규칙을 연결합니다. |
| CR-119와 김하늘의 관계 | G04 | 김하늘이 이 변경 건을 최종 승인했습니다. |
| PX-47과 점검표·작업의 연결 | G01, G12, G13, G18 | PX-47 점검 기록에 모드와 재시험 시각이 추가되고 작업 번호로 참조됩니다. |
| RH-12와 송장·반품 기록 연결 | G14, G15, G17 | 반품에 송장 원본 번호를 남기며 시험 출하 건에는 예외가 있습니다. |

논문은 LLM을 사용해 추출한 개체와 관계에 설명을 붙이고, 반복된 개체·관계 설명을 모아 요약합니다. 논문 실험의 개체 이름 연결은 문자열 완전 일치에 기반했습니다. 같은 이름으로 나온 내용을 합치는 것은 가능하지만, 별칭을 구별하거나 같은 이름의 다른 부품을 해소하는 데는 추가 설계가 필요합니다. 논문의 관계 집계에서는 반복 횟수가 그래프 간선의 가중치가 될 수 있습니다. **가중치**는 연결을 군집화 등에 사용할 때 반영할 수치입니다. 같은 공지를 베낀 열 개 페이지에서 관계가 열 번 나왔더라도, 독립된 출처 열 곳이 검증했다는 뜻은 아닙니다. 공식 데이터 흐름에서 선택적인 **Covariate**는 개체에 관한 시간 범위·평가 상태를 담을 수 있는 추출 주장입니다. 이 사례의 기간 조건을 보존하려면 TextUnit과 대장 행을 함께 검토합니다. [Edge et al., §3.1.2–3.1.3](https://arxiv.org/html/2404.16130#S3.SS1.SSS2), [Microsoft GraphRAG, Indexing Dataflow, Phase 3](https://microsoft.github.io/graphrag/index/default_dataflow/#phase-3-graph-extraction)

## 관계가 모이는 곳을 찾고 보고서를 씁니다

**군집화**는 여러 대상을 어떤 기준으로 묶는 일입니다. 이 방법은 개별 문단의 글이 비슷한지만 비교하는 대신, 개체 그래프에서 연결이 어떤 그룹에 모이는지를 사용합니다. Microsoft 방식은 계층적인 **Leiden 커뮤니티 탐지**를 사용합니다. 우선 그래프에서 큰 커뮤니티를 찾고, 필요한 경우 그 안에서 작은 커뮤니티를 다시 찾아 여러 수준을 만듭니다. ‘수준’은 여기서 같은 그룹 묶음을 어떤 상세도로 볼지를 나타냅니다. 다음 예는 큰 묶음이 작은 묶음을 포함하는 모습을 보여 줍니다. G01~G18에서는 세 관심사를 읽어 볼 수 있고, W-207이나 PX-47 같은 개체가 다른 관심사 사이의 관계를 매개할 수도 있습니다.

```text
상세도가 낮은 수준
  A 정비와 구매 기록                     B 반품과 배송 기록
       ↓                     ↓                        ↓
상세도가 높은 수준
  A1 점검·작업             A2 부품 공급·승인       B1 송장·반품
```

A1과 A2는 모의 관계 묶음에 붙인 이름입니다. 그림에서 B 영역은 두 수준에 걸쳐 같은 개체 묶음을 사용한다고 가정했습니다. `B1`은 상세 보고서의 범위를 알아보기 위한 이 예의 표기입니다. 실제 군집 경계는 이름과 같은 업무 taxonomy(업무상 분류 체계)에 의해 정해지지 않습니다. 예를 들어 PX-47이 정비·부품에 모두 등장해도, 분할에 사용한 수준에서 한 노드에 두 독립 커뮤니티 소속을 임의로 부여하지 않습니다. 커뮤니티 바깥으로 나가는 관계는 존재할 수 있습니다. 논문은 계층별 분할을 사용하며 구현은 데이터 흐름의 설정에 따라 커뮤니티를 계산합니다. [Edge et al., §3.1.4, §4.1.2 및 Appendix B](https://arxiv.org/html/2404.16130#S3.SS1.SSS4), [Microsoft GraphRAG, Community Detection](https://microsoft.github.io/graphrag/index/default_dataflow/#community-detection)

**커뮤니티 보고서**(community report)는 해당 그룹의 개체·관계 설명 및 관련 주장을 읽고 만들어 둔 요약입니다. 원문을 검색할 때마다 백 페이지를 다시 읽는 대신, 색인을 구축할 때 관심사별로 읽을 요약을 먼저 만드는 셈입니다. 아래와 같이 압축하면 어느 팀의 일이 어떻게 바뀌었는지 훑기 쉬워집니다.

| 보고서 | 교육용 보고서 본문 | 남은 원문 참조 |
| --- | --- | --- |
| R-A1 | PX-47 점검표는 모드와 재시험 시각을 구분해 남긴다. 정비 일지와 같은 작업 번호로 연결한다. | G12, G13, G18 |
| R-A2 | VL-042는 CR-119로 지정 공급사가 한빛정밀로 바뀌었다. CR-119부터 승인자의 담당 역할과 이름을 함께 남긴다. | G03, G04, G16 |
| R-B1 | RH-12 반품은 송장 사진만 남기는 관행에서 송장 번호를 구조화하는 방식으로 바뀌었다. | G14, G15 |
| R-A | 정비에서 점검 조건·시각을 같은 작업에 연결하고, 부품 공급 변경에서는 승인자의 역할까지 기록하도록 변경했다. | R-A1, R-A2 |
| R-B | 반품에는 송장 번호를 기록하도록 변경했다. | R-B1 |

논문에서 계층의 아래쪽에 있는 상세 보고서에는 해당 커뮤니티의 개체·관계·주장 설명을 토큰 한도 내에서 담습니다. 위쪽의 더 넓은 커뮤니티에서는 내용이 들어가면 개체·관계 등의 설명을 사용하고, 너무 길면 일부 하위 커뮤니티의 원래 설명 묶음을 그 커뮤니티의 짧은 요약으로 바꿉니다. 이미 요약한 설명을 다시 압축하면 규모를 감당하기 쉬워집니다. 위의 R-B1이 시험 출하 예외 G17을 빠뜨렸다면 R-B에서도 찾기 어렵습니다. ‘전체 흐름’ 요약에 빠져도 되는 내용과, ‘예외 조건 전부’라는 질문에 빠져서는 안 되는 내용이 다릅니다. 변경 추적을 위해 어떤 보고서가 어떤 조각에서 파생되었는지 보존합니다. [Edge et al., §3.1.5](https://arxiv.org/html/2404.16130#S3.SS1.SSS5)

## Local Search는 특정 개체를 중심으로 근거를 모읍니다

“VL-042 공급 변경 CR-119의 승인 기록을 설명해 주세요”라는 질문에는 개체를 지목하는 코드가 있습니다. 공식 Local Search의 입력은 질문과 선택적인 대화 이력입니다. 질문을 벡터로 바꾸어 **개체 설명의 임베딩**과 비교하면 CR-119, VL-042가 시작점 후보가 됩니다. 개체의 이름 외에 설명을 비교하는 까닭은 질문의 표현이 추출된 제목과 조금 달라도 연결할 수 있기 때문입니다. 이 사례처럼 특정 코드가 명확하면 코드 일치 여부를 추가로 검사하는 설계도 가능합니다.

개체에서 관계와 원문, 관련 보고서를 회수해 제한된 입력으로 만듭니다. 시작점과 연결된 모든 텍스트를 무조건 읽히면, 전체 경향을 집약한 보고서나 상관없는 부품 정보가 오히려 G04를 밀어낼 수 있습니다. 아래는 이 질문에 후보를 제한하는 한 가지 예입니다.

| 후보 종류 | 후보 | 컨텍스트에 담는 예 |
| --- | --- | --- |
| 연결 개체 | CR-119, VL-042, 김하늘, 한빛정밀 | 네 개체의 짧은 이름·역할 |
| 관계 | 대상 부품, 공급사 변경, 최종 승인 | CR-119를 중심으로 한 세 연결 |
| TextUnit | G03, G04, G16, G05, G08 | G03, G04, G16. 이전·관련 없는 변경 행은 제외 |
| 커뮤니티 보고서 | R-A2, R-A | 부품 변경 문맥이 더 가까운 R-A2 |
| Covariate | 선택 기능이 켜진 경우 평가 상태와 시간 조건을 담은 추출 주장 | 이 모의 예에서는 생략하고 대장 원문으로 확인 |

답변에는 “CR-119는 VL-042의 지정 공급사를 2026년 4월 1일부터 한빛정밀로 변경한 건이고 [G03], 구매품질 담당 김하늘이 최종 승인했습니다 [G04]. CR-119부터 승인 대장에는 승인자의 역할과 이름을 함께 남깁니다 [G16].”라고 쓸 수 있습니다. 집어넣은 R-A2는 변화의 배경을 잡는 데 도움이 되지만, 정확한 사람 이름과 날짜는 원문에서 확인합니다. 앞 수업의 고정 세 홉 방식은 경로 조건을 명시하여 행을 찾습니다. Local Search는 질문에서 관련 개체를 매핑하고 관계에 붙은 여러 자료를 한 창 안에 조합합니다. [Microsoft GraphRAG, Local Search, Methodology](https://microsoft.github.io/graphrag/query/local_search/#methodology)

## Global Search는 보고서 묶음에서 질문과 관련된 관점을 합칩니다

“이 자료에서 분기 동안 일하는 방식이 어떻게 바뀌었나요?”는 어떤 개체 또는 한 승인 행에서 끝나는 질문이 아닙니다. 보고서가 이미 자료 전반의 여러 부분을 요약하고 있으므로, 선택한 커뮤니티 수준에서 보고서들을 묶어서 질문을 보낼 수 있습니다. **Map** 단계는 각 묶음을 독립적으로 읽고 질문의 답변에 도움이 될 요점을 만듭니다. **Reduce** 단계는 중간 요점을 모아 예산 안에서 최종 답변으로 엮습니다. 논문의 Map은 보고서를 섞어 크기가 제한된 여러 묶음으로 나누고, 모델이 응답의 유용성을 점수화한 뒤 0점을 제거합니다. 공식 문서는 중요도가 붙은 중간 요점들을 필터링·결합하는 흐름을 설명합니다. 이 점수는 모델의 추정입니다. 시행 일자나 내용의 진실성을 검증한 수치로 해석할 수 없습니다. [Edge et al., §3.1.6](https://arxiv.org/html/2404.16130#S3.SS1.SSS6), [Microsoft GraphRAG, Global Search, Methodology](https://microsoft.github.io/graphrag/query/global_search/#methodology)

| Map에 넣은 모의 자료 묶음 | 모의 중간 요점 | 모의 중요도 |
| --- | --- | --- |
| R-A1 | 점검 모드와 재시험 시각을 별도 기록하고 작업 번호로 연결합니다. | 90 |
| R-A2 | 공급 변경 때 승인자의 역할과 이름을 함께 남깁니다. | 84 |
| R-B1 | 반품 기록에 송장 번호를 항목으로 남깁니다. | 88 |
| R-A2에서 나온 별도 문장 | 특정 부품의 지정 공급사가 한빛정밀로 바뀌었습니다. | 15 |

Reduce에 요점 세 개를 넣을 수 있다면 90, 88, 84 순서의 요점이 들어갑니다. 최종 답변은 세 업무 영역에서 공통으로 **사건을 다른 기록과 연결할 식별자나 역할을 구체적으로 남기는 방향**의 변화가 관찰된다고 정리할 수 있습니다. 문서의 분기 전체 업무 횟수나 실제 이행률은 이 보고서에서 계산할 수 없습니다. 정확한 횟수가 필요하면, 날짜 범위와 대상 레코드를 지정한 조회로 확인해야 합니다. 점수 두 개만 들어가면 공급 변경의 승인 역할 기록은 누락됩니다. 더 자세한 수준에서 보고서를 고르면 특정 예외가 보일 수도 있고, 처리할 보고서 수가 늘 수 있습니다.

## 출력 하나로 원인을 짚습니다

보고서에 “모든 RH-12 반품과 시험 출하에서 송장 원본 번호를 남긴다”라고 적혔다고 해 보겠습니다. G17은 시험 출하 예외를 명시합니다. 어디에서 잘못됐는지는 최종 문장 하나만으로 특정할 수 없습니다.

| 처음 달라진 위치 | 확인할 입력과 출력 | 어디에서 고칠까요? |
| --- | --- | --- |
| 원문 분할 | G17에 코드와 예외 문장이 함께 들어갔나요? | 청크를 행 단위로 만들고 제목·코드를 남깁니다. |
| 추출 | RH-12 시험 출하와 ‘시험용 참조 번호’가 올바르게 연결됐나요? | 추출 후보와 근거 조각을 대조하고, 필요하면 특정 유형의 추출 예를 추가합니다. |
| 보고서 | G17의 예외 관계가 보고서 입력에는 있었는데 요약에서 사라졌나요? | 예외를 보존하는 보고서 항목을 두고 해당 산출물을 재생성합니다. |
| Map·Reduce | 예외가 보고서에는 있는데 중간 응답이나 최종 입력에서 빠졌나요? | 각 단계의 후보·점수·토큰 한도와 잘린 내용을 확인합니다. |
| 최종 생성 | 예외가 최종 문맥에 있는데 모델이 ‘모두’라고 했나요? | 답변의 양화 표현과 인용을 검토합니다. |

‘모든’과 ‘항상’은 몇 예를 요약하는 문장에서 범위를 크게 바꾸는 표현입니다. 짧은 질문이라도 정확한 예외가 필요하면 Global Search의 요약에서 답하지 않고, 필요한 범위의 원문으로 확인합니다. 반대로 “지침 전반에서 어떤 문서 관행이 새로 생겼는가?”라면 같은 사례에 여러 관점을 모으는 설계가 도움이 됩니다.

## 설명 연습

1. “CR-119의 승인 규칙”과 “분기 자료의 공통 변화” 중 어느 질문에 어떤 입력을 고를까요? 각 방식에서 최종 모델이 읽는 자료를 말해 보세요.
2. 보고서 R-A2가 G04를 누락해도 R-A2에 “승인자의 역할과 이름을 기록한다”는 문장이 남을 수 있습니다. 이 문장이 김하늘의 승인 사실을 뒷받침할까요?
3. 새 사례로 출장·교육·장비 요청 문서가 수천 건 있다고 가정합니다. 전체에서 반복된 승인 지연 유형을 설명하는 질문과, “교육 T-133의 재승인 날짜는?”에 같은 컨텍스트를 쓰면 어떤 한계가 생길까요?

### 해설

1. CR-119에는 Local Search의 개체·관계·TextUnit 입력이 맞습니다. 변경 건과 맞는 대장 행을 함께 읽혀 사람과 승인 규칙을 정확히 전할 수 있습니다. 공통 변화에는 Global Search로 여러 보고서 묶음에서 변화 요점을 만든 뒤 한 답변에 합치는 접근이 맞습니다.
2. 기록 규칙은 어떤 종류의 정보를 남겨야 하는지 설명합니다. 누가 실제로 승인했는지는 대장 행 G04의 개별 사실입니다. G04를 회수하지 못하면 김하늘을 확인할 수 없습니다.
3. 전체 지연 유형의 요약에는 여러 업무 묶음이 필요합니다. T-133 날짜는 한 교육 기록의 시점과 업무 번호를 정확히 찾아야 합니다. 묶음 요약에서 T-133 날짜는 쉽게 생략되며, 한 교육 기록으로 세 업무의 반복 유형을 설명할 수 없습니다.
