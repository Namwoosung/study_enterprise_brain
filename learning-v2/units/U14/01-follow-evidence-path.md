# 부품 교체 기록에서 승인 근거까지 경로를 따라가기

PX-47 정비원이 화면에서 수리 기록 W-207을 열었습니다. 기록에는 “현장 밸브 교체”라고 적혀 있고, 부품표에는 “릴리프 밸브”라고 적혀 있습니다. 같은 부품입니다. 이 부품의 공급사를 확인하고, 해당 공급 변경 건의 승인 담당자가 누구였는지 알아내려면 작업일지에서 부품표로, 부품표에서 공급 변경 대장으로, 대장에서 승인 기록으로 이동해야 합니다. 검색창에 작업 번호를 넣었을 때 작업일지만 잘 찾는다면, 질문에 답하기까지 여전히 세 번 더 찾아가야 합니다.

이 문제는 문장 하나와 질문의 표현이 얼마나 비슷한지 판단하는 일에 더해, 먼저 알아낸 식별자를 다음 조회에 사용하는 일이 필요합니다. 이 수업에서 그래프는 그 이동을 명시합니다. 질문을 이루는 대상과 관계를 찾아 경로를 만들고, 경로를 다시 원문과 연결한 뒤에 답변을 씁니다.

> **교육용 모의 예.** PX-47, W-207, 부품과 공급사, 승인 기록은 합성했습니다. W-207의 발생 사례는 U13에서 이어집니다. 교체와 공급 승인에 관한 아래 기록은 이번 수업에 추가한 합성 자료입니다. 경로와 필터는 [예제 자료](../../examples/rag-graph/graph.json)에서 로컬 Python으로 계산합니다. 생성 답변과 검색 후보 점수는 예시입니다.

## 그래프 안에서 어떤 지식을 찾을 수 있나요?

아래 기록을 읽고 작업 W-207의 교체 부품에 대해, **2026년 4월 10일 현재 적용 중인 공급 변경 건을 누가 승인했는지** 답해 보겠습니다. 작업 당시의 공급 조건을 묻는다면 기준일이 2026년 3월 20일로 달라집니다. 이 두 날짜에는 서로 다른 변경 건이 적용됩니다.

| 원문 조각 | 원본 위치 | 원문에 해당하는 내용 |
| --- | --- | --- |
| G01 | W-207 r1, p.2 교체 내역 | 2026-03-20, PX-47에서 현장 밸브 VL-042를 교체했다. |
| G02 | 부품표 v4, p.7 VL-042 행 | 표준 명칭은 ‘릴리프 밸브’, 품목 ID는 VL-042, W-207 기록에서 쓴 별칭은 ‘현장 밸브’다. |
| G03 | 공급 변경 대장 v3, p.6 CR-119 행 | VL-042 지정 공급사를 한빛정밀로 변경한다. 2026-04-01부터 적용한다. |
| G04 | 승인 대장 v3, p.3 CR-119 행 | 공급 변경 CR-119의 최종 승인자는 여러 검토자 중 구매품질 담당 김하늘이다. |
| G05 | 공급 변경 대장 v3, p.5 CR-106 행 | VL-042의 이전 공급 변경 건 CR-106에서 공급사는 세림밸브다. 2026-01-01부터 2026-04-01 직전까지 적용했다. |
| G06 | 승인 대장 v3, p.2 CR-106 행 | CR-106 최종 승인자는 조달 담당 박정우다. |
| G07 | W-207 r1, p.2 교체 내역 | 같은 작업에서 실링 부품 SE-077도 교체했다. |
| G08 | 공급 변경 대장 v3, p.9 CR-121 행 | SE-077 공급 변경 CR-121은 2026-04-02부터 적용한다. 지정 공급사는 한빛정밀이다. |
| G09 | 승인 대장 v3, p.4 CR-121 행 | CR-121 최종 승인자는 운영 담당 이별이다. |
| G10 | W-305 r1, p.1 작업 개요 | 별개 장비 PX-48에서 별개 작업 W-305를 열었다. |
| G11 | W-305 r1, p.2 교체 내역 | W-305에서 현장 밸브 VL-142를 교체했다. |

**개체**(entity)는 다른 것과 구별해서 찾을 대상입니다. W-207은 작업 개체, VL-042는 부품 개체, CR-119는 공급 변경 사건 개체입니다. 이 개체들을 **노드**(node)로 놓고, 두 개체 사이에 어떤 사실이 있는지를 **관계**로 기록합니다. 예를 들어 ‘W-207이 VL-042를 교체했다’는 `W-207 -[REPLACED]-> VL-042`로 표현합니다. 대괄호 안의 `REPLACED`는 관계 종류이고, 화살표는 작업에서 교체 부품을 찾는 방향입니다. 두 노드 사이에 이어지는 관계들의 열을 **경로**(path)라고 하고, 관계 하나를 건너는 이동을 한 **홉**(hop)이라고 합니다.

VL-042와 한빛정밀을 ‘공급한다’는 관계 하나로 바로 붙일 수도 있습니다. 이 경우 공급 변경 번호, 승인자, 적용 기간을 따로 따라가기가 어렵습니다. 이 예에서는 CR-119를 중간 노드로 두었습니다. 승인한 사람이 변경 건에 붙기 때문에, 실링 부품도 한빛정밀에서 공급한다는 사실이 승인자를 뒤섞지 않습니다. 점검자는 다음처럼 두 경로가 같은 CR-119에서 갈라지는 것을 확인합니다.

```text
W-207 ─REPLACED→ VL-042 ─HAS_CHANGE→ CR-119 ─APPROVED_BY→ 김하늘
                  │                      └NEW_SUPPLIER→ 한빛정밀
                  └HAS_CHANGE→ CR-106 ─APPROVED_BY→ 박정우
                   (2026-04-01 이전) └NEW_SUPPLIER→ 세림밸브

W-207 ─REPLACED→ SE-077 ─HAS_CHANGE→ CR-121 ─APPROVED_BY→ 이별
                                         └NEW_SUPPLIER→ 한빛정밀
W-305 ─REPLACED→ VL-142
```

이 데이터를 사내 **지식 그래프**(knowledge graph, KG)라고 부를 수 있습니다. 개체에 업무 식별자를 주고 관계에 해석할 수 있는 뜻을 부여했기 때문입니다. **그래프 데이터베이스**는 이런 노드와 관계를 저장하고 질의하는 역할을 합니다. 업무팀이 공급 변경과 승인의 뜻을 합의하고 기록을 정리하는 일은 데이터베이스를 설치하는 일과 별개입니다. **그래프 활용 RAG**는 관계를 사용해 생성 모델에 읽힐 근거를 찾는 응용 방식입니다. 관계로 필요한 행을 찾아 화면에 표시하면 그래프 조회이고, 같은 조회 결과로 자연어 답변을 구성하면 그래프를 활용한 검색 증강 생성이 됩니다. 이 예의 실습은 JSON 파일과 파이썬으로 관계를 처리합니다.

## 질문 속 표현을 실제 노드와 연결합니다

시작 질문은 “W-207에서 교체한 현장 밸브의 현재 지정 공급사와 그 변경 건의 승인자는 누구인가요?”입니다. 먼저 `W-207`이 작업 번호인지 찾습니다. 작업 테이블의 고유 번호와 일치하면 작업 노드가 시작점이 됩니다. 그다음 ‘현장 밸브’가 어느 부품인지 찾습니다. **개체 연결**(entity linking)은 질문의 표현을 자료 속 개체 ID와 대응시키는 일입니다. 표현이 같아도 ID가 여러 개일 수 있고, 표현이 달라도 같은 ID를 가리킬 수 있습니다.

이 예에서 ‘현장 밸브’는 VL-042와 VL-142의 후보를 모두 반환합니다. 업체별 용어가 같으므로 장비 조건이 없으면 별칭만으로는 식별하기 어렵습니다. W-207에서 `REPLACED` 관계를 따라가면 VL-042와 SE-077이 나옵니다. 별칭 후보 두 개와 이 교체 부품 두 개의 교집합에는 VL-042만 있습니다. 정규화된 명칭 ‘릴리프 밸브’는 원문 G02로 확인합니다.

| 단계 | 남는 대상 | 빠지는 대상과 이유 |
| --- | --- | --- |
| 작업 번호 조회 | W-207 | W-305는 질문의 번호와 다릅니다. |
| W-207의 교체 부품 | VL-042, SE-077 | VL-142는 W-305에서 교체했습니다. |
| ‘현장 밸브’ 후보와 교차 | VL-042 | SE-077은 작업 이력에는 있지만 별칭이 일치하지 않습니다. |
| 변경 건 후보 | CR-119, CR-106 | CR-121은 SE-077의 변경 건입니다. |
| 2026-04-10의 효력 검사 | CR-119 | CR-106은 2026-04-01에 효력이 끝났습니다. |
| 공급사 및 승인 관계 확인 | 한빛정밀, 김하늘 | CR-119에 붙은 관계만 사용합니다. |

실제로는 별칭 사전이나 문자열 규칙 외에 벡터 검색으로 개체 설명을 비교할 수도 있습니다. 그 경우 근접 점수가 높은 몇 개를 시작점 후보로 두고, 문서 번호·장비·개체 유형 등으로 확인합니다. 최고 점수 후보를 확정해 버리면 뒤쪽 경로가 그럴듯해도 잘못된 개체의 기록입니다. 예를 들어 `VL-142`를 별칭만으로 확정하면 W-207에 교체 관계가 없어 경로가 끊깁니다. 이 상태는 ‘승인 없음’을 뜻하지 않습니다. 현재 연결에서 승인에 이르는 경로를 확인하지 못한 상태입니다.

개체를 과하게 합치는 오류도 생깁니다. 수집 중 W-207과 W-305의 ‘현장 밸브’를 같은 노드로 합쳐 버리면, 이후 질의에서 작업 번호를 정확히 지정해도 한 노드에 두 장비의 변경 이력이 붙습니다. 질문 시점의 검색보다 앞선 **지식 구축** 단계의 문제입니다. 문서별 부품 식별자를 보존하고, 이름이 같을 때 장비·부품표·원문 위치를 함께 대조해야 합니다.

## 어느 관계를 얼마나 확장할지 정합니다

노드 하나에서 붙어 있는 관계를 전부 따라가면, 처음엔 관계가 몇 개 없어 보여도 금세 상관없는 기록에 닿습니다. 이 예에서 `CR-119 → 한빛정밀 ← CR-121`을 따라가면 SE-077의 변경 건에 닿습니다. 승인 경로는 `CR-119 → 김하늘`이고 이미 충분합니다. 공급사를 매개로 모든 변경 건을 가져오면 이별도 함께 새로운 후보가 됩니다. 1,000개의 부품을 공급하는 업체라면 한 번의 이웃 확장이 1,000건으로 늘어날 수 있습니다.

**탐색**(traversal)은 시작 노드에서 연결을 따라 다음 노드로 이동합니다. 어떤 시작점에서 어떤 종류와 방향의 관계를 몇 홉까지 허용할지 정할 수 있습니다. 이 질문에는 `작업 → 교체 부품 → 변경 건 → 승인자`라는 세 홉, 그리고 같은 변경 건에서 공급사로 가는 가지 하나면 충분합니다. 범용 검색이라면 여러 경로를 후보로 가져온 뒤 관계 종류·날짜·업무 영역으로 먼저 제외하고, 남은 후보를 질문의 표현이나 출처의 신뢰도로 정렬할 수 있습니다. 조건 충족 여부와 순위 점수는 다릅니다. 4월 10일에 만료된 CR-106은 문장 유사도가 높아도 ‘현재’ 답변 근거에 들어가지 않습니다.

날짜 계산에서 시작일은 포함하고 종료일은 제외합니다. `start ≤ 기준일 < end`에서 부등호 `≤`는 같은 날을 포함하고, `<`는 종료일과 같은 날을 제외한다는 뜻입니다. 종료일이 기록되지 않은 최신 행은 이 사례에서 ‘현재 대장에 종료일이 설정되어 있지 않다’는 뜻입니다. 이후에도 유효하다고 보증하려면 최신 대장과 검토가 필요합니다. 질문이 ‘교체 당시에 누가 승인했던 공급사가 적용 중이었나’로 바뀌면 기준일이 3월 20일이므로 CR-106, 세림밸브, 박정우가 남습니다. 날짜를 먼저 정하고 동일한 경로 조건을 적용합니다.

### 원문을 회수해 생성 입력을 만듭니다

관계마다 원문 조각 ID를 붙여 둡니다. `W-207 → VL-042`의 출처는 G01, CR-119가 VL-042에 적용되고 한빛정밀이 공급사라고 한 출처는 G03, 김하늘의 승인 출처는 G04입니다. G02는 이름을 설명할 때 필요한 부품표입니다. **컨텍스트**는 검색 후보 가운데 답변 모델에 실제로 전달한 자료입니다. 이 수업에서는 아래 네 줄을 기본 컨텍스트로 삼습니다. G03을 두 관계가 참조하므로 원문은 한 번만 넣습니다.

| 모델 입력의 역할 | 전달하는 내용 |
| --- | --- |
| 질문 범위 | 작업 W-207, 기준 2026-04-10, 현재 적용 중인 변경 건 |
| 개체 확인 | G01과 G02로 현장 밸브가 VL-042임을 확인 |
| 현재 공급 조건 | G03으로 CR-119가 4월 1일부터 적용되고 지정 공급사가 한빛정밀임을 확인 |
| 승인 조건 | G04로 CR-119의 최종 승인자가 김하늘임을 확인 |

교육용 답변은 다음과 같습니다. “W-207에서 교체한 현장 밸브는 VL-042입니다 [G01, G02]. 2026년 4월 10일 기준, 해당 부품의 지정 공급사는 CR-119에 따라 한빛정밀이며 [G03], 이 변경 건의 최종 승인자는 김하늘입니다 [G04].” 이 사례에서는 대괄호 안의 ID를 위 표의 위치·텍스트와 대조합니다. 실제 응용에서는 그 ID로 원문 페이지·행을 열 수 있게 구성합니다. ‘교체 작업의 승인자’는 물어본 변경 건의 승인자와 역할이 다르므로 문장에 변경 건 번호를 명시합니다.

승인 원문 G04가 없는데 관계만 들어왔다면, 모델은 두 가지를 구별해야 합니다. 승인 기록에 접근할 수 없는 경우라면 보이는 공급 정보까지만 제시하고 승인자를 단정할 근거가 부족하다고 답합니다. 관계를 생성한 도구가 잘못 기록한 경우라면 원문과 대조할 때 막힙니다. 둘 모두 표면에는 승인자 문장이 없지만, 앞의 경우는 권한·원문 회수 문제이고 뒤의 경우는 데이터 오류입니다.

## 문서에 가까운 질문과 경로에 가까운 질문

앞의 질문을 U13과 같은 Vector RAG 구성으로도 물어볼 수 있습니다. 비교하려면 동일한 G01~G11을 사용할 수 있어야 합니다. 그래프 쪽에만 구조화된 승인 대장을 주면 자료 차이 때문에 생긴 성능을 경로의 이점으로 잘못 읽게 됩니다. 또한 그래프의 기준일 제한을 벡터 쪽에서도 메타데이터나 후속 검사로 적용하고, 원문 네 조각·동일 생성 모델 같은 조건을 맞춥니다.

| 동일 자료에서의 모의 비교 | 네 조각의 선택 | 남는 판단 |
| --- | --- | --- |
| 질문 벡터로 문서 조각을 한 번 고르는 예 | G01, G02, G03, G08 | CR-119의 공급사는 보이지만 G04 승인자가 없습니다. G08은 동일 공급사의 다른 부품입니다. |
| 작업→부품→변경→승인 경로 | G01, G02, G03, G04 | 부품, 현재 변경, 공급사, 승인자를 함께 확인할 수 있습니다. |
| 첫 검색 결과에서 CR-119를 읽고 다시 검색하는 예 | G01, G02, G03, G04 | 두 번째 검색이 승인 대장의 정확한 번호를 찾으면 같은 답변을 구성할 수 있습니다. |

표의 선택 순서는 합성한 교육 자료입니다. 예를 들어 승인 대장에 “W-207 현장 밸브 VL-042 변경 승인”이라는 문구도 있었다면 단일 벡터 검색에서 G04가 상위에 올 수 있습니다. 문서가 이미 여러 식별자를 함께 전해 주는지, 질의가 앞 단계의 값으로 다음 단계를 찾아야 하는지에 따라 선택할 검색이 달라집니다.

반대로 “현재 PX-47의 E17 복귀 판정은 점검 모드에서 몇 분인가요?”는 U13의 D02a 하나로 답할 수 있습니다. 최신 판본·적용 장비를 먼저 고르고 표의 올바른 행을 찾는 과정이 필요하지만, 승인이나 공급 변경 경로를 추가로 순회할 이유는 없습니다. 어떤 방법이 도움이 되는지를 결정하려면, 질문이 요구하는 근거 구조를 함께 보아야 합니다.

## 설명 연습

1. “2026-03-20에 W-207 현장 밸브에 적용되던 지정 공급사와 승인자는?”라는 질문을 위 경로로 풀어 보세요. 바뀌는 조건과 필요한 원문을 말해 보세요.
2. 한빛정밀 노드가 포함된 모든 이웃을 답변에 넣으면 어떤 잘못이 생길 수 있나요? `CR-121 → 이별`의 연결이 맞더라도 왜 현재 질문에선 고르지 않는지 설명해 보세요.
3. 비품 수리 접수 R-001에 “작업대 램프”라고만 적혀 있고, 별관과 본관 부품표에 모두 같은 별칭이 있습니다. 출발할 노드를 고르는 데 필요한 추가 조건을 예와 함께 설명해 보세요.

### 해설

1. 장비·작업·별칭 조건은 그대로입니다. 기준일만 3월 20일로 바뀌면 CR-119는 아직 시행 전이고 CR-106은 유효합니다. W-207과 VL-042는 G01과 G02, 공급사 세림밸브와 기간은 G05, 승인자 박정우는 G06에서 확인합니다.
2. CR-121은 SE-077에 대한 변경 건입니다. 같은 공급사를 쓰더라도 승인 기록은 공급사 전체의 속성이 아니라 개별 변경 건의 관계입니다. 연결이 의미하는 바가 질문에서 요구하는 조건과 일치하는지 검사해야 합니다.
3. 접수 기록의 건물·작업대 ID, 교체 부품의 자산 코드처럼 후보를 구별하는 정보가 필요합니다. 접수에서 실제 교체 부품으로 가는 관계가 하나라면 그 관계와 별칭 후보 집합을 교차할 수 있습니다. 기록이 없거나 둘 다 남으면 출발점을 확정하지 않고 후보와 확인할 항목을 제시합니다.
