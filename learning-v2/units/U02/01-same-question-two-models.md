# 같은 질문을 표와 그래프로 따라가기

장비 관리자가 ‘작성자의 소속 팀장이 승인한 문서는 무엇인가요?’라고 묻습니다. 직원·팀·문서·승인의 연결을 따라가야 하는 질문입니다. 관계형 DB에서도 답할 수 있고 그래프 모델로도 표현할 수 있습니다. 이번에는 동일한 작은 자료로 두 표현의 차이를 읽어 보겠습니다. 그래프 DB가 빠르다는 결론을 미리 정하는 실험은 아닙니다.

## 1. 먼저 같은 데이터를 고정합니다

직원은 민수 P1, 지연 P2, 현우 P3입니다. 민수와 지연은 정비팀 T1, 현우는 검사팀 T2에 속합니다. 정비팀장은 지연이고 검사팀장은 현우입니다. 민수는 문서 D1과 D2를 작성했습니다. D1은 지연이 승인했고, D2는 현우가 승인했습니다.

| Person.id | 이름 | team_id |
|---|---|---|
| P1 | 민수 | T1 |
| P2 | 지연 | T1 |
| P3 | 현우 | T2 |

| Team.id | 팀 이름 | manager_id |
|---|---|---|
| T1 | 정비팀 | P2 |
| T2 | 검사팀 | P3 |

| Document.id | author_id | approver_id |
|---|---|---|
| D1 | P1 | P2 |
| D2 | P1 | P3 |

각 표의 id는 행을 구별하는 기본키로 사용합니다. team_id·manager_id·author_id·approver_id는 다른 표의 식별자를 참조합니다. 데이터베이스에 외래키 제약을 선언하면 존재하지 않는 대상 ID의 참조 등을 검사할 수 있습니다. 실제 부서 정책상 누가 누구를 승인할 수 있는지까지 자동 결정하는 것은 별도의 규칙 문제입니다.

‘작성자의 팀장이 승인한 문서’를 찾아 보면 D1이 남아야 합니다. D2의 승인자는 작성자 민수의 팀장 지연이 아니기 때문입니다. 승인 자체가 유효하지 않다고 단정하는 것은 아닙니다. 질문의 조건에 해당하지 않을 뿐입니다.

## 2. JOIN은 관계를 따라가는 한 방법입니다

관계형 표현에서는 참조 값이 같은 행들을 JOIN으로 연결합니다.

```sql
SELECT d.id, author.name, manager.name
FROM Document AS d
JOIN Person AS author ON author.id = d.author_id
JOIN Team AS t ON t.id = author.team_id
JOIN Person AS manager ON manager.id = t.manager_id
WHERE d.approver_id = manager.id;
```

SQL에 익숙하다면 문법을 이미 알고 있을 수 있습니다. 여기서는 어떤 연결을 했는지 읽는 데 집중하세요. Document에서 작성자를 찾고, 작성자의 팀을 찾고, 그 팀의 팀장을 찾습니다. 마지막에 문서 승인자와 팀장 ID를 비교합니다.

| 중간 단계 | D1 | D2 |
|---|---|---|
| 작성자 | P1 민수 | P1 민수 |
| 작성자 팀 | T1 정비팀 | T1 정비팀 |
| 그 팀의 팀장 | P2 지연 | P2 지연 |
| 문서 승인자 | P2 지연 | P3 현우 |
| 질문 조건 만족 | 예 | 아니요 |

이 중간 표는 논리적으로 결과를 이해하기 위한 전개입니다. 실제 DB가 반드시 표의 순서대로 한 행씩 실행한다는 뜻은 아닙니다. 옵티마이저가 통계와 인덱스 등을 바탕으로 물리적인 실행 방법을 선택할 수 있습니다.

RDB에서 관계를 다룰 수 없다는 설명이 왜 틀렸는지 이제 분명합니다. 참조 키와 JOIN을 통해 연결된 질문을 표현할 수 있습니다. 다대다 관계가 생기면 별도의 관계 테이블을 두는 것도 익숙한 방법입니다.

## 3. 같은 연결을 그래프 패턴으로 표현합니다

속성 그래프에서는 사람·팀·문서를 노드로, 연결을 관계로 표현할 수 있습니다. 이번 예의 관계 방향을 다음처럼 정하겠습니다.

```text
민수(P1) ─MEMBER_OF→ 정비팀(T1) ─MANAGED_BY→ 지연(P2)
민수(P1) ─AUTHORED→ D1 ─APPROVED_BY→ 지연(P2)
민수(P1) ─AUTHORED→ D2 ─APPROVED_BY→ 현우(P3)
```

이 그림은 전체 자료 중 이번 질문에 관련된 연결만 뽑은 부분 그래프입니다. 전체 그래프에는 지연의 정비팀 소속, 현우의 검사팀 소속과 검사팀 관리 관계도 있습니다. 생략된 세 관계가 없어졌다는 뜻은 아닙니다.

`MEMBER_OF`는 소속, `MANAGED_BY`는 팀의 관리자, `AUTHORED`는 문서 작성, `APPROVED_BY`는 승인자를 가리킵니다. 이 이름은 예제를 위해 정했습니다. 영어 이름 자체가 업무 의미를 자동 보장하지 않으므로 관계를 설계할 때 정의와 방향을 문서화해야 합니다.

Neo4j의 Cypher로 위 질문을 적으면 다음처럼 읽을 수 있습니다. 아직 모든 문법을 외울 필요는 없습니다.

```cypher
MATCH (author:Person)-[:AUTHORED]->(d:Document),
      (author)-[:MEMBER_OF]->(t:Team)-[:MANAGED_BY]->(manager:Person),
      (d)-[:APPROVED_BY]->(manager)
RETURN d.id, author.name, manager.name
```

괄호는 노드, 대괄호와 화살표는 타입과 방향을 가진 관계입니다. `author`, `d`, `t`, `manager`는 찾아낸 대상을 가리키는 변수입니다. 같은 `manager`가 팀장 위치와 승인자 위치에 반복되므로 두 위치가 같은 노드를 가리켜야 합니다. 그래프 패턴이 질문의 연결 구조를 직접 드러냅니다. 예상 결과는 D1·민수·지연입니다. 이 Cypher는 엔진을 실행하지 않은 읽기용 예제입니다. [Neo4j graph concepts](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/)

이 표현에서는 관계 테이블을 별도로 보지 않아도 관계를 질의의 선으로 읽을 수 있습니다. 그러나 장점은 단순히 SQL보다 코드가 짧다는 데 있지 않습니다. 여러 종류의 연결을 반복해서 탐색하는 질문에서 데이터 모델과 질의의 표현이 얼마나 자연스러운지 살피는 것입니다.

## 4. 데이터 모델·질의 언어·저장 엔진을 나눠 생각하기

세 가지를 구분하면 제품 비교가 쉬워집니다.

**데이터 모델**은 데이터를 어떤 요소로 나타내는가입니다. 위에서는 표와 참조 키, 또는 노드와 타입 있는 관계를 사용했습니다. **질의 언어**는 그 데이터에 무엇을 요청할지 적는 방법입니다. 여기서는 SQL과 Cypher입니다. **저장·실행 엔진**은 디스크·메모리·색인·실행 계획을 사용해 실제 요청을 처리합니다.

그래프 그림을 그렸다고 그래프 DB를 사용한 것은 아닙니다. 관계형 테이블을 읽어 화면에 노드·선을 그릴 수도 있습니다. 반대로 그래프 DB도 시작 노드를 찾기 위한 인덱스와 실행 계획이 중요합니다. Neo4j에서 `EXPLAIN`은 실행하지 않고 계획과 추정치를 보여주고, `PROFILE`은 실제 질의를 실행하며 측정 정보를 제공합니다. 같은 논리 패턴이라도 출발점과 데이터 분포가 달라지면 처리량이 달라질 수 있습니다. [Neo4j query plans](https://neo4j.com/docs/cypher-manual/current/planning-and-tuning/execution-plans/)

또한 RDF와 속성 그래프는 서로 다른 그래프 데이터 모델입니다. RDF를 저장하는 제품과 Neo4j가 같은 노드·관계 규칙이나 같은 질의 언어를 쓴다고 가정하면 안 됩니다. 이후 단원에서 두 모델을 같은 사건 자료로 비교합니다.

## 5. 연결이 많을수록 항상 빠를까요

직원 한 명의 팀장 한 명을 찾는 것은 작은 범위입니다. 반면 ‘모든 연결을 길이 6까지 따라가 모든 경로를 나열하라’는 질문은 그래프 DB에서도 매우 커질 수 있습니다. 시작점 하나에서 매 단계 정확히 10개를 선택할 수 있다고 단순 가정하면, 겹침과 가지치기를 무시한 정확히 길이 6의 선택 조합은 10의 6제곱입니다. 길이 1부터 6까지를 모두 세면 10 + 10² + … + 10⁶입니다. 이것은 실제 DB 실행량의 측정치가 아니라 분기 확장의 직관을 위한 계산입니다.

이 때문에 시작점을 좁히고, 관계 타입과 방향을 제한하고, 중간 조건과 경로 범위를 정하는 일이 중요합니다. 관계 참조를 찾는 방식이 효율적이어도 결과 후보 자체가 폭발하면 전체 작업이 저렴해지지 않습니다.

RDB도 재귀 질의를 통해 계층과 반복 연결을 탐색할 수 있습니다. PostgreSQL의 `WITH RECURSIVE`는 앞 단계 결과를 다음 반복의 입력으로 사용해 더 깊은 부분을 찾게 합니다. 예를 들어 제품의 직접 부품을 찾고 그 부품의 하위 부품을 계속 확장하는 표현이 가능합니다. 순환이 있는 데이터라면 종료와 중복·경로 처리도 고려해야 합니다. [PostgreSQL 재귀 질의 설명](https://www.postgresql.org/docs/18/queries-with.html#QUERIES-WITH-RECURSIVE)

따라서 ‘관계가 많다’는 한 문장보다 질문의 모양을 구체적으로 적어야 합니다. 고정된 몇 단계 조인인지, 길이가 달라지는 경로인지, 대규모 집계인지, 작은 시작점에서 국소 탐색하는지 살펴보세요. 비교 실험은 같은 데이터·정답·인덱스·하드웨어·캐시 조건과 실제 쿼리를 포함해야 합니다. 이번 예제로 성능 우열을 결론 내릴 수는 없습니다.

## 6. 선택을 설명하는 연습

**질문:** 문서별 작성자와 승인자만 매달 집계한다면 바로 그래프 DB로 옮겨야 할까요?

**해설:** 기존 표와 JOIN으로 요구를 충족한다면 이 질문만으로 이전의 이득은 입증되지 않습니다. 가변 길이의 연결 탐색, 여러 관계를 조합한 질의, 모델 확장의 필요 등을 함께 보아야 합니다. 이전·동기화·운영 비용도 비교해야 합니다.

**질문:** 문서에 승인자가 두 명일 수 있게 됐다면 어떻게 바꿀까요?

**해설:** 관계형 모델에서는 문서-승인자 관계 테이블로 다대다 연결을 표현할 수 있습니다. 속성 그래프에서는 승인자마다 APPROVED_BY 관계를 둘 수 있습니다. 승인 시각·단계·결과가 필요하면 관계에 속성을 두거나 승인을 별도 사건으로 모델링할 수도 있습니다. 어느 모델에서도 ‘승인 한 건’의 의미를 먼저 정해야 합니다.

**질문:** 한 질의에서 JOIN이 세 개였다는 사실만으로 느릴 것이라고 판단할 수 있나요?

**해설:** 행 수·선택도·인덱스·실행 계획과 실제 측정을 보아야 합니다. 그래프 패턴도 경로 후보 수와 실행 계획 영향을 받습니다. 표기된 연결의 수와 실제 처리 비용을 같은 것으로 읽지 않아야 합니다.
