# C7. Property Graph — 대상과 연결에 속성을 붙이기

**목표:** Property Graph를 읽고 RDF와 비교하며 사건·관계 속성·변환의 선택을 설명한다.

<a id="c7-01"></a>
## 1. 무엇이며 어떤 필요에 맞는가?

Property Graph는 노드와 관계에 속성을 붙여 데이터를 표현하는 그래프 모델 계열이다. 응용 개발에서 대상·관계·값을 직접 다루기 쉽다는 점이 특징이다. 제품별 세부가 다르므로 여기서는 Neo4j의 모델을 구체 기준으로 삼는다.

Neo4j에서는 노드가 여러 라벨을 가질 수 있고, 관계는 시작·끝 노드와 방향, 하나의 관계 타입을 가지며, 노드·관계 모두 key-value 속성을 가질 수 있다. [Neo4j Graph database concepts](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/)

~~~text
(:Equipment {id:"E01", site:"NORTH", serial:"SN101"})
(:Run {id:"RUN002"})-[:USED_EQUIPMENT]->(:Equipment {id:"E01"})
~~~

괄호는 노드, 대괄호는 관계, 중괄호는 속성이다. 이 표현은 뒤의 Cypher를 읽는 출발점이 된다. 라벨 Equipment가 붙었다고 OWL 클래스의 공리·추론이 자동 적용되는 것은 아니다.

<a id="c7-02"></a>
## 2. 값으로 둘까, 노드로 만들까?

일련번호 "SN101"은 단순 조회용 값이라면 속성으로 둘 수 있다. Site가 다른 장비·조직·권한과 연결되는 중요한 대상이면 Site 노드로 분리할 수 있다. 둘 중 하나가 언제나 정답은 아니다.

기준은 세 가지다. 그 값이 **독립 식별·갱신**되어야 하는가, **여러 대상이 공유하는 관계 중심점**인가, **별도 속성과 이력**을 가지는가? 답이 그렇다면 노드를 검토한다.

예를 들어 NORTH를 문자열로만 저장하면 간단하다. 하지만 사이트의 관리자·승인 절차·지역 정보를 연결하려면 Site 노드가 자연스러울 수 있다. 반대로 모든 상태 코드 한 개까지 노드로 만들면 그래프가 불필요하게 복잡해질 수 있다. 이 기준은 교재의 모델링 지침이다.

<a id="c7-03"></a>
## 3. 관계 속성과 사건 노드는 어떻게 고르는가?

~~~text
L02 -[INSPECTED_ON {runId:"RUN002", time:"..."}]-> E01
~~~

이 구조도 작업을 표현할 수 있다. 그러나 작업에 문서·사람·관측값·정정 이력을 더 연결해야 하면 사건 노드가 편할 수 있다.

~~~text
RUN002 → L02
RUN002 → E01
RUN002 → D02
RUN002 → OBS002
~~~

관계 속성은 두 대상 사이 연결의 부가값을 담기 쉽다. 사건 노드는 그 사건을 다른 관계의 대상으로 삼기 쉽다. 하나의 작업에 참가자가 많고 장기 이력을 관리한다면 사건을 독립 대상으로 모델링할 이유가 커진다. RDF에서도 같은 업무 질문으로 사건 모델을 선택할 수 있다.

<a id="c7-04"></a>
## 4. RDF Graph와 나란히 비교하기

| 비교축 | RDF 1.1 기본 모델 | Neo4j Property Graph 기준 |
|---|---|---|
| 핵심 단위 | subject-predicate-object triple | 노드·관계·속성 |
| 대상 이름 | IRI·blank node | 노드와 응용 식별 속성 |
| 종류 표현 | rdf:type 등 어휘 | 라벨 |
| 관계의 부가 정보 | 사건·주장·별도 맥락 모델 등 | 관계 속성 사용 가능 |
| 질의 생태계 | SPARQL | Cypher |
| 의미 공유 | 표준 어휘·IRI·의미론 활용 | 응용 모델·규약·확장에 의존 |

이는 “RDF는 의미가 있고 Property Graph는 의미가 없다”는 표가 아니다. Property Graph에서도 관계 정의·ID·검증 정책을 설계해 KG를 구현할 수 있다. RDF에서도 의미 없는 relatedTo만 잔뜩 쓰면 업무 활용이 어렵다.

표현 모델과 의미 품질을 분리해서 비교해야 한다. 또한 RDF 저장소가 항상 느리거나 Property Graph가 항상 빠르다는 주장은 데이터·엔진·질의 측정 없이 할 수 없다.

<a id="c7-05"></a>
## 5. 심화: 두 모델을 변환할 때 무엇이 사라질 수 있나?

RDF의 IRI를 짧은 이름으로 바꾸면 namespace 충돌이 생길 수 있다. 언어 태그·datatype을 평범한 문자열로 바꾸면 값의 의미가 손실될 수 있다. named graph를 버리면 원천 분리가 사라질 수 있다.

반대 방향에서는 같은 두 노드 사이의 여러 관계 인스턴스가 동일 triple 하나로 합쳐질 위험이 있다. 작업별 관계 ID나 사건 노드를 두어 다중성을 보존해야 한다. 관계 속성의 출처도 별도 표현이 필요하다.

이 내용은 두 모델의 차이에서 도출한 변환 검토 항목이다. 실제 변환 도구가 항상 손실을 낸다는 주장은 아니다. 검증할 것은 파일 변환 성공뿐 아니라 **대표 질의의 답·중복성·맥락이 유지되는가**다.

<a id="c7-06"></a>
## 6. 발표에서의 비교와 확인 문제

**꼭 설명:** 라벨·노드·관계 타입·속성, 값과 노드 선택, 사건 노드, RDF와의 차이. **생략 가능:** 모든 엔진별 속성 타입·변환 플러그인 옵션.

**확인 질문:** "NORTH"는 반드시 노드여야 하는가? 같은 로트와 장비 사이의 두 작업을 RDF triple 하나로 변환하면 무엇이 사라질 수 있나?

### 해설

사이트의 역할과 조회 요구에 따라 속성 또는 노드를 선택한다. 두 작업을 구별하는 ID·시각·사용 문서를 보존하지 않으면 작업 두 번이 한 관계로 축약되어 이력이 손실된다.
