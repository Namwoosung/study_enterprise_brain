# C4. Semantic Web과 W3C — 문서의 웹에서 데이터의 웹으로

**목표:** Semantic Web의 목적과 Linked Data 원칙을 이해하고 W3C 규격의 역할·지위를 구별한다.

<a id="c4-01"></a>
## 1. 왜 Semantic Web이라는 생각이 나왔나?

웹 페이지는 사람이 읽기 좋지만, 프로그램이 서로 다른 사이트의 “저자·기관·제품·날짜”를 일관되게 결합하기는 어렵다. Semantic Web은 데이터의 의미와 연결을 기계가 다룰 수 있는 방식으로 표현해, 응용·조직 경계를 넘어 공유·재사용하려는 비전과 기술 생태계다. W3C의 과거 활동 페이지는 이 목표를 설명한다. 해당 페이지는 2013년에 동결된 역사 자료다. [W3C Semantic Web Activity](https://www.w3.org/2001/sw/)

“기계가 의미를 안다”는 말을 인간처럼 이해한다는 뜻으로 과장하면 안 된다. 예를 들어 장비 ID와 문서 ID를 명확히 구별하고, usedDocument가 무엇인지 약속하면 프로그램이 그 약속에 따라 결합·질의·추론할 수 있다는 의미다.

LLM 이전부터 존재한 지식 표현·웹 데이터 상호운용 문제다. Semantic Web은 현재의 임베딩 기반 **semantic search**와 같은 말이 아니다. 전자는 공유 데이터 의미·표준·연결을, 후자는 흔히 표현의 유사성을 이용한 검색을 가리킨다.

<a id="c4-02"></a>
## 2. Linked Data는 어떻게 연결을 가능하게 하는가?

Tim Berners-Lee의 Linked Data 설계 글은 대상을 URI로 이름 붙이고, HTTP URI를 통해 유용한 정보를 제공하며, 다른 대상에 대한 링크를 포함하는 원칙을 제시한다. 이 글 자체는 W3C Recommendation이 아니라 저자의 설계 견해로 표시되어 있다. [Linked Data Design Issues](https://www.w3.org/DesignIssues/LinkedData.html)

기업 내부의 예를 생각해 보자. 시스템 A의 "E01"과 시스템 B의 "E01"은 우연히 같은 문자열일 수 있다. 식별자의 관리 범위를 명확히 하면 충돌을 줄일 수 있다. 다만 IRI를 붙였다고 현실의 동일성이 해결되지는 않는다. 두 IRI가 같은 장비인지 판단하는 작업은 여전히 필요하다.

Linked Data는 무조건 공개 데이터를 뜻하지 않는다. 내부 접근 통제 아래에서도 같은 원칙을 적용할 수 있다. 공개 여부, 연결 가능한 식별자, 라이선스·접근 권한은 서로 다른 문제다.

<a id="c4-03"></a>
## 3. W3C는 무엇을 하는가?

W3C는 웹 기술의 상호운용을 위한 표준을 개발하는 조직이다. RDF나 OWL은 W3C가 제공하는 DB 서비스가 아니라, 서로 다른 도구가 공통으로 해석할 수 있도록 정의한 규격이다. [W3C 표준 안내](https://www.w3.org/standards/)

규격 문서의 상태를 읽는 습관이 필요하다. Recommendation, Working Draft, Working Group Note는 같은 지위가 아니다. 입문 설명 문서와 규범 문서도 역할이 다를 수 있다. 날짜가 오래되었다고 잘못된 기술이라고 판단하거나, 최신 초안이라고 이미 모든 제품이 지원한다고 판단하지 않는다.

이 교재의 재현 기준은 안정적으로 참조할 수 있는 RDF 1.1, RDFS 1.1, OWL 2, SPARQL 1.1, SHACL 2017이다. 이는 최신 후속 버전의 존재를 부정하는 말이 아니다. 제품 적용 시에는 필요한 기능의 규격 지위와 실제 엔진 지원 버전을 별도로 확인한다.

<a id="c4-04"></a>
## 4. 표준들의 역할을 한 번에 구별하기

| 이름 | 맡는 역할 | 이번 사례에서의 질문 |
|---|---|---|
| RDF | 진술을 그래프로 표현하는 데이터 모델 | RUN002가 E01을 사용했다는 말을 어떻게 적나? |
| Turtle·JSON-LD 등 | 데이터를 기록·교환하는 구문 | 파일에서 어떻게 쓸까? |
| RDFS | 기본 클래스·속성·계층의 의미 | 검사장비는 장비 종류인가? |
| OWL | 더 풍부한 공리와 논리적 의미 | 분류·동일성·조건에서 무엇이 따라오나? |
| SPARQL | RDF 데이터 질의·관련 표준군 | 조건에 맞는 장비·문서를 어떻게 찾나? |
| SHACL | RDF 그래프가 조건을 만족하는지 검사 | 필요한 문서 관계가 빠졌나? |
| PROV-O | 생성·파생·책임의 출처 모델 | 이 주장은 어떤 자료·활동에서 나왔나? |

이 표는 단일 설치 스택을 강요하지 않는다. RDF를 쓰면서 OWL 추론을 전혀 사용하지 않을 수 있다. Property Graph 시스템에서 별도 규칙과 검증으로 비슷한 업무 목표를 구현할 수도 있다. 선택 시에는 **필요한 기능과 공유 계약**을 먼저 명확히 한다.

표준 원문은 [RDF Concepts](https://www.w3.org/TR/rdf11-concepts/), [OWL Overview](https://www.w3.org/TR/2012/REC-owl2-overview-20121211/), [SPARQL Overview](https://www.w3.org/TR/sparql11-overview/)에서 역할을 대조할 수 있다.

<a id="c4-05"></a>
## 5. 심화: 표준화해도 통합이 자동으로 되지 않는 이유

두 회사가 모두 RDF를 쓴다고 같은 뜻의 용어를 쓰지는 않는다. 한쪽의 Equipment가 센서까지 포함하고 다른 쪽은 설비만 포함하면 어휘 대응을 검토해야 한다. 같은 구문, 같은 의미, 같은 현실 대상은 각각 다른 수준의 일치다.

또 데이터에 문장이 쓰였다는 것과 신뢰할 수 있다는 것은 다르다. 표준은 진술의 형식·해석을 제공하지만 작성자가 정확한지는 별도 문제다. 공개 웹에서 가져온 장비 설명을 내부 승인된 작업 절차와 같은 권위로 취급하지 않는다.

반대로 상호운용을 위해 모든 원천을 먼저 동일 DB로 옮겨야 하는 것은 아니다. 어휘와 식별자·매핑을 합의하고 가상 질의나 교환 파일로 연결할 수 있다. 이 접근의 장점과 비용은 원천 안정성·성능·권한 조건에 따라 평가한다.

<a id="c4-06"></a>
## 6. 발표에서 사용할 설명과 점검

**꼭 설명:** Semantic Web과 semantic search의 차이, W3C와 제품의 차이, RDF·OWL·SPARQL·SHACL 역할, 표준과 데이터 사실성의 차이. **생략 가능:** 모든 역사적 웹 표준, 모든 직렬화 문법, 표준화 절차의 세부 위원회 구조.

**확인 질문:** RDF 문서를 사용하면 데이터는 공개되는가? OWL을 도입하면 필수값 누락 검사가 자동으로 되는가? W3C 규격 준수는 내용의 진실성을 보장하는가?

### 해설

공개 여부는 배포·권한 정책에 달려 있다. OWL의 논리적 의미와 데이터 제출 검사는 별도이며 SHACL 같은 검증 수단을 목적에 맞게 둔다. 규격 준수는 데이터의 표현·처리 계약과 관련되며 현실의 정확성을 보증하지 않는다.
