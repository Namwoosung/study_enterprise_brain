# C10. Auto ontology — 무엇을 자동으로 만들고 무엇을 검토하는가?

**목표:** 자동 ontology 작업을 분해하고 일반 연구·특정 제품·운영 승인 사이의 차이를 설명한다.

<a id="c10-01"></a>
## 1. 왜 자동화하려 하는가?

수백 개 테이블과 수천 문서에서 용어·관계·매핑을 모두 사람이 처음부터 정리하면 비용이 크다. 원천 스키마와 업무 용어가 계속 바뀌므로 한 번 작성하고 끝낼 수도 없다. 자동화의 목적은 반복적인 후보 발굴·매핑·검사 부담을 줄이는 데 있다.

Auto ontology라는 말은 단일 표준 알고리즘의 이름으로 전제하지 않는다. ontology learning이라는 연구 과제, LLM 기반 후보 생성 파이프라인, 특정 제품 이름이 섞여 쓰일 수 있다. “자동 생성”이라는 말 뒤에 **어떤 입력에서 무엇을 출력하는지**를 확인한다.

LLMs4OL은 용어 유형 분류, 분류체계 발견, 비계층 관계 추출을 나누어 평가한다. 이처럼 작업 단위가 나뉜다는 점이 중요하며, 몇 가지 과제의 성능이 곧 전사 ontology의 자동 완성을 의미하지 않는다. [LLMs4OL, ISWC 2023](https://arxiv.org/abs/2307.16648)

<a id="c10-02"></a>
## 2. 자동화할 작업을 분해하기

| 작업 | 입력 → 출력 | 다른 작업과의 차이 |
|---|---|---|
| 용어·타입 후보 | 문서 표현 → 클래스 후보 | 실제 개체를 등록하는 것과 다름 |
| 계층 학습 | 종류들 → 상하위 관계 | partOf와 subClassOf를 구분 |
| 관계 학습 | 문장·스키마 → 관계 의미 | 문자열 동시 출현만으로 확정 불가 |
| Ontology alignment | 두 모델 → 대응 후보 | 모델 사이 의미 대응 |
| Population | 정의된 모델 + 기록 → 개체·주장 | ontology 설계 자체와 다름 |
| Entity resolution | 여러 기록 → 같은 현실 대상 | 클래스 계층 생성과 다름 |
| Mapping | 원천 필드 → 업무 개념·속성 | 구조와 의미를 연결 |

이 표는 학습을 위한 작업 분해다. 한 제품이 모든 작업을 지원한다고 가정하지 않는다. “ontology를 추출했다”는 보고에서 실제로 클래스 목록만 만든 것인지, 인스턴스까지 만들었는지, 관계 정의도 검토했는지 질문해야 한다.

<a id="c10-03"></a>
## 3. 정형 자료와 비정형 자료의 출발점

정형 데이터는 컬럼명·키·외래키·값 분포·기존 SQL이 단서다. eqp_id가 장비 ID 후보라고 추정하고 실제 참조값을 검사할 수 있다. 그러나 컬럼명이 flag라고 의미가 명확한 것은 아니다. 코드 사전과 업무 담당자 확인이 필요하다.

비정형 문서는 제목·표·문장·인용·조건절이 단서다. “센서 확인이 필요하다는 의견”에서 센서, 점검 제안, 발언자, 불확실성을 분리한다. 관계만 추출하고 “의견”이라는 성격을 버리면 원문보다 강한 주장을 만든다.

학습용 후보 파이프라인은 원천 보존 → 후보 추출 → 허용 모델 대응 → 동일성 검토 → 구조·근거 검사 → 위험 기반 검토 → 발행이다. 사람과 프로그램의 분담은 이 단계별 실패 비용으로 정한다. 모든 항목을 사람이 봐야 한다거나 LLM 점수만 높으면 통과시켜야 한다고 미리 확정하지 않는다.

<a id="c10-04"></a>
## 4. NVIDIA Auto Ontology는 구체적으로 무엇인가?

2026-11-18 확인한 공식 저장소는 업무 개념을 데이터에 연결하는 의미 계층을 설명한다. 개념, 컬럼 매핑, 테이블 관계, SQL 지표, 계보, 인증을 구분하며, 원천 DB에서 초안을 만들고 사람이 검토·인증하는 흐름을 제시한다. 저장은 Postgres와 pgvector를 사용한다고 설명한다. [NVIDIA 공식 README의 How it works](https://github.com/NVIDIA/auto-ontology#how-it-works)

따라서 이 제품의 ontology라는 단어를 “OWL 파일과 완전한 OWL 추론 엔진”으로 자동 번역하면 안 된다. 비즈니스 의미·질의 경로·지표 계산을 관리하는 범위와 W3C의 논리 언어 범위를 대조해야 한다.

여기서는 제품의 목적·입출력·사람 검토 역할을 학습한다. 설치하거나 실제 데이터 정확도를 측정한 것은 아니다. README의 개선 효과 주장을 본 반도체 사례의 실측 성능으로 인용하지 않는다. 제품 문서는 변경 가능하므로 구현 시 커밋과 의존 버전을 고정한다.

<a id="c10-05"></a>
## 5. 심화: 좋은 JSON이 나와도 의미는 틀릴 수 있다

허용 클래스가 Equipment·Run·Document로 제한되어 있으면 엉뚱한 타입 생성을 줄일 수 있다. 그러나 E02를 E01로 연결하거나, usedDocument 방향을 뒤집거나, 가설을 확정 원인으로 바꾸는 오류는 남는다.

따라서 구조 검사와 의미 평가를 분리한다. 구조 검사는 필드·타입·관계 범위를 본다. 근거 검사는 원문이 그 주장을 실제 지지하는지 본다. 모델 평가는 대표 질문이 풀리는지, 금지된 결론이 나오지 않는지 본다. 모두 같은 “정확도” 숫자로 뭉치지 않는다.

교재의 합성 평가 예를 보자. 정답 관계 20개 중 16개를 찾고 잘못된 관계 4개도 출력하면 precision=16/20=0.8, recall=16/20=0.8이다. 같은 숫자라도 누락과 오추출은 다르게 고쳐야 한다. 장비 연결 오류와 사소한 라벨 표기 차이는 업무 비용도 다르다.

<a id="c10-06"></a>
## 6. 심화: 자동화의 경계는 평가와 변경 관리로 정한다

검토 정답셋에는 흔한 정상 문서뿐 아니라 별칭 충돌, 개정본, 부정 문장, 가설, 표 병합 셀, 원인 미확정을 포함한다. 같은 문서의 개정본이 학습과 평가에 나뉘어 들어가면 새로운 문서에 대한 성능을 과대평가할 수 있다.

모델 변경 후보는 “새 클래스 30개 생성” 대신 정의·예시·반례·기존 매핑 영향·대표 질의 변화와 함께 검토한다. 승인된 모델과 후보 모델을 버전으로 구분한다. 재처리 시 source version·모델 version·추출 설정을 기록해 왜 결과가 달라졌는지 추적한다.

자동 수용 비율만 높이는 것은 목표가 아니다. 100개 중 90개를 수용했고 수용분에 오류가 2개라면 coverage는 90%, 수용분 오류율은 2/90 약 2.22%다. 전부 보류하면 coverage는 0이고 수용분 오류율은 정의할 수 없다. 이 계산은 합성 예이며 모델 confidence의 실제 보정 성능을 뜻하지 않는다.

<a id="c10-07"></a>
## 7. 발표 수준과 확인 문제

**꼭 설명:** learning·population·alignment·resolution·mapping의 구분, 정형·비정형 단서, 후보와 승인 모델, 의미 평가. **생략 가능:** NVIDIA 설치 절차, 모든 프롬프트·군집 모델의 구현 세부.

**확인 질문:** 사람이 설계한 ontology가 있으면 추출 결과를 전부 자동 승인해도 되는가? 자동 ontology 제품이 그래프 기반이면 반드시 그래프 DB에 저장하는가?

### 해설

허용 구조는 오류 종류 일부를 제한하지만 근거·동일성·시점 오류를 제거하지 않는다. 그래프라는 논리적 구조와 물리 저장 제품은 다르다. NVIDIA README의 Postgres·pgvector 사용례가 이를 구별하는 데 도움이 된다.
