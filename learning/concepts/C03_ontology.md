# C3. Ontology — 공통 의미를 어떻게 설계하는가?

**목표:** ontology의 구성과 필요성을 이해하고 용어집·분류체계·스키마·공리의 차이를 판단한다.

<a id="c3-01"></a>
## 1. Ontology가 해결하려는 문제

두 개발팀이 JSON에 tool이라는 필드를 만들었다고 같은 뜻으로 통합되지는 않는다. 한쪽은 설비 전체, 다른 쪽은 교체 가능한 센서 부품을 뜻할 수 있다. 구조가 맞아도 해석이 어긋나는 것이다.

정보 시스템에서 ontology는 관심 영역의 개념, 속성·관계, 제약 또는 공리 등을 명시해 공유하려는 모델이다. 모든 ontology가 OWL의 풍부한 논리를 사용하지는 않는다. Stanford의 입문 자료는 공통 이해·지식 재사용·가정 명시·영역 지식 분석 등을 구축 이유로 든다. [Ontology Development 101](https://protege.stanford.edu/publications/ontology_development/ontology101-noy-mcguinness.html)

철학의 존재론이라는 단어와 연결되지만, 이번 학습에서는 기업 업무를 기계가 다룰 수 있도록 개념화하는 공학적 용법에 집중한다. “세상의 모든 것을 완벽하게 정의”하는 과제가 아니라 **현재 질문에 필요한 구분을 명시**하는 과제다.

<a id="c3-02"></a>
## 2. 구성 요소를 작은 예로 읽기

| 요소 | 의미 | 합성 예 |
|---|---|---|
| 클래스 | 어떤 종류의 대상인가 | Equipment, InspectionTool |
| 개체 | 구체적으로 무엇인가 | E01 |
| 객체 관계 | 대상과 대상의 연결 | RUN002 usedEquipment E01 |
| 데이터 속성 | 대상과 값의 연결 | E01 serialNumber "SN101" |
| 계층 | 종류 간 포함 관계 | InspectionTool subClassOf Equipment |
| 공리 | 해석에 적용하는 명시적 문장 | 두 클래스의 비양립성 등 |

E01은 Equipment의 **개체**이고 InspectionTool은 Equipment의 **하위 클래스**다. “검사기 1호”는 E01의 별칭일 수 있다. 별칭·개체·클래스를 하나의 종류로 섞으면 모델이 흔들린다.

관계도 구분한다. E05 partOf E01은 부품 관계이고 E05 sameAs E01은 동일 대상이라는 강한 선언이다. “함께 자주 등장한다”는 이유로 sameAs를 생성하면 안 된다. 클래스 포함, 구성, 동일성은 모두 연결처럼 보이지만 뜻이 전혀 다르다.

<a id="c3-03"></a>
## 3. 용어집·taxonomy·schema와 무엇이 다른가?

용어집은 말의 설명을 제공한다. Taxonomy는 개념의 분류 계층을 다룬다. 스키마는 데이터의 구조·타입·제약 등을 정한다. Ontology는 의미와 관계를 공유하는 모델에 초점을 둔다. 실제 시스템에서는 이 역할이 겹치므로 “스키마는 의미가 없고 ontology만 의미가 있다”는 이분법은 부정확하다.

예를 들어 DB 스키마에 status 정수만 정의하면 부족하지만, 코드 사전과 업무 규칙을 붙이면 의미를 상당히 명시할 수 있다. 반대로 클래스 이름만 많이 나열한 ontology 파일은 업무 의미를 충분히 설명하지 못할 수 있다.

통제 어휘·동의어·상하위 개념 관리가 주목적이면 SKOS를 검토할 수 있다. SKOS의 broader 관계를 곧바로 OWL 클래스 포함과 같은 뜻으로 읽지 않는다. [SKOS Primer](https://www.w3.org/TR/skos-primer/)

<a id="c3-04"></a>
## 4. 실제 설계는 질문에서 시작한다

“우리 회사의 ontology를 만들어라”는 범위가 너무 크다. 먼저 답해야 하는 질문을 적는다. 이번 사례의 질문은 “L02가 어떤 작업을 거쳤고 각 작업에서 어떤 문서를 사용했는가?”다. 이 질문으로부터 Lot, Run, Equipment, Document와 사건별 관계가 도출된다.

그다음 가능한 답과 불가능한 답을 대조한다. 작업 ID가 없으면 재작업을 구분할 수 있는가? 문서 ID만 있으면 버전을 구분할 수 있는가? 현장 별칭만 있으면 사이트가 다른 장비를 구분할 수 있는가? 반례가 모델을 구체화한다.

첫 모델이 완벽할 필요는 없다. 기존 어휘 재사용을 검토하고, 샘플 데이터로 질문을 실행하며 반복 수정한다. 이 과정의 출발점은 범위·역량 질문·재사용·반복 개발을 강조하는 [Stanford 가이드](https://protege.stanford.edu/publications/ontology_development/ontology101-noy-mcguinness.html)이며, 여기의 반도체 질문은 교재가 만든 응용이다.

<a id="c3-05"></a>
## 5. 심화: 모델의 강도를 어디까지 높일까?

“검사 작업은 검사장비를 쓴다”는 필요조건과 “검사장비를 쓰는 작업은 모두 검사 작업이다”는 충분조건은 다르다. 유지보수도 그 장비를 사용할 수 있다. 문서의 일반적 설명을 논리적 동치로 강화하면 원치 않는 분류가 생긴다.

또 “작업은 문서를 하나 써야 한다”는 업무 규칙에는 두 의도가 섞여 있다. 현실에 사용 문서가 존재한다는 논리와 제출 데이터에 문서 ID 한 개가 적혀 있어야 한다는 검사는 다르다. OWL의 존재·개수 해석과 SHACL의 입력 검사 차이는 [C6](C06_semantics.md)에서 다룬다.

모델의 강도는 많을수록 좋은 것이 아니다. 관계 이름과 정의만으로 해결되는 질문에 복잡한 추론을 추가하면 운영 부담이 커질 수 있다. 반대로 규정 준수·분류 일관성을 자동 확인해야 한다면 정교한 공리가 도움이 될 수 있다. 선택은 질문과 오류 비용에 연결한다.

<a id="c3-06"></a>
## 6. 심화: 매핑·버전·거버넌스도 모델의 일부다

업무 모델에 Equipment가 있어도 원천의 asset_id, eqp_no, tool_name을 어디에 대응할지 정해야 한다. **Ontology는 의미의 계약, 매핑은 원천과 계약의 연결**이다. 잘 설계된 ontology도 잘못된 매핑을 자동 치료하지 않는다.

review_flag를 defect라는 속성에 연결하면 구조 검사를 통과해도 의미가 틀린다. 변경 시에는 정의·매핑·예제·질의의 diff를 함께 검토한다. 클래스 하나를 이름만 바꾼 경우와 의미 범위를 좁힌 경우는 데이터 마이그레이션 영향이 다르다.

운영 제안으로 모델마다 소유자, 적용 범위, 버전, 변경 이유, 폐기된 용어의 대체 경로를 남길 수 있다. 이는 이 교재의 거버넌스 설계 예이며 표준이 자동으로 강제하는 절차는 아니다. 더 깊은 공리 반례는 [D1](../deep/D1_semantics.md)로 이어진다.

<a id="c3-07"></a>
## 7. 발표에서 답해야 하는 질문

**꼭 설명:** ontology가 정하는 의미, 클래스·개체·관계·공리, 스키마와의 겹침, 질문 기반 설계, 자동 생성 후 검토가 필요한 이유. **생략 가능:** 설명 논리 전체 증명법, Protégé의 모든 메뉴, 모든 산업 ontology 정독.

**확인 질문:** ontology를 정하면 LLM이 항상 올바른 관계를 추출하는가? E05와 E01의 관계를 sameAs로 만들면 왜 위험한가?

### 해설

Ontology는 허용 범위와 의미를 제공해 오류를 줄이는 데 도움을 줄 수 있지만, 원문 해석·개체 식별·관계 방향·시점 오류는 남는다. sameAs는 단순 연관보다 강하다. 센서와 장비를 동일 개체로 취급하면 각각의 속성과 관계가 같은 대상에 대한 것으로 해석될 수 있다.
