# M3. 문서·DB·사람에게서 지식을 어떻게 얻는가?

이전: [M2](M2_representation.md) · [교재 안내](README.md) · 다음: [M4](M4_integration.md)

> 학습 목표: 정형 매핑·문서 추출·사람에게서 지식을 도출하는 일을 구별한다. 자동화 가능한 부분과 근거·맥락을 보존해야 할 부분을 사례로 설명한다.

<a id="m3-01"></a>
## 1. 수집이 끝났다고 지식이 생긴 것은 아니다

파일을 다운로드하면 bytes는 얻는다. 테이블을 읽으면 rows는 얻는다. 인터뷰를 녹음하면 발언은 남는다. 하지만 이 세 작업 모두 “이 기록은 무엇을 뜻하며 어떤 질문의 근거로 쓸 수 있는가”에 답하지는 않는다.

사례의 observations.csv에서 value=yes를 읽었다고 해보자. 컬럼 이름과 값만 보면 “합격”, “고장”, “검사 완료” 중 무엇인지 알 수 없다. metric=review_flag와 [D06](case/CORPUS.md#d06)의 정의까지 확인해야 검토 요청이라는 의미가 된다.

수집 단계의 산출물은 우선 **해석 가능한 원천 기록 묶음**이다. 지식 추출·정제·변화 관리는 그 이후에도 계속되는 작업이다. 자동 KG 구축 연구 역시 지식 획득, 정제, 변화 문제를 구분해 다룬다. [Zhong et al., Automatic KG Construction, 개요](https://arxiv.org/abs/2302.05019)

### 원천 카드 예시 — 교재의 설계 제안

| 필드 | runs.csv의 예 |
|---|---|
| 원천과 담당 | 작업 기록, 담당 P05 |
| 행 식별자 | RUN001 등 |
| 데이터 의미 | 실제로 남긴 작업 이력 |
| 갱신 방식 | 사례에서는 스냅샷, 실무에서는 별도 확인 |
| 관측 시점 | occurred_at |
| 연결할 키 | lot, equipment, used_document |
| 누락·충돌 처리 | 원본 보존 후 해석을 별도 기록 |
| 권한 | 원천과 파생 정보의 접근 범위 확인 |

원천 카드에 없는 내용을 LLM이 추측해서 채우게 하면 “출처가 없는 메타데이터”가 생긴다. 모르는 것은 미확인으로 남기고 실제 담당자나 시스템 정의를 찾는다.

## 2. 정형 데이터: 새로운 사실을 생성하기보다 의미를 매핑한다

runs.csv에는 이미 RUN002, L02, E01, D02가 있다. 이를 LLM에 보내 다시 읽고 이름을 만들게 할 필요가 있는지 먼저 묻는다.

~~~sql
SELECT r.id, r.lot, e.id AS equipment,
       r.occurred_at, r.used_document
FROM runs AS r
JOIN equipment AS e ON e.id = r.equipment
WHERE r.lot = 'L02'
ORDER BY r.occurred_at;
~~~

이 질의는 L02의 코팅 RUN008과 검사 RUN002를 가져온다. 조인 키를 알고 있다면 일반 프로그램으로 정확한 변환을 수행할 수 있다. 이때 “정형 데이터이므로 의미도 정확하다”는 결론은 아니다. 키가 잘못 입력되거나 metric의 의미가 다르면 오류는 그대로 전달된다.

매핑은 원천 구조를 의미 모델에 대응시킨다.

| 원천 필드 | 의미 모델 | 주의 |
|---|---|---|
| runs.id | Run의 안정된 ID | 다시 적재할 때 같은 사건인가 |
| runs.equipment | usedEquipment의 목적어 | 장비 이름 대신 식별자 |
| runs.occurred_at | 사건 발생 시각 | 수집 시각과 구별 |
| runs.used_document | 사용했다고 기록된 문서 | 실제 적용되어야 할 문서와 따로 비교 |

마지막 구분이 중요하다. 작업자가 D01을 썼다고 기록한 것과 정책상 D02를 써야 했다는 사실은 동시에 존재할 수 있다. 원천을 D02로 고쳐 “정답처럼 보이게” 만들면 실제 불일치를 지워버린다.

R2RML은 관계형 데이터에서 RDF 데이터셋으로의 매핑을 표현하는 W3C 언어다. 구현은 RDF를 만들어 저장할 수도 있고, 원천 관계형 데이터 위에 가상 질의 인터페이스를 제공할 수도 있다. 따라서 의미 연결이 항상 모든 데이터를 복사하는 것을 뜻하지 않는다. [R2RML, Abstract·§2](https://www.w3.org/TR/r2rml/)

### LLM은 어디에 쓸 수 있는가?

설명이 부족한 컬럼의 의미 후보를 제안하거나, 문서와 테이블 간 매핑 초안을 만들 수 있다. 그러나 컬럼명만 보고 의미를 확정하기보다 샘플 값·업무 정의·질문 결과와 대조해야 한다. SQL이 실행되었다는 사실도 의미가 맞다는 보장은 아니다. M4의 Auto Ontology 사례에서 다시 본다.

## 3. 비정형 자료: 파싱 오류와 의미 오류를 나눈다

PDF에서 표를 읽었다고 하자. 첫 단계의 문제는 셀과 제목을 제대로 복원했는지다. 두 번째 문제는 복원한 내용이 무엇을 의미하는지다. 이를 섞으면 잘못된 글자를 읽은 결과를 “LLM의 추론 오류”라고 잘못 진단할 수 있다.

~~~text
문서 파일
  → 페이지·표·문단의 구조 복원
  → 텍스트와 원본 위치 연결
  → 개체·사건·조건·부정·관계의 후보 추출
  → 식별·모델 매핑
  → 근거 확인
~~~

이는 교재의 설계 예다. 반드시 별도 서비스 다섯 개를 만들 필요는 없다. 단계의 책임을 구별하여 오류가 어디서 생겼는지 찾는 것이 목적이다.

[D02](case/CORPUS.md#d02)의 p1을 예로 보자. 대상 E01, 시작 시각 11월 3일 00:00, 이전 문서 D01, 새 문서 D02가 함께 나온다. “11월 3일부터 적용”만 추출하고 대상 장비를 버리면 E02에도 잘못 적용할 수 있다. 조건은 장식이 아니라 주장의 일부다.

다음은 자동 추출 결과의 **예시 형식**이다. 실제 LLM 호출 결과가 아니다.

~~~json
{
  "subject_id": "D02",
  "relation": "supersedes",
  "object_id": "D01",
  "scope": ["E01"],
  "valid_from": "2026-11-03T00:00:00+09:00",
  "evidence": {"document_id": "D02", "paragraph_id": "p1"},
  "epistemic_type": "policy",
  "review_status": "candidate"
}
~~~

JSON 형식이 맞는 것은 첫 관문이다. evidence가 가리킨 문단이 실제로 이 관계를 말하는지, scope가 누락되지 않았는지는 별도 검사다.

### 추출 지시를 더 구체적으로 만드는 법

“지식 그래프를 만들어라” 대신 다음과 같이 출력 계약을 제안할 수 있다.

- 지정한 유형·관계의 후보만 추출한다.
- 대상·시점·부정·가설 표현을 함께 보존한다.
- 모든 후보에 원문 위치를 붙인다.
- 근거가 없으면 없다고 표시한다.
- 모델 밖의 중요한 개념은 억지로 기존 관계에 넣지 말고 확장 후보로 분리한다.

이는 오류를 줄이기 위한 설계 제안이지 정확성을 보장하는 프롬프트가 아니다. 실제 데이터에 대한 평가가 필요하다. 원문에 “E01이 원인이라는 결론은 내리지 않았다”가 있다면 caused 관계를 확정 사실로 만들지 않는지가 평가 항목이다.

## 4. 암묵지: 말하지 않은 것을 단순 추출할 수는 없다

[D09](case/CORPUS.md#d09)의 담당자는 화면에 이전 작업 정보가 남아 보인 경험을 말한다. 이 발언을 “E01은 화면 오류가 자주 발생한다”로 요약하면 빈도와 원인이 새로 만들어진다. 원문은 빈도를 측정하지 않았다고 명시한다.

암묵지는 숙련자가 수행·판단에 활용하지만 완전히 명시하지 못한 지식이라는 관점에서 접근한다. 아직 문서가 없어서 누락된 사실과, 몸에 익은 판단·맥락을 모두 문장으로 표현하기 어려운 문제는 구별해야 한다.

NASA의 지식 포착 보고서는 사람의 소통 능력, 경험의 맥락, 1차 기록과 인터뷰의 결합을 강조한다. 단순 검색 도구 도입으로 모든 경험을 전달할 수 있다고 보지 않는다. 이는 반도체 규정이 아니라 지식 포착의 실제 사례로 참고한다. [Goodman, 2011, JSC-66136, pp.33, 36–37](https://ntrs.nasa.gov/api/citations/20110023477/downloads/20110023477.pdf)

### 사례 인터뷰를 한 단계 깊게 만들기

교재에서 제안하는 후속 질문은 다음과 같다.

| 막연한 질문 | 더 구체적인 질문 |
|---|---|
| 노하우가 무엇인가요? | 그날 무엇을 먼저 보고 확인이 필요하다고 판단했나요? |
| 왜 그렇게 했나요? | 다른 선택은 무엇이었고 어떤 단서로 제외했나요? |
| 항상 적용되나요? | 같은 방법을 쓰면 안 되는 경우가 있었나요? |
| 효과가 있었나요? | 전후에 무엇을 관찰했고 어떤 기록으로 확인할 수 있나요? |

이 질문으로 얻을 결과도 증거 수준이 다르다.

- 관찰: 담당자가 어떤 장면을 봤다고 보고한다.
- 판단: 그 단서를 어떤 의미로 해석했다.
- 행동: 무엇을 확인하거나 누구에게 요청했다.
- 가설: 가능한 원인을 제안했다.
- 검증: 다른 근거로 무엇이 확인되었는가.
- 적용 범위: 어떤 상황에서는 재사용하면 안 되는가.

이 분류는 교재의 기록 틀이다. 인터뷰의 모든 문장을 공식 절차로 바꾸려는 것이 아니다. 재현 가능한 지침으로 발전할 수도 있고, 유사 상황을 검토할 때 참고하는 경험 사례로 남을 수도 있다.

<a id="m3-05"></a>
## 5. 사람의 지식을 남기는 데도 검토가 필요하다

인터뷰는 질문 방식과 기억의 영향을 받는다. 그래서 “전문가가 말했다”는 이유만으로 모든 주장을 동일한 신뢰도로 저장하지 않는다. 담당자의 원문, 인터뷰 맥락, 관련 작업 기록을 연결하고, 필요한 경우 다른 담당자·기록과 대조한다.

LLM은 녹취의 주제 정리, 후속 질문 초안, 비슷한 사례 찾기, 표현 정리에 도움을 줄 수 있다. 원문에 없던 판단 이유를 매끄럽게 보충하면 오히려 증거를 오염시킨다. 자동화 결과를 다시 당사자가 확인하도록 하는 방식도 선택지다.

NASA Lessons Learned는 사건의 배경과 권고를 기록해 이후 학습·절차 개선에 활용하는 사례다. 여기서 가져올 관점은 “내용 저장”과 “다른 사람이 재사용할 수 있는 맥락”의 연결이다. [NASA Lessons Learned](https://www.nasa.gov/nasa-lessons-learned/)

## 선택 심화: 자료 종류보다 변환의 불확실성을 본다

CSV를 읽는 일은 결정적이어도 코드값의 의미 추정은 불확실할 수 있다. 문서도 규격이 매우 일정하면 규칙으로 추출하는 편이 단순할 수 있다. “정형=프로그램, 비정형=LLM”이라는 이분법 대신 작업마다 입력의 안정성과 의미의 불확실성을 따진다.

같은 작업에서도 파싱은 라이브러리, 필드 매핑은 규칙, 관계 후보는 LLM, 정책 판단은 사람이 담당할 수 있다. 역할 분담은 자료의 실제 오류와 검토 비용을 보고 결정한다.

## 확인 문제

1. runs.used_document를 정책상 유효한 문서로 자동 덮어써도 되는가?
2. JSON 추출 결과에 evidence 필드가 있으면 근거 확인이 끝났는가?
3. D09에서 “E01 화면 오류가 자주 발생한다”를 추출할 수 있는가?
4. 정형 데이터를 RDF로 활용하려면 반드시 전체 복사본을 만들어야 하는가?
5. 암묵지 도출과 문서 추출에서 실패 원인이 어떻게 다른가?

### 해설

1. 안 된다. 사용 기록과 준수해야 할 정책은 별도 사실이며 불일치 자체가 중요하다.
2. 아니다. 위치가 실제 존재하며 그 주장을 뒷받침하는지 확인한다.
3. 없다. 보고된 경험은 있지만 빈도·원인은 미측정이다.
4. 아니다. 가상 매핑·질의 등의 구현 대안이 있다. 신선도·원천 부하·권한·지연을 함께 고려한다.
5. 문서 추출은 이미 표현된 내용의 해석 오류를 주로 다룬다. 지식 도출은 무엇을 물어야 하는지, 기억·상황·판단을 얼마나 표현할 수 있는지의 문제까지 포함한다.

**3분 설명:** 하나의 SQL 행, D02 문단, D09 발언을 비교하며 “세 자료에 같은 자동화 방식을 적용하지 않는 이유”를 설명하라.
