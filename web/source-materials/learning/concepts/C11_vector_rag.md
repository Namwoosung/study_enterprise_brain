# C11. Vector RAG — 비슷한 의미를 찾아 근거로 쓰기

**목표:** 임베딩·유사도·색인·청킹·재랭킹의 원리를 익히고 검색 실패와 생성 실패를 분리한다.

<a id="c11-01"></a>
## 1. RAG와 Vector RAG가 필요한 이유

모델의 파라미터에만 지식을 의존하면 갱신·출처 추적에 한계가 있다. RAG는 외부 자료를 검색해 생성 과정에 사용하려는 접근이다. 2020년 RAG 논문은 파라미터 지식과 비파라미터 기억을 결합하는 학습 모델을 연구했다. 오늘날 실무에서 흔한 “검색 결과를 프롬프트에 넣기”가 원논문 구현과 완전히 같지는 않다. [Lewis et al., RAG](https://arxiv.org/abs/2005.11401)

Vector RAG는 검색에 벡터 표현을 활용하는 구성을 가리킨다. 질문 표현과 문서 표현이 달라도 관련 내용을 찾으려는 것이 장점이다. “장비를 다시 확인해야 한다”와 “설비 재점검”의 단어가 달라도 가까운 표현으로 배울 수 있다. 항상 그렇게 검색된다는 보장은 없으며 도메인·언어·모델로 평가한다.

검색이 붙었다고 자동으로 답이 정확해지지는 않는다. 필요한 자료가 원천에 없거나, 검색에서 빠지거나, 생성기가 근거를 잘못 해석할 수 있다.

<a id="c11-02"></a>
## 2. 임베딩과 유사도를 직관으로 이해하기

임베딩은 텍스트 등을 수치 벡터로 표현하는 함수의 출력이다. 검색용 모델은 질문과 관련 자료가 가까워지도록 학습될 수 있다. DPR은 질문·문서를 각각 인코딩하는 dual encoder를 통한 dense retrieval을 연구했다. [Dense Passage Retrieval](https://arxiv.org/abs/2004.04906)

벡터의 각 축이 반드시 “장비성·절차성” 같은 사람이 이름 붙일 수 있는 개념은 아니다. 벡터를 압축된 사실 DB로 해석하지 않는다. 유사도 점수도 곧 정답 확률이 아니다.

~~~text
cosine(q, d) = (q · d) / (||q|| × ||d||)
합성 계산: q=(1,0), d1=(1,0), d2=(0,1)
cosine(q,d1)=1, cosine(q,d2)=0
~~~

두 벡터가 0벡터가 아니어야 한다. 이 예는 방향 비교의 수학만 보여주며 실제 텍스트 임베딩 결과가 아니다. 모델마다 내적·코사인·거리와 정규화의 사용법이 다르므로 모델 권장 설정을 따른다.

<a id="c11-03"></a>
## 3. 오프라인 준비와 온라인 응답을 나누기

준비 단계는 문서 읽기 → 청크 분할 → 메타데이터 부착 → 임베딩 → 색인이다. 응답 단계는 질문 처리 → 후보 검색 → 권한·시간 등 조건 반영 → 필요시 재랭킹 → 근거 구성 → 생성 → 인용 확인이다. 이는 교재의 일반 파이프라인이며 모든 제품이 같은 순서를 쓰지는 않는다.

청크가 너무 작으면 조건절·표 제목·대상 범위가 떨어질 수 있다. 너무 크면 여러 주제가 한 벡터에 섞이고 프롬프트 비용이 커질 수 있다. 문서·섹션·표·부모 청크의 맥락을 보존하는 전략을 검토한다.

D02의 “확인 단계를 추가했다”만 남기고 E01용·개정 시점 정보를 잃으면 E02나 과거 작업에 잘못 적용할 수 있다. 청킹은 글자 수 자르기만이 아니라 **검색 가능한 근거의 단위를 설계하는 일**이다.

<a id="c11-04"></a>
## 4. 심화: ANN 색인은 정확성·속도·메모리의 선택이다

모든 벡터를 정확히 비교하는 방식은 자료가 많아지면 비용이 크다. Approximate Nearest Neighbor(ANN)는 근사적으로 가까운 후보를 효율적으로 찾는 접근이다. HNSW는 계층적 근접 그래프를 사용하는 대표 연구다. [Malkov & Yashunin, HNSW](https://arxiv.org/abs/1603.09320)

여기서 HNSW의 그래프는 **벡터 사이 검색을 돕는 근접 구조**다. 장비가 문서를 사용했다는 업무 관계 그래프와 다르다. 벡터 DB 내부가 그래프 알고리즘을 쓴다고 그 시스템을 곧바로 업무 지식 Graph RAG라고 부르지 않는다.

ANN recall과 업무 근거 recall도 구별한다. 전자는 정확한 벡터 최근접 결과를 얼마나 회수했는지, 후자는 답에 필요한 근거를 얼마나 찾았는지다. 임베딩 자체가 잘못된 순위를 주면 ANN을 정확하게 만들어도 업무 정답 근거는 빠질 수 있다.

<a id="c11-05"></a>
## 5. 심화: hybrid·reranking·filtering은 무엇을 보완하나?

정확한 ID "SN101"은 의미 유사도보다 키워드·필드 검색이 중요할 수 있다. Hybrid retrieval은 서로 다른 검색 신호를 결합하는 구성이다. 점수 척도가 다르면 단순 덧셈의 의미도 확인해야 한다. 순위 기반 결합이나 검증된 정규화를 검토한다.

Reranker는 1차 후보를 질문과 함께 더 정밀하게 비교해 재정렬한다. 많은 문서를 모두 정밀 비교하기보다 후보를 줄인 뒤 쓰는 이유는 비용이다. 그러나 1차 검색에서 빠진 문서를 reranker가 되살릴 수는 없다. 이 상한은 파이프라인 구조에서 따라오는 사실이다.

권한·유효 시점은 단순 관련도보다 우선하는 조건일 수 있다. 구현에 따라 검색 전·중·후 필터가 지원되는 범위가 다르다. 검색 후 많이 제거되어 빈 결과가 되거나, 제한 자료가 이미 생성기에 전달되는 문제를 점검한다.

<a id="c11-06"></a>
## 6. 어떤 질문에 강하고 어디서 실패할까?

D02의 특정 확인 절차를 찾는 질문은 원문 단락 검색으로 충분할 수 있다. L02의 모든 작업을 빠짐없이 열거하는 질문은 명시적 작업 목록 조회가 더 직접적일 수 있다. 그렇다고 Vector RAG가 다중 자료 질문을 원리적으로 절대 못 푼다는 뜻은 아니다. 반복 검색·질의 분해·메타데이터로 보완할 수 있다.

원인 질문은 더 엄격하다. D07의 센서 가설을 잘 검색했더라도 I01의 원인은 미확정이다. 검색 성공과 답변의 사실성은 다르다. 답변마다 어떤 주장에 어떤 근거가 연결되는지 확인해야 한다.

변경 시에는 원문뿐 아니라 청크·임베딩·색인·캐시의 버전을 추적한다. 문서를 삭제했는데 예전 요약이나 벡터가 남는다면 답변에 오래된 내용이 계속 섞일 수 있다. 이 운영 문제는 다른 RAG 방식에도 공통이다.

<a id="c11-07"></a>
## 7. 발표 수준과 확인 문제

**꼭 설명:** 임베딩·유사도·청킹·ANN·hybrid·reranking의 역할, 인덱싱과 질의 단계, 검색과 생성의 오류 구분. **생략 가능:** 임베딩 모델 훈련 코드, HNSW 내부 파라미터 전체, GPU 최적화.

**확인 질문:** 유사도 0.9는 90% 정답이라는 뜻인가? 후보에 없는 문서를 재랭킹으로 복구할 수 있나? HNSW 사용은 KG 도입인가?

### 해설

점수는 모델의 비교 척도이며 검증 없이 확률로 읽을 수 없다. 재랭킹은 주어진 후보 안에서 작동한다. HNSW의 근접 그래프와 업무 의미 관계 그래프는 역할이 다르다.
