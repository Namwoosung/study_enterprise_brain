# C8. Graph DB와 Neo4j — 표현한 그래프를 저장하고 질의하기

**목표:** 그래프 DB의 역할·비용을 이해하고 Neo4j를 ontology·KG·RAG와 구별한다.

<a id="c8-01"></a>
## 1. Graph DB는 왜 필요한가?

메모리에서 노드와 엣지를 그리는 것만으로도 작은 그래프는 탐색할 수 있다. 하지만 지속 저장, 동시 수정, 빠른 조회, 장애 복구, 접근 제어가 필요해지면 데이터베이스의 역할이 중요해진다. Graph DB는 그래프 구조를 저장·질의하는 데 초점을 둔 DB 시스템을 가리킨다.

연결을 반복해서 따라가는 업무에서는 그래프 질의가 문제의 모양과 잘 맞을 수 있다. 예를 들어 “문서가 바뀌면 영향을 받는 작업·로트·요약은 무엇인가?”는 관계 경로를 묻는 질문이다. 관계형 DB의 JOIN이나 재귀 질의로도 표현할 수 있다. 가능 여부보다 모델·질의의 명료함과 실행 비용을 비교한다.

KG는 데이터의 의미와 활용 방식에 관한 개념이고 Graph DB는 저장·질의 시스템이다. KG를 파일이나 관계형 뷰로 제공할 수도 있고, Graph DB에 의미가 빈약한 데이터만 저장할 수도 있다. [KG 모델·질의 개관](https://arxiv.org/abs/2003.02320)

<a id="c8-02"></a>
## 2. 그래프 DB도 여러 선택이 있다

RDF 저장소와 Property Graph DB는 표현·질의 생태계가 다르다. 다중 모델 제품도 존재하므로 모든 제품을 두 상자로 완전히 나눌 수는 없다. 기술 선정 시에는 이름보다 실제 지원을 확인한다.

| 확인 항목 | 왜 필요한가? |
|---|---|
| 데이터 모델·질의 언어 | RDF/SPARQL 또는 Property Graph/Cypher 등 계약 |
| 트랜잭션·동시성 | 작업·관계 갱신 도중 불완전 상태 방지 |
| 인덱스·계획 | 시작 노드 찾기와 확장 비용 |
| 제약 | 업무 ID 중복·타입 오류 방지 |
| 권한·백업 | 운영 범위와 복구 |
| 추론 지원 | RDF 저장과 OWL 추론은 별도 기능 |
| 배포·에디션·라이선스 | 실제 사용 조건 |

이 목록은 제품 기능을 전부 외우라는 뜻이 아니다. 발표에서는 어떤 책임을 DB에 맡기고 어떤 책임을 수집·검증 서비스에 두는지 설명할 수 있어야 한다.

<a id="c8-03"></a>
## 3. Neo4j는 무엇인가?

Neo4j는 Property Graph 모델을 사용하는 그래프 DB 제품·플랫폼이다. Cypher로 패턴을 질의하며, 관련 도구·드라이버·운영 기능·그래프 분석 및 검색 생태계를 제공한다. 기능과 사용 조건은 버전·제품·에디션에 따라 확인해야 한다. [Neo4j 공식 문서](https://neo4j.com/docs/)

이번 사례에서는 Equipment·Run·Document 노드를 저장하고, L02에서 관련 작업과 사용 문서를 찾는 데 활용할 수 있다. Neo4j를 선택했다고 원천의 잘못된 별칭이 자동 정리되거나 문서의 승인 여부가 자동 결정되지는 않는다.

Neo4j GraphRAG for Python은 관련 검색 파이프라인을 구성하는 별도 라이브러리다. DB 엔진, 검색 라이브러리, Microsoft GraphRAG는 서로 다른 대상이다. 제품 이름이 비슷해도 같은 알고리즘·출력을 보장하지 않는다. [Neo4j GraphRAG 패키지 문서](https://neo4j.com/docs/neo4j-graphrag-python/current/index.html)

<a id="c8-04"></a>
## 4. 심화: 인덱스와 순회가 함께 필요한 이유

L02라는 노드를 찾는 단계와 그 주변 관계를 따라가는 단계는 다르다. 인덱스는 선택적인 시작점을 찾는 데 도움이 될 수 있다. 이후 확장할 관계의 종류·방향·개수를 제한해야 한다. 공식 문서는 인덱스가 질의 계획에 미치는 영향을 예제로 설명한다. [Neo4j 인덱스와 질의 성능](https://neo4j.com/docs/cypher-manual/current/indexes/search-performance-indexes/using-indexes/)

교재의 단순 계산을 해보자. 단계마다 평균 20개 후보가 생기고 중복·필터를 무시하면 깊이 3의 경로 후보는 20³=8,000개다. 실제 엔진 비용 공식은 아니지만 “그래프니까 깊게 탐색해도 공짜”가 아님을 보여준다. 공통 허브 노드를 지나면 후보가 폭발할 수 있다.

ID·사이트·시간으로 시작 범위를 좁히고, 관계 타입·hop·결과 수를 제한한다. EXPLAIN은 실행 계획을 살펴보고 PROFILE은 실행 통계를 확인하는 데 사용한다. 쓰기 질의의 PROFILE은 실행을 수반할 수 있으므로 읽기 예제로 학습한다. [Cypher 실행 계획](https://neo4j.com/docs/cypher-manual/current/planning-and-tuning/execution-plans/)

<a id="c8-05"></a>
## 5. 심화: 트랜잭션과 지식의 정확성은 다르다

트랜잭션은 여러 변경을 하나의 처리 단위로 다루고 일관성·복구를 지원하는 DB 개념이다. Neo4j의 트랜잭션 동작은 공식 운영 문서에서 확인한다. [Database transactions](https://neo4j.com/docs/operations-manual/current/database-internals/transaction-management/)

그러나 DB가 원자적으로 저장했다고 의미까지 맞는 것은 아니다. RUN002와 E02를 잘못 연결한 변경도 기술적으로 정상 커밋될 수 있다. 업무 ID 제약은 중복을 막는 데 도움을 주지만 “NORTH 검사기 1호가 E01”이라는 해석은 데이터 통합 단계의 책임이다.

그래프와 벡터 색인을 별도로 운영하면 한쪽 갱신 후 다른 쪽 반영까지 지연이 생길 수 있다. 버전·처리 상태·재시도·삭제 전파를 설계해야 한다. 이 부분은 특정 제품의 장애를 주장하는 것이 아니라 다중 저장소 아키텍처에서 확인할 운영 질문이다.

<a id="c8-06"></a>
## 6. 그래프 DB 도입 여부를 어떻게 결정할까?

반복적인 연결 질의와 경로 설명이 핵심이면 그래프 모델을 검토한다. 단순 문서 검색이 대부분이라면 본문 색인과 메타데이터만으로도 시작할 수 있다. 대량 집계는 관계형·분석 시스템이 이미 잘 처리할 수 있다. 혼합 구성이 자연스러울 수 있다.

검토용 작은 실험은 세 질문으로 시작한다. 대표 질의를 모델이 명료하게 표현하는가? 갱신·철회·권한을 구현할 수 있는가? 같은 조건의 대안보다 비용·지연·운영 부담이 수용 가능한가? “그래프 DB가 더 빠르다”는 일반 문장 대신 질의·데이터·인덱스·버전을 적어 측정한다.

<a id="c8-07"></a>
## 7. 발표 수준과 확인 문제

**꼭 설명:** Graph DB와 KG의 역할 차이, Neo4j와 Property Graph·Cypher 관계, 인덱스와 탐색 비용, DB 일관성과 사실성의 차이. **생략 가능:** 클러스터 설치·운영 전체, 백업 명령 암기, 모든 GDS 알고리즘.

**확인 질문:** Neo4j가 있으면 OWL 추론이 자동 제공되는가? 관계를 따라가는데 인덱스가 왜 필요한가?

### 해설

Property Graph의 라벨·관계만으로 OWL 의미론이 자동 실행되는 것은 아니다. 필요한 변환·추론 지원을 따로 확인한다. 인덱스는 선택적인 시작 노드·값을 찾는 데 쓰일 수 있고, 이후 탐색 비용은 경로·분기·필터에 영향을 받는다.
