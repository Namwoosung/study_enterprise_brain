# C12. Graph RAG — 관계 구조를 검색 근거로 사용하기

**목표:** 일반 Graph RAG와 Microsoft GraphRAG를 구분하고 로컬 경로·커뮤니티 요약·오류 전파를 설명한다.

<a id="c12-01"></a>
## 1. 왜 그래프를 검색에 쓰려 하는가?

질문에 필요한 근거가 서로 다른 문서·테이블에 나뉘어 있으면 비슷한 청크 몇 개만으로 충분하지 않을 수 있다. “L02의 작업마다 사용한 문서와 해당 장비를 연결하라”는 질문은 사건별 연결이 중요하다. Graph RAG는 그래프 구조를 검색·근거 구성에 활용하는 접근을 넓게 가리킨다.

구체 구성은 다양하다. 개체를 찾아 주변 관계를 확장할 수도 있고, Cypher·SPARQL로 정확한 패턴을 질의할 수도 있고, 그래프 커뮤니티의 요약을 검색할 수도 있다. 이 교재의 분류이며 하나의 보편 표준 알고리즘이라고 주장하지 않는다.

Graph RAG를 사용한다고 반드시 LLM이 ontology 전체를 자동 생성해야 하는 것은 아니다. 사람이 관리한 자산·작업 관계나 기존 정형 데이터의 연결을 사용할 수 있다. 벡터 검색을 함께 사용할 수도 있다.

<a id="c12-02"></a>
## 2. 가장 작은 구현 흐름 이해하기

~~~text
질문에서 L02 식별
→ L02 관련 Run 조회
→ 각 Run의 장비·문서 연결
→ 관련 원문 구간 확보
→ 권한·시점·출처를 반영한 근거 묶음
→ 답변
~~~

RUN008과 RUN002를 모두 찾으면 코팅 E03/D04와 검사 E01/D02를 구분할 수 있다. 이 경로는 “각 작업에 사용한 문서”를 알려준다. 그 문서가 적절했는지 또는 원인이 무엇인지까지 답하려면 추가 지식이 필요하다.

그래프에 원문 링크를 남기는 이유는 관계만으로 세부 조건을 다 표현하기 어려울 수 있기 때문이다. 그래프는 탐색 길을 제공하고 원문은 문장·표의 세부 근거를 제공하는 혼합이 가능하다. 이 사례는 작동 원리 설명이며 검색 모델의 실측 결과가 아니다.

<a id="c12-03"></a>
## 3. Microsoft GraphRAG는 특정한 연구·구현이다

Microsoft GraphRAG는 문서에서 개체·관계를 추출하고 커뮤니티를 구성하며 요약 보고서를 만드는 처리 흐름을 제공한다. 기본 데이터 흐름에는 TextUnit, Entity, Relationship, Community report 등 구별되는 산출물이 있다. [공식 인덱싱 Dataflow](https://microsoft.github.io/graphrag/index/default_dataflow/)

이름이 같은 일반 Graph RAG 전체를 이 파이프라인 하나로 정의하지 않는다. Neo4j의 GraphRAG 라이브러리 역시 별도 구현이다. 도입 시 “GraphRAG를 쓴다”보다 **어떤 구조를 만들고 어떤 검색을 실행하는가**를 말해야 한다.

기업의 승인된 ontology·사실 그래프와, 문서 탐색을 위해 자동 추출한 검색용 그래프는 운영 목적이 다를 수 있다. 검색용 관계를 모두 검증된 업무 사실이라고 취급하면 안 된다. 필요에 따라 검토·불확실성 표시·분리 저장을 설계한다.

<a id="c12-04"></a>
## 4. Local Search와 Global Search의 차이

Microsoft 구현의 Local Search는 질문과 관련된 개체를 중심으로 관계·텍스트·커뮤니티 보고서 등을 조합한다. 개체 설명 임베딩도 활용한다. 따라서 그래프 검색과 벡터 검색이 완전히 분리된 대안이라는 설명은 맞지 않는다. [Local Search 공식 문서](https://microsoft.github.io/graphrag/query/local_search/)

Global Search는 데이터 전체에 걸친 질문을 다루기 위해 커뮤니티 보고서를 묶어 중간 응답을 만들고 결합하는 흐름을 제시한다. “이 문서 집합에서 반복되는 이슈는?”처럼 전반적 주제를 묻는 상황이 출발점이다. [Global Search 공식 문서](https://microsoft.github.io/graphrag/query/global_search/)

합성 사례에서 “E01 주변 이력”은 국소 연결, “자료 전반의 기록 문제”는 전체 요약을 검토할 수 있다. 다만 문서 수·중복·표본 선택이 편향되어 있다면 전체 요약도 실제 회사 전체의 통계가 아니다. 커뮤니티 수나 요약의 빈도만으로 발생률을 추정하지 않는다.

<a id="c12-05"></a>
## 5. 심화: 관계 탐색의 제한과 오류 전파

출발 개체를 잘못 식별하면 이후 경로가 모두 그럴듯하게 틀릴 수 있다. E01과 E02를 별칭만으로 합쳤다면 다른 사이트의 문서가 연결된다. 이 경우 LLM이 문장을 잘 써도 근거 구성 자체가 잘못됐다.

관계 확장에는 타입·방향·깊이·시간·권한·신뢰 조건을 둔다. 많은 노드와 연결된 일반 용어를 무제한 확장하면 관련 없는 자료가 늘 수 있다. 경로가 길어질수록 더 깊은 사고가 된다고 가정하지 않는다.

또 하나의 관계가 철회되면 그 관계에 의존한 경로·커뮤니티 보고서·캐시의 영향을 찾아야 한다. 같은 결론을 독립 근거가 지지하는 경우와 여러 근거가 함께 필요했던 경우를 구별한다. 단순히 모든 파생 결과를 무조건 삭제하거나 유지하는 대신 의존 규칙을 명시한다. 이는 교재의 운영 설계 제안이다.

<a id="c12-06"></a>
## 6. 심화: 비용과 평가를 어디서 측정할까?

그래프 추출·개체 통합·커뮤니티 요약은 준비 비용이다. 질의 시에는 개체 찾기·탐색·텍스트 회수·중간 응답·최종 생성 비용이 든다. 질문 한 번의 응답 속도만 비교하면 인덱스 구축·갱신 비용을 놓친다.

평가에서는 원천 근거 회수, 필요한 연결의 완전성, 답변 주장 지지, 시간·권한 준수, 답할 수 없을 때의 보류를 분리한다. 그래프가 잘 만들어졌는지와 답변이 좋은지도 별도 측정한다. 설명 가능한 경로가 있다고 그 경로의 모든 엣지가 사실인 것은 아니다.

발표에서 성능을 주장하려면 비교한 데이터·질문 종류·생성 모델·토큰 예산·구축 비용을 함께 제시한다. 특정 논문의 전체 요약 결과를 모든 반도체 작업 조회의 우월성으로 일반화하지 않는다.

<a id="c12-07"></a>
## 7. 발표 수준과 확인 문제

**꼭 설명:** 관계 기반 근거 구성, 일반 Graph RAG와 Microsoft 구현의 구분, local/global, 벡터와의 결합, 그래프 품질과 비용. **생략 가능:** 모든 커뮤니티 탐지 알고리즘 구현, 라이브러리 설정 전체.

**확인 질문:** Graph RAG는 벡터를 쓰지 않는가? 경로가 있으면 인과관계를 말해도 되는가? 검색용 그래프를 곧바로 운영 사실 그래프로 써도 되는가?

### 해설

벡터로 출발 개체나 텍스트를 찾고 관계로 확장할 수 있다. 경로의 의미는 관계 정의에 달려 있으며 인과 결론을 보장하지 않는다. 검색용 추출 결과의 승인 범위·원천 지지·불확실성을 확인한 후 사용 범위를 정해야 한다.
