# C14. 전체 연결 — 수집·검증·검색을 설명 가능한 체계로 만들기

**목표:** 모든 개념의 역할을 연결하고 비교·운영·평가 관점으로 발표 설명을 완성한다.

<a id="c14-01"></a>
## 1. 개념의 층위를 다시 연결하기

| 층위 | 개념 | 서로의 관계 |
|---|---|---|
| 개인의 지식 활용 | Second Brain | 외부 기억을 산출물에 재사용 |
| 조직의 지식 활용 | Enterprise Brain | 공유 의미·권한·책임·변경 관리 |
| 지식 표현 | Knowledge Graph·ontology | 개체 연결과 의미 모델 |
| 상호운용 생태계 | Semantic Web·W3C | RDF·OWL 등 공통 규격 |
| 그래프 데이터 모델 | RDF Graph·Property Graph | 진술·노드·관계를 표현하는 방식 |
| 저장·질의 | Graph DB·Neo4j·SPARQL·Cypher | 저장 엔진과 질의 언어 |
| 모델 구축 보조 | Auto ontology | 모델·매핑 등의 후보 생성·정비 |

이 표는 순서대로 모두 구매해야 하는 기술 목록이 아니다. 각 역할을 어떤 방식으로 구현할지 선택한다. 사용자가 발표할 “기업 지식을 어떻게 모으고 연결할지”는 수집뿐 아니라 이 역할 사이의 계약을 설명하는 주제다.

## 2. 같은 사례를 끝까지 따라가기

첫째, 장비 목록과 작업 CSV에서 E01·RUN002를 읽는다. 열 이름과 코드 의미를 매핑하고 업무 ID를 유지한다. 둘째, D02 절차에서 적용 장비·버전·시점을 추출한다. 셋째, D07의 가설은 확정 원인과 구분해 보관한다.

넷째, “검사기 1호”를 사이트와 일련번호로 식별한다. E05 부품은 E01과 합치지 않는다. 다섯째, 구조·참조·시점·원문 지지를 검증하고 위험에 따라 사람이 검토한다. 여섯째, 승인 범위가 명확한 지식을 운영 표현에 반영한다.

마지막으로 질문에 맞춰 조회한다. L02 작업 목록은 그래프나 정형 질의, D02의 문장 설명은 본문 검색, 자료 전체의 쟁점은 요약을 검토한다. I01의 원인에는 근거가 부족하므로 미확정이라고 답한다. 이는 기술들을 조합한 설명용 설계이며 성능 실측 결과가 아니다.

<a id="c14-03"></a>
## 3. 검토 병목은 무엇을 측정하며 줄일까?

전수 검토와 무검토 사이에 여러 정책이 있다. 구조·참조 검사처럼 반복 가능한 조건은 프로그램으로 처리하고, 높은 영향의 의미 변경·충돌·불확실성은 검토에 올릴 수 있다. 자동 처리분도 표본 감사를 통해 놓친 오류를 확인한다.

합성 계산으로 오류확률 0.02, 잘못 수용했을 때 비용 1,000, 검토 비용 5라면 오류 기대비용은 20이다. 완벽한 검토를 가정하면 5를 쓰는 편이 유리하다. 그러나 실제 검토도 틀릴 수 있고 비용 추정도 불확실하므로 이 계산을 자동 승인 공식으로 바로 쓰지 않는다. 위험을 분해하는 사고 도구다.

하루 1,000건에서 10%를 3분씩 검토하면 300분이 필요하다. 검토자 용량이 240분이면 단순 고정 평균에서 하루 20건이 밀린다. 중복 제거·원문 대조 화면·반복 오류 수정·위험 분류를 함께 검토한다. 단순히 검토율만 낮추면 품질을 잃을 수 있다.

<a id="c14-04"></a>
## 4. 정형·비정형·암묵지를 같은 방식으로 처리하지 않기

정형 자료는 필드 의미·키·단위·코드·시점을 확인한 매핑이 중심이다. 비정형 자료는 레이아웃·표·문장·조건·발언의 성격을 보존하는 추출이 필요하다. 두 경우 모두 원천이 잘못됐을 가능성은 남는다.

암묵지는 전문가에게 “아는 것을 모두 말해 달라”만으로 얻기 어렵다. 구체 사건에서 무엇을 보고, 어떤 대안을 버렸고, 어떤 조건이면 다른 판단을 했을지 질문하는 방식이 도움이 될 수 있다. 당시 기록·실물·후속 검토로 기억을 대조한다. NASA의 지식 포착 보고서는 문서화와 사람 간 지식 이전을 함께 다루는 참고다. [NASA Knowledge Capture Reports](https://ntrs.nasa.gov/citations/20110023477)

D09의 경험담은 탐색 단서로 가치가 있지만 빈도·원인·공식 절차를 입증하지 않는다. 경험을 수집한 뒤에는 적용 조건·반례·검토 상태를 명시한다. 모든 암묵지가 문장으로 완전히 변환된다는 전제도 피한다.

<a id="c14-05"></a>
## 5. 심화: 세 RAG를 공정하게 비교하려면

같은 원천·접근 권한·질문·정답 근거·생성 모델·평가 기준을 고정하고, 방식별 차이를 기록한다. 입력 청크와 요약·그래프 준비 비용이 다르면 질문당 비용만 비교하지 않는다. ID 조회, 다중 연결, 전체 요약, 시간 조건, 답 불가능 질문을 나누어 본다.

합성 정답 근거가 A·B·C이고 상위 4개 검색 결과가 A·B·X·Y라면 precision@4=2/4, recall@4=2/3이다. 둘을 혼동하지 않는다. 순위를 평가하는 MRR은 첫 정답의 역순위 평균이고, nDCG는 관련도와 순위 할인에 기반한 지표다. 이 지표들은 생성 답변의 사실성을 직접 측정하지 않는다. [Stanford IR 교과서의 평가 자료](https://nlp.stanford.edu/IR-book/)

답변 평가는 주장별 근거 지지, 필요한 내용의 완전성, 인용의 정확성, 잘못된 확신, 권한 위반을 따로 본다. LLM 심사만 사용한다면 사람 검토 표본과 채점 기준을 대조하고 심사 모델도 기록한다. 이 단원은 평가 설계이며 어떤 방식이 이겼다는 벤치마크가 아니다.

## 6. 발표 준비가 됐는지 스스로 확인하기

**꼭 설명:** 각 기술의 역할, 근거의 흐름, 선택의 이유와 한계. **생략 가능:** 발표 범위와 무관한 설치 명령·고급 쿼리 문법. 기간이 아니라 아래 설명 가능 여부를 학습 완료 기준으로 삼는다.

다음 항목을 자료를 보지 않고 각각 1분 안에 설명한다. 단어의 정의만 말하지 말고 합성 사례 하나와 한계를 붙인다.

1. Second Brain을 조직으로 확장할 때 새로 생기는 요구.
2. Knowledge Graph·ontology·Graph DB의 역할 차이.
3. Semantic Web과 W3C RDF·OWL이 제공하는 것.
4. RDF Graph와 Property Graph의 표현 차이.
5. Neo4j·Cypher·SPARQL이 각각 무엇인지.
6. Auto ontology가 자동화하는 작업과 검토할 결과.
7. Vector·Graph·Tree RAG가 어떤 근거를 선택하는지.
8. 추론·검증·사실성·인과관계가 왜 다른지.
9. 수집·매핑·추출·연결·검토·운영의 책임.
10. 원천 변경·권한 변경이 파생 지식에 미치는 영향.

### 해설

답변의 기준은 이 단원 표의 역할 구분과 C1~C13의 사례·한계다. “Graph RAG가 항상 우수하다”, “ontology가 있으면 오류가 없다”, “표준이면 사실이다” 같은 단정이 나오면 해당 단원을 다시 읽는다. 발표 범위 밖의 쿼리 문법·설치 세부는 외우지 않아도 되지만, 예제가 무엇을 질문하고 무엇을 보장하지 않는지는 설명할 수 있어야 한다.
