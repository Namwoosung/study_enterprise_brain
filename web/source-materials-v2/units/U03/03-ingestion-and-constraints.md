# 파일 재적재·제약·트랜잭션이 맡는 책임

장비 파일을 매일 받습니다. 어제 넣었던 E01이 오늘 다시 나오고, 제조번호가 정정된 행도 있습니다. 한 줄을 DB에 넣는 구문을 아는 것과 반복 적재가 같은 결과를 유지하도록 만드는 것은 다릅니다. 이번 수업은 작은 변경 하나를 처리하면서 DB가 보장하는 범위와 애플리케이션의 책임을 구체화합니다. 예제의 파일·부품·시간은 합성이며 Cypher 결과는 문서를 기준으로 도출했습니다.

## 재실행해도 중복되지 않아야 하는 대상은 무엇인가요?

이 입력을 받았다고 합시다.

| 적재 시도 | 원천 자산 키 | 제조번호 | 원천 판 |
|---|---|---|---|
| 1 | E01 | S100 | asset-r1 |
| 2 | E01 | S100 | asset-r1, 재전송 |
| 3 | E01 | S101 | asset-r2, 정정 |

시도 2를 다시 처리해도 같은 자산 노드가 하나여야 합니다. 이런 성질을 여기서는 **멱등성(idempotence)**이라고 부릅니다. 동일한 입력 작업을 반복해도 의도한 최종 효과가 반복 횟수만큼 늘지 않는 것입니다. 하지만 ‘장비가 두 번 검사됐다’는 서로 다른 발생은 두 건을 보존해야 합니다. 자산 중복과 검사 반복을 같은 규칙으로 없애면 실제 이력을 잃습니다.

```cypher
MERGE (e:Equipment {id:$assetId})
SET e.serial = $serial
```

`$assetId`, `$serial`은 원천에서 검증·매핑해 전달한 값입니다. 첫 줄은 ID가 같은 장비 패턴을 찾거나 만듭니다. 둘째 줄은 제조번호 속성을 설정합니다. 시도 3에서도 자산은 E01 하나이고 번호만 S101로 바뀝니다. 이 설계는 **현재 번호를 덮어써도 된다**는 합의가 있을 때 맞습니다. 이전 번호와 정정 이유를 보여 줘야 한다면 원천 판과 정정 기록을 별도 보존해야 합니다.

반대로 `MERGE (e:Equipment {id:$assetId, serial:$serial})`는 두 값이 모두 맞는 패턴을 찾습니다. S100에서 S101로 바뀌면 기존 노드와 전체 패턴이 다릅니다. 고유성 제약이 없다면 같은 E01이 늘어날 수 있고, 제약이 있으면 충돌로 실패할 수 있습니다. 변경 가능한 값이 식별 패턴에 섞인 것이 원인입니다. [Neo4j MERGE: full pattern과 constraints](https://neo4j.com/docs/cypher-manual/current/clauses/merge/)

## 제약을 넣으면 무엇이 거절되나요?

첫 수업의 `Equipment.id IS UNIQUE`는 같은 라벨의 같은 id 값이 반복되지 않게 합니다. id가 없는 장비까지 모두 거부하는 규칙은 아닙니다. 존재 제약은 값의 존재를 요구하고, 키 제약은 존재와 고유성을 함께 요구하는 종류입니다. 제품 버전·에디션마다 지원 조건을 확인해야 합니다. 현재 공식 문서에서 존재·키·타입 제약의 에디션 조건을 표시하므로, 이 수업의 개념을 그대로 모든 설치판의 기능 목록으로 읽지 않습니다. [Neo4j Create constraints](https://neo4j.com/docs/cypher-manual/current/schema/constraints/create-constraints/)

| 잘못된 입력 | id 고유성만으로 막나요? | 더 필요한 판단 |
|---|---|---|
| E01이 같은 라벨에 두 노드로 생성 | 같은 값이 있으면 차단 | 적재 실패·재시도 처리 |
| 장비에 id 자체가 없음 | 고유성만으로는 충분하지 않음 | 필수 값 검사 또는 지원되는 존재/키 제약 |
| E01과 TOOL-A가 같은 실물의 별개 ID | 값이 달라 통과 가능 | 원천 교차표와 개체 정합 |
| 존재하는 장비를 잘못된 정비와 연결 | 단순 id 고유성으로는 차단 못 함 | 업무 관계와 원문 근거 검사 |
| 식각 장비에 다른 업무 라벨을 부착 | 라벨 자체는 논리 분류 규칙을 자동 강제하지 않음 | 모델 정의·입력 검사·필요시 추론 |

제약은 실패를 보여 주는 중요한 도구입니다. 하지만 어떤 제약을 정의하느냐가 앞서야 합니다. 모든 문자열을 강하게 고유하게 만들면 맞는 자료까지 거부할 수 있습니다. 실물과 모델이 같은 표시명을 쓰는 예에서 표시명 고유성을 전역 요구하는 것이 대표적인 오류입니다.

## 관계를 합칠 때 양쪽 노드를 먼저 찾습니다

장비 E01이 매뉴얼 M17을 사용한다는 현재 연결을 재적재합니다.

```cypher
MATCH (e:Equipment {id:'E01'}), (m:Manual {id:'M17'})
MERGE (e)-[:USES_MANUAL]->(m)
```

첫 줄은 이미 존재하는 두 대상을 찾습니다. 둘째 줄은 그 두 노드 사이의 지정된 패턴을 맞춥니다. 어느 노드가 없으면 첫 MATCH에서 행이 생기지 않아 뒤의 MERGE도 실행할 입력이 없습니다. 이를 성공으로만 기록하면 누락을 놓칩니다. 적재 건수, 참조 실패, 후보 보류를 별도 기록하고 원천 키가 왜 없었는지 확인합니다.

현재 연결 하나가 목적이면 이런 병합이 맞을 수 있습니다. 매뉴얼 검토 R1·R2 두 사건을 적재할 때 동일한 끝점만 보고 `REVIEWED` 관계 하나로 합치면 두 번째 발생이 사라집니다. 원천의 검토 ID가 그 사건의 기준이어야 합니다. 한 원천 행을 재전송한 것인지 같은 사람이 다시 검토한 새 행인지 구별할 키를 먼저 정합니다.

## 트랜잭션은 중간 변경의 노출을 다룹니다

E01의 P7 장착을 종료하고 P8 장착을 시작하는 변경을 생각해 보겠습니다. 기존 연결 종료만 성공하고 새 연결 생성이 실패하면, DB의 현재 장착 조회에는 부품이 없는 중간 상태가 남을 수 있습니다. 두 변경을 하나의 **트랜잭션(transaction)**으로 묶으면 함께 커밋하거나 실패 시 롤백하는 단위로 다룰 수 있습니다. Neo4j는 그래프·색인·스키마 접근을 트랜잭션으로 수행합니다. [Neo4j Database transactions](https://neo4j.com/docs/operations-manual/current/database-internals/transaction-management/)

일반적으로 ACID라는 네 가지 성질로 설명합니다. 원자성은 관련 변경의 전부 또는 전무, 일관성은 정의된 DB 규칙을 만족하는 전이, 격리는 동시 작업 간에 제공하는 분리 수준, 지속성은 완료된 커밋의 보존을 다룹니다. 특히 **일관성**이라는 단어를 ‘현장 장비의 실제 상태와 항상 일치함’으로 읽지 않습니다. 날짜를 잘못 입력해도 DB 제약에 맞으면 커밋될 수 있습니다. DB의 보장과 세계에 대한 확인은 다릅니다.

| 시나리오 | DB 안에서 확인할 결과 | 남는 업무 문제 |
|---|---|---|
| 새 장착 생성 중 오류, 트랜잭션 롤백 | 옛 종료 변경도 반영되지 않음 | 원천 작업이 실제로 수행됐는지는 따로 확인 |
| 두 변경 정상 커밋 | 종료·시작이 함께 반영 | 시각과 부품 ID가 사실에 맞는지 검토 |
| 동일 파일 재전송 | 승인된 키 기준으로 같은 최종 효과 | 잘못된 ID 정책이면 틀린 병합도 반복 가능 |

여러 클라이언트가 동시에 같은 자산을 생성하면 앞서 조회했을 때 없었다는 결과만으로 중복 생성을 막을 수 없습니다. 고유성 제약과 적재 패턴, 실패 후 재시도를 함께 설계합니다. 드라이버가 재시도하는 트랜잭션 함수에는 외부 이메일 발송처럼 되돌릴 수 없는 효과를 무심코 넣지 않습니다. DB 안에서 되돌린 변경과 외부 작업은 다른 시스템의 효과이기 때문입니다. 이 개념은 특정 그래프 제품만의 문제도 아닙니다. [Neo4j Python driver transaction functions와 재시도](https://neo4j.com/docs/python-manual/current/transactions/)

## 화면에서 삭제한 점은 무엇을 없앴을까요?

현재 사용 관계를 지우는 일, 문서의 폐기를 기록하는 일, 문서 노드 자체와 관계를 물리적으로 지우는 일은 다릅니다. Neo4j의 `DELETE`는 지정한 노드·관계를 삭제하며 관계가 남은 노드는 그 관계도 처리해야 합니다. `DETACH DELETE`는 연결 관계까지 함께 삭제하는 구문입니다. 편하게 지울 수 있다는 사실이 업무상 그 기록을 없애도 된다는 결정은 아닙니다. [Neo4j DELETE](https://neo4j.com/docs/cypher-manual/current/clauses/delete/)

승인 기록을 폐기했다는 이력이 필요하면 폐기 사건·사유·시각을 보존하고 기본 조회에서 현재 유효한 기록만 고를 수 있습니다. 반대로 보존하면 안 되는 자료를 실제로 삭제해야 하는 상황도 있습니다. 그때 원문 사본, 검색 색인과 요약에도 남았는지 확인할 의존 관계가 필요합니다. 이런 수명주기는 U17에서 다룹니다. 그래프 DB에서 노드를 지웠다는 한 동작만으로 외부 색인이나 생성된 답변까지 자동 삭제되지는 않습니다.

## 설명 연습

**1.** 파일 재전송 때 노드 수가 늘지 않습니다. 따라서 적재 파이프라인이 모두 정확하다고 할 수 있나요?

중복 방지의 한 조건만 확인한 것입니다. E01과 다른 실물을 잘못 합쳤을 수도 있고, 두 실제 검토 사건을 하나로 덮었을 수도 있습니다. 원천 키·반복 발생·정정·집계 단위를 시험해야 합니다.

**2.** 부품 교체 변경이 원자적으로 커밋됐습니다. 현장에서도 교체됐다는 근거로 사용할 수 있나요?

DB 변경이 함께 반영됐다는 근거입니다. 현장 수행 보고·관측·승인과 연결해 실제 수행의 근거를 확인해야 합니다. DB 내부 일관성과 실제 사실은 별도의 검사입니다.

**3.** 원문 링크 노드를 지웠는데 RAG가 옛 내용을 답합니다. 어디를 확인할까요?

문서 청크·임베딩 색인·그래프 설명·요약과 캐시가 어느 원천 판에서 파생됐는지 확인합니다. 원천 삭제 신호가 그 자료에 전달되어 무효화됐는지 보아야 합니다. 노드 하나와 그 파생물의 수명은 자동으로 같아지지 않습니다.
