# 정정·철회가 파생 지식으로 전파되는 과정

원문 M-v2의 ‘12분’이 잘못 전재됐다는 정정이 들어왔습니다. 운영 화면의 문서만 새 판으로 바꾸었는데 RAG는 옛 요약에서 계속 12분을 답합니다. 원문과 답변 사이에는 추출 주장·그래프 설명·요약·임베딩·캐시가 있습니다. 어느 것을 다시 만들지 알아야 정정이 실제 사용자 답변에 도달합니다.

이 수업의 처리 정책과 ID는 합성 설계입니다. 특정 제품이 다음 절차를 기본으로 제공한다는 뜻은 아닙니다. 앞 단원의 정제·evolution과 PROV 계보를 실제 운영 변경으로 연결해 보겠습니다. [자동 KG 구축 survey §6](https://arxiv.org/html/2302.05019v1#S6)

## 원문 승인과 주장 채택은 별도 상태입니다

문서가 원천 시스템에서 승인됐다고 그 문서에서 추출한 모든 관계가 맞는 것은 아닙니다. 표의 열을 잘못 읽으면 승인 문서에서도 잘못된 후보가 나옵니다. 반대로 파일이 초안이라는 이유로 ‘초안에 이런 의견이 있다’는 보고 사실까지 기록할 수 없는 것은 아닙니다. 무엇을 어떤 용도로 제공하는지 나눕니다.

| 대상 | 이 설계의 상태 예 | 판단하는 질문 |
|---|---|---|
| 원문 판 | 초안·승인·대체·철회 | 원천에서 어떻게 관리하며 언제 적용되나? |
| 추출 후보 | 생성·구조 확인·충실성 확인·보류·기각 | 원문에서 그 의미를 옮겼나? |
| 채택 주장 | 제공 가능·대체·철회 | 정해진 사용 목적의 기준을 만족하나? |
| 인덱스·요약 | 작성 중·검사 완료·활성·무효 | 어떤 채택 주장과 원문 판을 사용했나? |

이 목록을 모든 항목이 같은 순서로 거치는 단일 상태 기계로 만들 필요는 없습니다. 낮은 영향의 자산 표 매핑은 승인된 규칙과 자동 검사로 제공할 수 있고, 근거 없는 원인 후보는 전문가 확인이 필요할 수 있습니다. 중요한 것은 자동 승인 범위·예외·이유를 먼저 정해 두고, 실제 상태 변경의 근거를 기록하는 것입니다.

‘검증 통과’ 플래그 하나도 무엇을 검사했는지 없으면 모호합니다. JSON 형식 검사를 통과한 후보와 독립 사실 확인이 끝난 주장을 같은 `verified:true`로 읽지 않도록 검사 종류·입력 판·결과·담당자를 남깁니다. U11에서 배운 여러 검사는 여기서 상태를 바꾸는 증거로 연결됩니다.

## 후보와 제공 범위를 분리하는 두 설계

**분리 저장**에서는 후보 영역과 제공 영역을 따로 둡니다. 검토·자동 정책을 통과한 결과를 새 제공 그래프에 반영합니다. 사용 질의가 후보까지 실수로 읽는 위험을 줄일 수 있지만, 복사와 ID 대응·재처리·전환 관리가 필요합니다. 제공 영역의 시점이 후보 최신 상태와 다를 수도 있습니다.

**공통 저장과 제한된 뷰**에서는 후보와 채택 이력을 같은 저장소에 두고, 정책을 적용한 뷰나 조회 API가 제공 범위를 고릅니다. 하나의 대상을 추적하기 쉽지만 모든 관련 조회가 상태·시점·권한 규칙을 빠뜨리지 않도록 강제해야 합니다. 화면 하나에서만 필터링하고 다른 API는 전체 노드를 읽으면 같은 정책을 지키지 못합니다.

두 방식 모두 운영 그래프에 들어갔다는 사실 자체가 진실성의 증명은 아닙니다. 정해 놓은 기준에서 사용 가능한 상태라는 의미를 갖습니다. 자료의 종류와 위험에 따라 별도 출처 확인·감사·철회 절차가 이어집니다. 인간 검토를 모든 레코드에 강제하는 방식과 승인된 규칙을 통한 제한적 자동 적용도 비교할 수 있습니다. 병목과 오류 손실을 함께 검토한 뒤 정책을 선택합니다.

## 무엇이 무엇에 의존하는지 적습니다

M-v2에서 얻은 주장 C12를 사용한 산출물의 예입니다.

```text
M-v2 p.9 → 추출 X5 → C12-r1
                         ├→ 장비 설명 E-desc-4
                         ├→ 커뮤니티 보고 R7
                         │       └→ 보고서 임베딩 V7
                         └→ 답변 캐시 A9
```

그림의 화살표는 실세계 인과가 아니라 **처리 의존**입니다. 원문이 바뀌면 화살표 뒤쪽의 영향을 조사합니다. 장비 자체 E01의 ID를 삭제하는 것은 아닙니다. 그 장비에 관한 설명·정책 사실의 특정 판이 바뀌는 것입니다. 온톨로지의 클래스 정의까지 바뀌었다면 매핑과 타입 추론, 검증·질의에도 영향이 생길 수 있습니다.

| 변경 | 다시 확인할 최소 대상 | 자동으로 없앨 수 없는 것 |
|---|---|---|
| 표의 값만 정정 | 해당 구간 추출·주장·의존 설명/요약·관련 색인/캐시 | 장비의 식별자와 무관한 이력 |
| 장비 ID 매핑 정정 | 연결된 사건의 대상·집계·그래프 경로·이름 검색 | 다른 장비와 독립인 원천 기록 |
| 원천 철회 | 해당 판에서 얻은 주장들의 지지 근거와 제공 상태 | 다른 유효 원천이 독립적으로 지지하는 주장 |
| 권한 축소 | 파생물의 읽기 허용·요약 재생성·캐시 | 사실의 진위 자체는 별개 |

변경을 전부 ‘원문 하나가 바뀜’으로 처리하면 필요 이상으로 다시 만들거나 필요한 변경을 놓칩니다. 사용한 구간·규칙·데이터 판의 의존을 남기면 재처리 대상을 좁힐 수 있습니다. 다만 의존 기록이 부정확하면 증분 처리가 누락을 만들 수 있어 전체 재구축과 결과를 대조하는 표본도 필요합니다.

## 여러 근거의 OR와 여러 입력의 AND

같은 사실 Q를 D1과 D2가 각각 독립적으로 지지한다고 합시다. D1이 철회돼도 D2가 유효하고 현재 질문 범위에 맞으면 Q를 계속 제공할 수 있습니다. **대체 지지 근거 중 하나가 충분한 구조**입니다. 모든 후손을 무조건 삭제하는 규칙은 이 상황에서 맞는 지식도 잃게 합니다.

반대로 Q와 R을 함께 읽고 만든 요약 S는 두 내용을 모두 포함할 수 있습니다. R이 잘못됐다면 S의 Q 부분만 맞더라도 현재 S 전체를 그대로 제공하기 어렵습니다. Q를 남겨 새 요약을 만들거나 문장별 지지를 확인해야 합니다. **생성에 함께 사용한 입력들의 영향**을 추적하는 구조입니다. 의미상 대체 지지와 생성 계보를 하나의 단순 부모 목록으로만 다루면 철회 판단을 틀리기 쉽습니다.

예를 들어 D1은 현행 12분, D2는 구판 8분을 말하면 애초에 같은 사실의 대체 근거가 아닙니다. 문장에 숫자만 비슷하거나 같은 장비 이름이 있다는 이유로 OR 묶음에 넣을 수 없습니다. 기간·모델·조건이 같은 주장을 뒷받침하는지 검토해야 합니다. 출처별 주장을 보존한 뒤 채택 정책으로 값을 고르는 U10의 통합 방식을 떠올려 보세요.

## 증분 처리를 순서대로 실행합니다

이 설계에서는 변경 신호가 들어오면 다음 산출물을 남깁니다. 표는 반복 처리의 계약 예이며 특정 큐 제품의 표준 형식이 아닙니다.

| 단계 | 입력 | 남기는 산출물 |
|---|---|---|
| 변경 식별 | 문서 ID·원천 판·새 내용·변경 이유 | 변경 이벤트 ID, 수집·검증 시각 |
| 영향 계산 | 기존 구간·매핑·파생 의존 | 재처리 대상과 임시 제공 중지 대상 |
| 재추출·검토 | 새 원문과 고정한 모델·정책 | 새 후보와 전후 diff, 검사 결과 |
| 파생 갱신 | 채택한 새 주장 집합 | 새 그래프·요약·색인 판 |
| 회귀 확인 | 기존 질문과 변경 질문 | 유지할 답·바뀔 답·보류할 답의 비교 |
| 활성 전환 | 검사한 산출물 묶음 | 활성 판·전환 기록·복구 대상 |

원천 이벤트가 항상 순서대로 도착하지 않을 수 있습니다. r3를 먼저 처리한 뒤 늦게 온 r2를 최신으로 덮어쓰면 정정을 되돌리는 오류가 생깁니다. 원천의 판 순서나 수정 토큰을 비교하고 같은 이벤트를 재처리해도 중복 효과가 생기지 않게 합니다. 동일 문서가 원천에서 같은 판 번호로 재전송됐으나 내용이 다르면 수집 실패로 보류하고 조사할 수도 있습니다. 정책이 내용 변경을 어떻게 해석하는지 명확해야 합니다.

모든 변경을 원자적으로 한 DB 트랜잭션에 넣을 수 있는 것도 아닙니다. 원문 저장소·그래프·벡터 인덱스가 별도라면 갱신 중 잠시 서로 다른 판을 볼 수 있습니다. 새 묶음을 따로 작성해 확인한 뒤 조회가 참조하는 활성 판을 전환하거나, 각 응답에 자료 판을 표시해 불일치를 탐지할 수 있습니다. 원천·파생물 버전을 함께 기록하는 이유입니다.

## 롤백은 사실을 되돌리는 일과 다릅니다

새 파서가 표를 잘못 읽어 제공 오류가 생기면 직전 인덱스와 매핑으로 돌아갈 수 있습니다. 하지만 원천이 보안 사유로 철회되거나 권한이 축소됐다면 옛 인덱스를 통째로 복구해 그 자료를 다시 노출해서는 안 됩니다. 복구할 소프트웨어·파생 산출물과 현재 유효한 원천·정책의 조합을 다시 확인합니다.

원천 정정으로 세상이 바뀐 것처럼 옛 사실을 삭제하는 것도 피합니다. 이전 답변을 재현하는 감사 자료와 현재 제공하는 지식은 목적이 다릅니다. 감사 자료도 접근 정책과 보존 기간을 갖습니다. 어떤 기록을 어디까지 보존할지는 해당 조직의 자료 정책에서 정해야 합니다.

## 설명 연습

**1.** D1이 철회됐으니 D1에서 한 번이라도 파생된 모든 노드를 지웁니다. 무엇을 놓칠까요?

같은 주장을 독립적으로 지지하는 D2가 있을 수 있고, 장비 ID처럼 원천 철회와 무관한 대상도 있을 수 있습니다. 특정 주장의 지지와 특정 산출물의 생성 의존을 나누어 확인합니다.

**2.** 그래프의 값은 새 판인데 답변은 옛 값을 말합니다. 어디부터 볼까요?

생성기가 받은 컨텍스트와 그 판을 확인하고, 문서 청크·개체 설명·커뮤니티 보고·임베딩·캐시 중 어느 것이 옛 값을 보냈는지 추적합니다. 최종 DB 값만 확인하면 중간 파생물을 놓칩니다.

**3.** 새 파서 오류로 이전 인덱스를 복구하려 합니다. 그 사이 원문 권한이 바뀌었다면요?

이전 인덱스의 내용에 현재의 접근 정책을 다시 적용하고, 철회·삭제된 자료가 되살아나지 않는지 확인합니다. 동작 버전의 복구가 정책의 과거 복원을 의미하지는 않습니다.
