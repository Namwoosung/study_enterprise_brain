# 사건이 일어났다는 말과 문서가 그렇게 주장한다는 말

앞 수업의 drive1은 실제 운전의 발생을 나타냈습니다. 그런데 기업 지식을 모을 때는 사건뿐 아니라 **그 사건에 관해 누가 어떤 기록을 남겼는지**도 관리해야 합니다. 원문이 정정되거나 서로 다른 기록이 충돌할 수 있기 때문입니다.

예를 들어 교육용 정비 보고서 R17에 ‘장비 E01은 부품 P7을 사용한다’고 적혀 있습니다. 이 문장을 곧바로 운영 그래프의 확정 사실로 받아들일까요? 아니면 보고서가 한 주장으로 저장한 뒤 검토할까요? 같은 문자열을 추출했어도 두 선택이 갖는 의미는 다릅니다. 이번에는 사건·주장·문서·그래프 묶음이 각각 무엇을 가리키는지 나눠 보겠습니다.

## 1. 관계의 종류를 설명하는 것과 특정 기록을 설명하는 것

아래는 관계 종류 자체에 이름을 붙이는 예입니다.

```turtle
@prefix ex: <https://example.org/fab/> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
ex:usesPart rdfs:label "사용 부품"@ko .
```

`usesPart`라는 관계가 사람에게 어떤 이름으로 보일지 설명합니다. 여기에 검토자를 붙여도 ‘E01이 P7을 쓴다는 이번 주장’을 특정하지는 못합니다. 같은 관계를 E02와 P8 사이에서도 사용할 수 있으므로 어느 주장인지 구분할 대상이 더 필요합니다.

다음은 실제 대상 사이의 진술입니다.

```turtle
@prefix ex: <https://example.org/fab/> .
ex:E01 ex:usesPart ex:P7 .
```

이제 장비 E01과 부품 P7을 연결합니다. 하지만 이 한 트리플만으로는 어떤 보고서에서 얻었는지, 누가 확인했는지, 언제 유효한지 알 수 없습니다. RDF가 그 정보를 금지해서가 아니라 아직 그 정보를 적지 않았기 때문입니다.

## 2. 진술을 대상으로 설명하는 reification

RDF 1.1의 reification 어휘를 사용하면 어떤 진술의 주어·술어·목적어가 무엇인지 설명할 수 있습니다. reification은 여기서 진술을 설명 가능한 대상으로 나타내는 방식이라고 이해하면 됩니다.

```turtle
@prefix ex: <https://example.org/fab/> .
@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .

ex:claim17 a rdf:Statement ;
    rdf:subject ex:E01 ;
    rdf:predicate ex:usesPart ;
    rdf:object ex:P7 ;
    ex:reportedIn ex:R17 ;
    ex:reviewState "미검토" .
```

`claim17`은 이번 진술 설명에 붙인 식별자입니다. `rdf:Statement`는 RDF 진술을 나타내기 위한 클래스이며, `rdf:subject`, `rdf:predicate`, `rdf:object`는 그 진술의 세 자리를 기록하는 어휘입니다. 마지막 두 속성은 이 교재에서 만든 예제 어휘로, 기록된 문서와 검토 상태를 나타냅니다. 상태 문자열은 W3C가 정한 운영 정책이 아닙니다.

위 코드는 ‘E01 usesPart P7이라는 내용을 가진 진술을 설명한다’고 읽습니다. 이 reification 정보만으로 원래의 `ex:E01 ex:usesPart ex:P7`을 함께 주장하는 것은 아닙니다. 따라서 원문에 나온 미확인 내용을 설명하는 자료와 운영에서 채택한 사실을 다르게 다룰 수 있습니다. 실제 시스템에서는 어떤 그래프를 조회할지, 언제 원 진술을 채택할지를 정책으로 정해야 합니다. [RDF Schema §5.3 reification vocabulary](https://www.w3.org/TR/rdf-schema/#ch_reificationvocab), [RDF semantics의 reification 설명](https://www.w3.org/TR/rdf11-mt/#reification)

운전 사건 노드와 비교해 보세요. `drive1`의 시각은 운전이 시작된 때입니다. `claim17`의 기록 시각을 추가한다면 그것은 문서에 기록되거나 시스템에 수집된 때일 수 있습니다. 사건 시각과 기록 시각을 하나의 ‘timestamp’로 합쳐 버리면 ‘언제 일어났나’와 ‘언제 알게 됐나’의 답이 섞입니다.

같은 내용을 두 문서가 독립적으로 주장했다면 서로 다른 claim 식별자를 사용할 수 있습니다. 반대로 하나의 사실에 문서 링크 두 개만 붙이는 간단한 모델도 가능합니다. 각각 독립 검토·철회해야 하는지에 따라 선택합니다. 표기 방법을 정하기 전에 관리할 대상이 사건인지, 진술의 내용인지, 개별 문서 기록인지부터 정해야 합니다.

## 3. 여러 그래프를 묶는 dataset

문서마다 얻은 진술을 묶어 관리하고 싶다면 named graph를 사용할 수 있습니다. RDF dataset은 default graph와 이름이 붙은 그래프들의 모음입니다. 예를 들어 보고서 R17에서 얻은 연결들과 매뉴얼 M17에서 얻은 연결들을 서로 다른 그래프에 넣을 수 있습니다.

Turtle은 한 그래프를 표현합니다. 아래는 그래프 묶음을 적는 **TriG** 구문입니다. `@prefix`와 트리플은 익숙하지만, 이름 뒤의 중괄호가 해당 named graph에 들어가는 트리플을 묶습니다.

```trig
@prefix ex: <https://example.org/fab/> .

ex:graphR17 {
    ex:E01 ex:usesPart ex:P7 .
}
ex:graphM17 {
    ex:E01 ex:usesManual ex:M17 .
}
ex:graphR17 ex:sourceDocument ex:R17 .
```

첫 묶음의 그래프 이름은 `graphR17`, 안의 내용은 E01이 P7을 사용한다는 트리플입니다. 두 번째 그래프에는 매뉴얼 연결이 있습니다. 마지막 트리플은 중괄호 밖, 즉 이 예의 default graph에 있습니다. 이것은 graphR17이라는 이름의 대상에 sourceDocument R17을 연결합니다.

여기서 ‘graphR17은 R17에서 수집한 내용의 묶음이다’라는 관례를 도입한 것은 **우리 설계**입니다. RDF dataset의 형식만으로 그래프 이름이 언제나 문서 출처를 뜻하거나, 그 내용이 참이거나, 검토가 끝났다는 결론은 나오지 않습니다. named graph를 쓰더라도 출처 어휘와 운영 정책이 필요합니다. [RDF Concepts §4](https://www.w3.org/TR/rdf11-concepts/#section-dataset), [TriG](https://www.w3.org/TR/trig/)

질의에서도 어떤 그래프를 읽는지 중요합니다. SPARQL은 앞 수업에서 본 것처럼 변수로 패턴을 찾는 언어입니다. 다음에서 `?g`는 그래프 이름, `?part`는 부품을 담는 변수입니다.

```sparql
PREFIX ex: <https://example.org/fab/>
SELECT ?g ?part WHERE {
  GRAPH ?g { ex:E01 ex:usesPart ?part }
}
```

이 dataset의 named graph들에서 지정 패턴을 찾으면 예상 결과는 `graphR17, P7` 한 행입니다. `GRAPH ?g`의 중괄호는 변수 g가 가리키는 named graph 안에서 찾으라는 뜻입니다. default graph와 모든 named graph의 내용을 자동으로 합쳐 조회한다고 가정하지 마세요. 실제 endpoint가 구성하는 default dataset과 질의의 그래프 범위를 확인해야 합니다. [SPARQL §13 RDF datasets](https://www.w3.org/TR/sparql11-query/#rdfDataset)

## 4. ‘이 그래프의 최신 상태’와 ‘그때의 사실’은 다릅니다

11월 보고서가 정정돼 E01의 사용 부품이 P8이었다고 밝혀졌다고 합시다. 트리플 P7을 지우고 P8을 넣으면 현재 그래프의 내용은 바뀝니다. 하지만 그것만으로 과거에 어떤 기록이 존재했고 왜 바뀌었는지는 보존되지 않습니다.

현재 상태만 답하면 되는 시스템은 단순 교체를 선택할 수 있습니다. 당시 판단의 근거를 설명해야 하는 시스템은 원천 버전과 수정 이력을 남겨야 합니다. ‘장비가 실제로 부품을 바꿨다’와 ‘원래 문서의 오기를 고쳤다’도 다른 사건입니다. 전자는 실세계 변경, 후자는 지식 기록의 정정입니다. 두 가지를 같은 ‘변경’ 관계로 처리하면 시간 질의가 모호해집니다.

RDF는 사건·시간을 표현할 어휘를 사용해 이를 나타낼 수 있습니다. 다만 한 그래프에 날짜 값 하나를 붙였다고 유효기간·이력·철회가 자동 관리되는 것은 아닙니다. 이후 U17에서 출처와 수명주기의 정책으로 발전시킬 내용입니다. 이 수업에서는 **표현할 수 있는 능력과 운영 의미를 설계하는 책임이 별개**라는 점을 예제로 이해하면 됩니다.

## 5. RDF 1.2에서 달라지는 부분을 읽는 방법

RDF 관련 글에서는 RDF-star나 triple term이라는 용어도 만날 수 있습니다. 이는 진술에 관한 정보를 다루는 표현과 관련됩니다. RDF 1.2 Concepts는 다른 트리플의 목적어 위치에 triple term을 사용할 수 있게 하는 데이터 모델을 설명합니다. 이 문서를 확인한 2026-11-18 기준으로 2026-11-16 Candidate Recommendation Draft이며, 해당 페이지의 Latest Recommendation은 RDF 1.1을 가리킵니다. [RDF 1.2 고정 판본](https://www.w3.org/TR/2026/CRD-rdf12-concepts-20261116/)

그러므로 RDF 1.1 reification 예제에 최신 초안의 구문을 섞어 놓고 모든 엔진에서 그대로 작동한다고 설명하면 곤란합니다. 사용하는 파서·저장소·질의 언어가 어느 버전과 표현을 지원하는지 확인해야 합니다. 새로운 표기라도 사건과 주장, 진술 내용과 사실 채택의 차이를 설계해야 한다는 문제는 남습니다. 이 단원의 실행 검증은 RDF 1.1 예제에 한정합니다.

## 6. 설명해 볼 질문과 해설

**질문 1:** 문서 R17이 미검토 상태인데 E01→usesPart→P7을 운영 그래프에 바로 넣었습니다. 출처 링크가 있으니 이 상태를 ‘검증된 사실’이라고 불러도 될까요?

**해설:** 출처 링크는 어디에서 얻었는지 설명하지만 내용의 정확성을 검증했다는 뜻은 아닙니다. 미검토 후보와 채택된 주장을 어떻게 구분할지 정책이 필요합니다. 모든 정보를 같은 그래프에 둘 수도 있지만, 그 경우 조회 시 상태를 빠뜨리지 않도록 별도 설계가 필요합니다.

**질문 2:** 운전 3건을 각각 나타내는 drive1~3과, 한 운전에 대한 보고서 두 건은 같은 종류의 노드인가요?

**해설:** drive1~3은 서로 다른 실제 사건을 나타냅니다. 보고서 두 건은 같은 사건에 관한 서로 다른 기록입니다. 사건을 세는 질의와 기록을 세는 질의는 분리해야 합니다. 보고서 수를 운전 횟수로 합산하면 잘못된 결과가 나옵니다.

**질문 3:** named graph 두 개가 같은 트리플을 포함하면 트리플의 중복이라는 이유로 문서별 구분이 사라지나요?

**해설:** 각 그래프 내부는 트리플의 집합이지만 dataset에서 두 named graph는 구분됩니다. 어느 그래프에 속했는지 조회할 수 있습니다. 다만 두 그래프를 한 그래프로 합치면 같은 트리플은 하나가 되므로 출처별 발생 구분을 유지할 방법을 별도로 보존해야 합니다.

이제 RDF가 ‘주어·술어·목적어 세 칸’ 이상으로 어떤 설계 문제를 담는지 설명할 수 있습니다. 다음 단계에서는 도메인의 클래스·관계·가정을 정하는 ontology와, 그 규칙에서 따라 나오는 추론 및 데이터 검사를 연결합니다.
