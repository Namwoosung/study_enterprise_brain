# 그래프 질의를 선택하고 틀린 관계의 파급을 따라가기

앞 수업의 승인 대장 행을 읽는 방식은 업무가 반복될수록 유용합니다. 사용자가 오늘은 W-207을 묻고 내일은 W-305를 묻더라도 “작업→부품→변경→승인자”의 모양은 같습니다. 반면 관계 유형이 다양한 지식 탐색 화면에서는 질문마다 보고 싶은 경로가 달라질 수 있습니다. 어떤 부분을 사람이 미리 정하고, 어떤 부분을 질문에 맞춰 고를지에 따라 그래프 활용 RAG의 설계가 나뉩니다.

## 직접 탐색, 정해 둔 질의, 모델이 구성한 질의

**직접 탐색**은 프로그램이 W-207의 나가는 관계 목록을 읽고 `REPLACED`인 것만 고른 뒤 다음 노드를 찾아가는 방식입니다. 앞 수업의 로컬 사례에서 사용한 방식입니다. 그래프 관계를 데이터베이스에 보관한다면, 찾아갈 형태를 **그래프 패턴**으로 써서 반환할 행을 지정할 수 있습니다. 그래프 패턴은 ‘어떤 유형의 노드들 사이에 어떤 종류의 관계가 있어야 하는지’를 질의에 표현한 것입니다. 속성 그래프를 읽는 Neo4j의 언어는 **Cypher**이고, RDF의 문장(주어·술어·목적어)을 패턴으로 조회하는 표준 언어는 **SPARQL**입니다. 저장된 데이터 모델에 맞는 언어를 선택합니다. [Neo4j Cypher Manual, MATCH](https://neo4j.com/docs/cypher-manual/current/clauses/match/), [W3C SPARQL 1.1 Query Language, §2, §5.1](https://www.w3.org/TR/sparql11-query/#BasicGraphPatterns)

### 정해진 질문에 맞추어 값만 채우는 Cypher

예를 들어 업무팀이 `Work`, `Part`, `Change`, `Person`, `Supplier`라는 노드 라벨을 사용한다고 가정합니다. `Work`에는 `id`가 있고, `Change`에는 적용 시작일 `validFrom`과 적용 종료일 `validTo`가 있습니다. 날짜 속성은 데이터베이스의 날짜 값이고, 종료일이 없는 행에는 그 속성이 없습니다. 별칭 후보 확인은 질의 전단에서 끝내 `partId`로 넘깁니다.

```cypher
MATCH (w:Work {id: $workId})-[r:REPLACED]->(p:Part {id: $partId})
MATCH (p)-[h:HAS_CHANGE]->(c:Change)
WHERE c.validFrom <= date($asOf)
  AND (c.validTo IS NULL OR date($asOf) < c.validTo)
MATCH (c)-[s:NEW_SUPPLIER]->(supplier:Supplier)
MATCH (c)-[a:APPROVED_BY]->(person:Person)
RETURN p.id AS part, c.id AS change,
       supplier.name AS supplier, person.name AS approver,
       [r.source, h.source, s.source, a.source] AS evidence
ORDER BY change, approver
```

`(p:Part {id: $partId})`는 노드 변수 `p`에 `Part` 라벨을 가진 노드를 연결하되 그 노드의 `id`가 입력 `partId`와 일치해야 한다는 뜻입니다. 대괄호의 `r:REPLACED`는 첫 관계를 `r`에 담습니다. `WHERE`는 기간 조건을 만족한 변경 건만 남기고, `IS NULL`로 종료일 값이 없는 경우를 다룹니다. `RETURN`은 결과에 넣을 항목을 고릅니다. `r.source`는 첫 관계에서 읽어 낸 원문 조각 ID입니다. 공급 변경 관계와 공급사 관계가 같은 G03을 참조하므로 원문을 회수할 때 중복을 제거합니다. 별칭 확인용 G02는 별칭 확인 단계에서 별도로 회수합니다.

`$workId=W-207`, `$partId=VL-042`, `$asOf=2026-04-10`일 때 예상 행은 `VL-042 | CR-119 | 한빛정밀 | 김하늘 | [G01, G03, G03, G04]`입니다. 쿼리가 행을 여러 개 돌려주면 현재 변경 건이 여럿인지, 데이터가 중복됐는지 확인합니다. 승인 간선이 그래프에 없으면 필수 `MATCH`에서 그 분기가 반환되지 않습니다. 간선이 남은 상태에서 원문 G04가 누락되거나 접근이 제한되면 쿼리는 여전히 행을 반환할 수 있습니다. 이때는 후속 원문 회수와 권한 검사에서 승인 사실을 확정할 수 있는지 판단합니다. 부분 답변이 필요한 응용은 공급 건만 먼저 확인하고 승인 근거 상태를 따로 반환하게 할 수 있습니다. 이 예의 [Python 확인](../../examples/rag-graph/verify.py)은 원천 fixture에서 경로와 날짜를 계산합니다. 위 Cypher 구문의 실행 결과는 예상 결과입니다.

### 같은 패턴을 RDF에서 읽는 SPARQL

동일 사실을 RDF에 저장했다고 가정하면 `ex:W-207 ex:replaced ex:VL-042 .` 같은 **트리플**이 있습니다. 마침표는 문장 끝, `ex:`는 공통 주소 앞부분을 짧게 붙이는 **접두사**입니다. `?change`처럼 물음표로 시작하는 것은 결과에서 일치하는 값을 담을 **변수**입니다. 아래 SPARQL은 승인자 이름 자체 대신 승인자 식별자를 남깁니다. 출처는 RDF에서 작업에 어떤 원문 또는 출처 그래프를 연결했는지에 맞춰 별도로 조회합니다.

```sparql
PREFIX ex: <https://example.org/rag-graph/>
PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>
SELECT ?change ?supplier ?person
WHERE {
  VALUES (?work ?part ?asOf) { (ex:W-207 ex:VL-042 "2026-04-10T00:00:00+09:00"^^xsd:dateTime) }
  ?work ex:replaced ?part .
  ?part ex:hasChange ?change .
  ?change ex:validFrom ?start ;
          ex:newSupplier ?supplier ;
          ex:approvedBy ?person .
  OPTIONAL { ?change ex:validTo ?end . }
  FILTER (?start <= ?asOf && (!BOUND(?end) || ?asOf < ?end))
}
```

`VALUES`는 질의에서 사용할 입력 값을 지정합니다. `^^xsd:dateTime`은 입력 문자열을 날짜·시간 자료형으로 해석한다는 표시입니다. 업무 일자의 경계를 한국 시각(+09:00) 자정으로 두고 RDF의 시작·끝 값도 같은 형식으로 기록했다고 가정합니다. 세미콜론은 같은 주어에 서로 다른 술어를 이어 쓰는 표기입니다. `OPTIONAL`은 끝 날짜가 있는 경우에만 `?end`에 값을 넣습니다. `BOUND(?end)`는 그 변수에 값이 있는지 검사하고, `!`는 결과를 뒤집습니다. `&&`와 `||`는 각각 ‘그리고’와 ‘또는’입니다. 예상 결과는 CR-119, 한빛정밀 ID, 김하늘 ID의 조합이며, 독립 검토에서 이 스키마로 만든 합성 RDF와 RDFLib 7.6.0을 사용해 확인했습니다. 원문 근거의 위치는 위 결과 열만으로 알 수 없습니다. RDF에서 출처를 읽으려면 출처를 사건이나 별도 주장 리소스에 붙이거나, 출처가 있는 그래프의 이름을 반환하는 식의 모델링이 필요합니다. [W3C SPARQL 1.1, §4.2, §6, §10.2, §17.3–17.4](https://www.w3.org/TR/sparql11-query/#GraphPattern)

### 시작점을 자유롭게 찾고 경로는 제한하는 방법

질문에 “릴리프 밸브”처럼 이름만 나오면 설명 벡터 검색으로 시작 후보를 찾고, 일치한 부품에서 미리 정한 공급 변경·승인 패턴을 추가로 조회할 수 있습니다. 예를 들어 벡터 단계가 VL-142와 VL-042를 둘 다 반환해도, W-207의 실제 교체 부품과 일치하는 쪽만 승인 질의에 넘깁니다. 이 설계에서 벡터는 후보를 찾고, 그래프 패턴은 후보 주변에 어떤 문맥을 붙일지 제한합니다. Neo4j의 `VectorCypherRetriever`가 벡터 유사도 검색 뒤 사용자 지정 Cypher를 실행하는 예입니다. `HybridCypherRetriever`는 벡터와 전문 검색 후보를 양쪽에서 찾은 뒤 연결 문맥을 더할 수 있습니다. 전문 검색은 본문의 단어나 코드를 찾는 색인을 이용합니다. [Neo4j GraphRAG for Python, Vector + Cypher Retriever 및 Hybrid Cypher Retriever](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html#hybrid-cypher-retrievers)

### 질문을 보고 패턴을 새로 구성하는 방법

**Text-to-query**는 자연어 질문을 읽고 질의문을 만드는 방식입니다. `Text2CypherRetriever`를 사용하면 첫 모델이 질문과 스키마 설명에 맞춰 Cypher를 쓰고, 그 질의의 결과를 다음 모델이 읽어 답변합니다. 스키마는 어떤 라벨, 관계, 속성, 자료형이 쓰이는지 알려주는 정의입니다. 예를 들어 승인자 관계가 현재 `APPROVED_BY`이고 사람 이름의 속성이 `name`이면 그렇게 알려줍니다. 질문이 새롭고 패턴 수가 많을 때 편리하지만, 문법 검사를 통과한 쿼리도 실제 의미를 틀릴 수 있습니다. `REVIEWED_BY`가 별도로 있다면 최종 승인자가 아닌 검토자를 조회할 수 있습니다. [Neo4j GraphRAG for Python, Text2Cypher Retriever](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html#text2cypher-retriever)

운영에서는 조회 전용 권한의 실행 주체를 두고, 접근 가능한 라벨·관계·사용자 범위·반환 필드·질의 비용을 시스템이 제한합니다. 자주 쓰는 승인 조회라면 검토된 질의 틀에서 작업과 기준일 같은 값만 입력으로 받는 편이 단순합니다. 동적으로 만든 질의가 필요하면 실행 전에 허용된 형태인지 구조적으로 확인합니다. 예를 들어 이 서비스는 공급 변경 검색만 허용하므로 허용된 노드·관계 패턴인지 확인하고, 단계 수와 시간 제한도 둡니다. 자연어로 ‘조회만 하라’고 지시하면 결과를 검토하기 좋아지지만 실제 권한 집행은 별도로 필요합니다. 반환된 원문도 답변 구성 전에 요청자의 읽기 범위를 검사합니다.

## 관계 한 줄을 바꿔 보고 파급을 살핍니다

가상의 추출 과정이 G04의 CR-119와 G09의 CR-121 행을 섞어, CR-119에 `APPROVED_BY → 이별`을 붙였다고 해 보겠습니다. 변경된 것은 관계 한 건이고, `김하늘`과 `이별` 모두 올바른 `Person` 유형입니다. 타입 검증만 하면 관계가 통과할 수 있습니다.

| 단계 | 올바른 경로 | 오류가 있는 경로에서 보이는 결과 |
| --- | --- | --- |
| 시작점과 기간 | W-207, VL-042, CR-119 | 그대로입니다. 이 단계만 보면 문제를 찾기 어렵습니다. |
| 승인 관계 | CR-119 → 김하늘, G04 | CR-119 → 이별, G09가 붙어 있습니다. |
| 원문 회수 | G04에서 CR-119와 김하늘을 확인 | G09는 CR-121의 승인 행입니다. 변경 번호부터 다릅니다. |
| 요약·색인 | R-A2는 확인한 공급·승인 규칙을 설명 | 틀린 승인자 서술을 입력받은 파생 설명에 이별이 전해질 수 있습니다. |
| 생성 | 현재 공급사 한빛정밀, 승인자 김하늘 | 연결만 믿으면 이별을 CR-119 승인자라고 답할 수 있습니다. |

오류가 발생한 연결을 삭제하거나 정정해도 보고서·개체 설명·임베딩·캐시가 자동으로 일치하지는 않습니다. **파생 산출물**은 원문이나 관계를 입력에 넣어 만든 데이터입니다. 입력과 출력의 의존성을 보존하면 CR-119 관계가 바뀔 때 어느 설명, 보고서, 검색 색인, 이전 답변 캐시를 갱신해야 하는지 찾을 수 있습니다. 해당 구간에서 커뮤니티를 나눈 기준 자체가 바뀌었으면 이전 그룹뿐 아니라 새로운 그룹의 보고서까지 다시 만들어야 할 수 있습니다. 어느 부분을 다시 계산할지는 변경한 자료와 사용한 알고리즘에 달려 있습니다.

증분 갱신은 변경된 부분과 그 영향을 받는 부분을 다시 만드는 일입니다. 예를 들어 사람 이름 오탈자만 고쳐도 개체 설명 벡터를 재계산해야 할 수 있습니다. 여러 문서가 같은 변경 레코드를 뒷받침할 때는 원문 하나 철회가 관계 전체의 철회를 뜻하는지 별도로 확인합니다. 단절을 줄이려면 원문과 산출물의 판본을 연결하고, 사용자 질문 하나가 서로 맞는 스냅샷을 보도록 배포 순서를 정합니다. 한쪽 색인만 갱신하면 관계는 새 승인으로 나왔는데 근거 링크는 이전 행을 열 수 있습니다. [Microsoft GraphRAG, Indexing Dataflow](https://microsoft.github.io/graphrag/index/default_dataflow/)

### 권한은 원문에서 요약까지 이어집니다

승인 대장 원문은 구매팀만 읽을 수 있고 정비원은 공급 변경 대장만 읽을 수 있다고 가정해 보겠습니다. R-A2를 더 자세히 써서 G04의 “김하늘이 승인했다”를 추가한 판본을 정비원에게 보여 주면, 클릭할 수 있는 원문 링크를 막아도 정보는 이미 전달됩니다. 관계·개체 설명·보고서 어디에 승인자 사실이 저장되었는지 따라가고, 요청자가 볼 수 있는 입력만으로 조회하거나 권한 집합에 맞는 산출물을 관리해야 합니다.

가장 직접적인 대응은 공유 범위를 가진 원문으로 공용 보고서를 만들고, 제한된 승인 원문과 여기서 파생한 관계·설명·캐시는 권한이 있는 요청에만 사용하도록 범위를 나누는 것입니다. 여러 권한의 자료를 섞어 요약해야 하는 응용에서는 문장별 출처뿐 아니라 요약 과정에서 드러나는 간접 내용도 고려합니다. ‘회사 전체에서 승인 한 건’ 같은 집계가 제한된 건수나 존재 여부를 드러낼 수 있기 때문입니다. 기간·권한·출처의 일관성은 시스템이 관리할 조건입니다. 모델이 문장 뒤에 링크를 생성하는 것만으로 생기지 않습니다.

## 구축과 질문 시점의 일을 함께 비교합니다

| 설계 | 구축 작업 | 질문 처리 | 판단할 질문 |
| --- | --- | --- | --- |
| 구조화 전용 질의 | 노드·관계 유형과 ID, 스키마, 출처, 접근 규칙을 합의합니다. | 주어진 코드와 조건으로 조회합니다. | 필요한 업무 경로가 명확하고 충분히 기록되나요? |
| 벡터+그래프 | 위 구조와 함께 검색할 설명의 벡터를 생성합니다. | 표현이 다른 후보를 찾아 그래프에서 관계 근거를 넓힙니다. | 시작점이 애매할 때 다음 단계의 제약을 적용할 수 있나요? |
| Microsoft GraphRAG식 보고서 | TextUnit, 추출, 통합, 계층적 군집, 보고서, 필요한 임베딩을 만듭니다. | Local에서 혼합 문맥을 모으거나 Global에서 보고서들을 Map·Reduce합니다. | 전역 질문에 다양한 문서 범위를 쓰는 것이 자주 요구되나요? |

그래프를 만들 때 초기 처리 비용뿐 아니라 어떤 변경이 반복적으로 들어오는지와 누가 검토할지도 따집니다. 수백 건의 개정에서 동일 좁은 경로를 쓰는 업무는 미리 검토한 조회 조건을 재사용하는 편이 효율적일 수 있습니다. 일주일마다 전역 보고를 만들고 자료가 매번 새로 쌓이는 업무라면 군집·보고서에 들어가는 시간과 재배포 작업을 비교에 넣습니다. 소스 정책이 바뀌면 접근 규칙을 재구성해야 합니다. 정확한 비용과 지연은 같은 조건에서 관찰한 로그가 있어야 비교할 수 있습니다.

## 설명 연습

1. CR-119를 조회하는 질의가 `REVIEWED_BY`를 반환했습니다. 왜 문법 검사 결과가 좋아도 이 답변을 채택할 수 없나요? 어디에서 오류를 잡을 수 있나요?
2. G04가 정정되어 승인자가 달라졌습니다. 원문 앞뒤 문장이 그대로라면 무엇을 갱신해야 할까요? 질의 시점에 그래프에서 직접 읽을 경우와 보고서 검색일 경우를 함께 설명해 보세요.
3. 장비 모델과 작업 번호가 정확히 주어지는 반복 질문 한 종류와, 여러 부서의 새 제도를 함께 비교하는 질문 한 종류를 만들어 보세요. 두 질문에 어떤 검색 방식을 붙이고 어떤 자료를 답변에 넣을까요?

### 해설

1. `REVIEWED_BY`는 검토 관계로, 질문이 요구한 최종 승인 관계와 뜻이 다릅니다. 승인자 조회의 허용된 패턴을 `APPROVED_BY`로 제한하거나 질의가 반환한 행을 원문에서 확인합니다. 맞는 속성 타입과 실행 성공은 질문 의미에 맞았음을 보증하지 않습니다.
2. 해당 원문 판본과 관계의 원문 참조를 갱신합니다. 직접 조회에서는 CR-119 연결을 최신 상태로 고친 뒤 최신 출처 행이 반환되는지 확인합니다. 보고서 또는 임베딩이 관계를 입력으로 이미 사용했다면 갱신 대상입니다. 이전 결과를 재사용하는 캐시는 같은 판본 기준으로 갱신하거나 무효화합니다.
3. 예를 들어 “작업 W-207의 현재 공급 변경 승인자”는 고정 질의와 대장 원문을 사용합니다. “부서별 예외 처리의 기록 방법이 어떻게 바뀌었나”에는 시기와 부서 범위를 먼저 정하고 주제 묶음 요약을 비교할 수 있습니다. 예외 자체를 열거할 때는 각 요점의 원문을 다시 확인합니다.
