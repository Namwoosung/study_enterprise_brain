# D1. 의미를 선언하는 것과 데이터를 검사하는 것

**목표:** 공리의 방향·존재 조건·추론 범위를 구별하고, SHACL 검사 대상과 실행 순서가 결과를 바꾸는 이유를 설명한다.

[M2 표현 기초](../M2_representation.md)와 [M5 검증 기초](../M5_validation.md)를 먼저 읽는다. 아래 작은 데이터는 기존 사례를 변형한 반례이며 실제 원천 기록을 수정하지 않는다.

<a id="d1-01"></a>
## 1. 모델은 질문에 대한 계약이다

Equipment라는 클래스가 있다는 것만으로는 좋은 모델인지 평가하기 어렵다. “작업 당시 적용 절차를 찾는다”라는 질문은 사건·장비·시간·문서 적용 범위가 함께 표현되어야 한다. 모델의 완성도는 클래스 개수보다 **필요한 답을 구분할 수 있는가**로 판단한다.

모델을 세 층으로 나누어 검토해 보자. 첫째, 용어의 의미다. usedDocument는 사용했다고 기록한 문서이고 requiredDocument는 정책상 적용해야 할 문서라는 차이를 정한다. 둘째, 표현 구조다. 시점과 참여자가 있는 Run 노드에 관계를 붙인다. 셋째, 제출 데이터의 계약이다. 작업에 문서 ID가 반드시 하나 있어야 한다는 조건을 정한다. 이 세 층은 하나의 파일에 있을 수도 있지만 서로 대체되지 않는다.

| 질문 | 이 사례에서 필요한 구분 | 반례 |
|---|---|---|
| 어떤 절차를 사용했나? | 작업 기록의 usedDocument | 정책에 맞추어 기록을 덮어씀 |
| 어떤 절차를 써야 했나? | 대상·유효 구간·승인 정책 | 현재 최신 문서를 모든 과거에 적용 |
| 이 행을 받아도 되나? | 필수값·타입·개수·처리 정책 | ontology가 있으므로 입력 검사를 생략 |

이는 교재의 설계 계약이다. 범위를 질문으로 정하고 반복 개선한다는 출발점은 [Ontology Development 101, Step 1](https://protege.stanford.edu/publications/ontology_development/ontology101-noy-mcguinness.html)에 근거한다.

<a id="d1-02"></a>
## 2. 필요조건과 충분조건을 바꾸면 결론이 달라진다

다음은 읽기용 논리 표기다. ⊑는 왼쪽 종류가 오른쪽 조건에 포함됨을, ≡는 두 방향의 포함을 뜻한다.

~~~text
A. InspectionRun ⊑ Run
B. InspectionRun ⊑ uses some InspectionTool
C. InspectionRun ≡ Run and (uses some InspectionTool)
~~~

A와 B는 검사 작업이라고 아는 대상이 어떤 조건을 만족해야 하는지 말한다. B만으로는 검사장비를 사용하는 모든 작업이 InspectionRun이라고 따라오지 않는다. C는 반대 방향도 허용한다. Run이면서 검사장비를 쓰는 사건을 InspectionRun으로 분류할 수 있다.

여기서 유지보수 작업도 검사장비를 사용할 수 있다고 해보자. 그 작업을 Run으로 분류했다면 C는 원치 않는 검사 작업 분류를 만들 수 있다. “대체로 그렇다”는 업무 설명을 충분조건으로 승격한 결과다. 정의를 강하게 만들기 전에 분류되어서는 안 되는 반례를 넣어야 한다.

OWL 클래스 표현과 공리의 해석은 [OWL 2 Primer §5](https://www.w3.org/TR/owl2-primer/#Advanced_Class_Relationships)에서 확인한다. 위 업무 예시는 해당 의미를 적용한 교재의 변형 사례다.

<a id="d1-03"></a>
## 3. 존재·전체·개수는 서로 다른 조건이다

“작업은 문서를 사용한다”를 정교하게 읽으면 다음 네 문장은 다르다.

| 표현 | 의미 | 보장하지 않는 것 |
|---|---|---|
| usedDocument some Document | Document에 속하는 사용 대상이 적어도 하나 존재 | 그 대상의 ID가 파일에 적혀 있음 |
| usedDocument only Document | 이 관계의 모든 대상은 Document | 관계 대상이 하나라도 존재 |
| usedDocument exactly 1 Document | Document에 속하는 서로 다른 대상이 정확히 하나 | 다른 종류의 대상까지 포함한 전체 개수가 하나 |
| SHACL minCount 1, maxCount 1 | 검사 그래프의 해당 path 값 수가 하나 | 그 값이 현실적으로 올바른 문서 |

only의 존재 함정과 some의 의미는 [OWL Primer §6.1](https://www.w3.org/TR/owl2-primer/#Property_Restrictions)에 설명되어 있다. 단, 파일에 관계가 없다는 사실만으로 실제 관계도 없다고 결론내리는 것은 열린 세계 가정에 맞지 않는다. “대상이 실제로 0개인 경우 only가 성립할 수 있다”와 “기록이 없으니 only라고 추론한다”는 다른 말이다.

개수도 IRI 문자열을 세는 것과 개체를 세는 것이 다르다. 최대 1개라는 공리 아래 D02와 DocRevision2가 모두 연결되어도 두 이름이 같은 개체일 수 있다. 둘이 다르다는 조건까지 들어오면 해석이 달라진다. [OWL Primer §4.7 및 §6.2](https://www.w3.org/TR/owl2-primer/)

실무에서 “필수 입력 누락을 잡고 싶다”면 검사 그래프의 값을 세는 제약을 직접 작성하는 편이 의도를 분명히 한다. 반대로 존재하는 대상의 이름을 아직 모르는 지식도 표현하려면 논리적 존재 조건이 유용하다.

<a id="d1-04"></a>
## 4. SHACL은 무엇을 검사할지부터 정해야 한다

기존 shape가 sh:targetClass ex:Run을 대상으로 삼는다고 하자. 잘못 생성한 작업에서 rdf:type ex:Run이 빠졌고 다른 타입·하위 클래스 정보도 없다면 그 대상이 검사에서 빠질 수 있다. 검사 결과 conform=true만 보고 필수값이 모두 있다고 결론내리면 안 된다.

작업의 정의상 forLot 관계가 있는 모든 주체를 검사하려는 경우에는 sh:targetSubjectsOf ex:forLot 같은 대안을 검토할 수 있다. 입력 목록을 알고 있다면 targetNode로 명시할 수도 있다. 검증 보고서 외에 **예상 대상 수, 실제 대상 수, 제외 사유**를 대조한다. [SHACL §2.1.3 Targets](https://www.w3.org/TR/shacl/#targets)

또 하나의 함정은 “추론 없음이면 클래스 계층도 전혀 보지 않는다”는 가정이다. sh:class는 SHACL instance 정의를 사용하며 데이터 그래프의 rdf:type과 rdfs:subClassOf 경로를 반영한다. 범용 OWL 추론기를 켜는 것과 같은 말은 아니다. [SHACL §1.3 및 §4.1.1](https://www.w3.org/TR/shacl/#ClassConstraintComponent)

예를 들어 E01 a InspectionTool과 InspectionTool subClassOf Equipment가 데이터 그래프에 있으면 sh:class Equipment를 통과할 수 있다. 반면 “usedEquipment의 range가 Equipment”라는 정보만 있고 E01 타입·계층 경로가 없다면, range 추론을 먼저 했는지에 따라 검사 결과가 달라질 수 있다.

그래서 검증 실행 명세에는 데이터 그래프, shapes 그래프, 사전 추론 방식, 검사 대상 선택을 함께 적는다. 타입이 없다는 오류를 찾는 것이 목적이라면 사전 추론으로 타입을 보충한 뒤 검사할 때 그 누락이 가려질 수도 있다.

<a id="d1-05"></a>
## 5. 표현력을 늘리면 실행 전략도 선택해야 한다

OWL 2의 EL·QL·RL은 단순한 성능 등급이 아니다. 표현 가능한 문장에 제약을 두어 서로 다른 추론 작업에 적합하게 만든 프로파일이다. EL은 큰 클래스·속성 모델, QL은 많은 개체 데이터에 대한 질의 재작성, RL은 규칙 기반 실행을 검토하는 출발점이 된다. 어느 하나가 다른 것의 상위 버전이라는 포함 관계로 이해하지 않는다. [OWL 2 Profiles §1](https://www.w3.org/TR/owl2-profiles/)

우리 사례에서 하위 클래스 몇 개만 필요하면 곧바로 전체 OWL DL 추론 환경을 도입할 필요는 없다. 그러나 “소형 RL 예제가 동작했으니 모든 OWL 공리를 처리한다”는 주장도 성립하지 않는다.

추론 결과를 언제 만들지도 선택한다.

- **미리 계산:** 질의 전에 유도 관계를 저장한다. 반복 읽기가 단순해질 수 있지만 원천 삭제·정정 때 유도 결과를 다시 관리한다.
- **질의 시 해석:** 질의나 실행 계획에 의미를 반영한다. 저장량을 줄일 수 있지만 지원 범위와 질의 비용을 확인해야 한다.
- **혼합:** 자주 쓰는 타입만 미리 계산하고 나머지는 필요할 때 다룬다.

이 세 선택은 구현 전략이며 OWL 프로파일 이름과 일대일로 동일하지 않다. 성능은 선택 엔진·데이터·질의로 측정한다. 본 교재의 실행 예제는 RDFS와 OWL RL의 일부 동작만 확인한다.

<a id="d1-06"></a>
## 6. 의미 모델의 회귀 검사는 무엇을 확인해야 하나?

새 공리를 추가했을 때 “새 정답이 나왔나”만 보면 부족하다. 기존에 답할 수 있어야 했던 질문, 나오면 안 되는 분류, 검사에서 빠지면 안 되는 대상, 모순이 생기면 안 되는 조건을 함께 둔다.

실습에서는 세 반례를 실행한다. 타입 없는 작업이 targetClass 검사에서 빠지는 경우, targetSubjectsOf로 누락을 발견하는 경우, range 추론 전후에 sh:class 결과가 달라지는 경우다. [심화 실행 예제](../examples/verify_deep.py)는 이 범위만 확인하며 전체 OWL DL 판정기가 아니다.

**확인 질문**

1. 모든 사용 문서가 Document라는 말로 문서 누락을 찾을 수 있는가?
2. 검사 결과가 통과했는데 작업 100개 중 80개만 검사했다면 무엇부터 확인할 것인가?
3. 새로운 충분조건이 유지보수 작업까지 검사 작업으로 분류하면 무엇을 수정해야 하나?

### 해설

1. 존재 조건과 데이터 제출 조건을 따로 정의한다.
2. target 선택·타입 누락·실제 검사 대상을 확인한다.
3. 조건 방향·업무 정의·반례를 검토한다. 데이터만 임의로 지우기보다 공리가 의도에 맞는지 먼저 본다.

**설명 연습:** “Ontology가 있으면 검증이 끝난다”는 주장에 대해 존재 조건과 검사 대상이라는 서로 다른 반례를 하나씩 설명하라.
